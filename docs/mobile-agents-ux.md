## 0. 前提：移动端是展示层

桌面已经有完整的智能体体系：`AgentDefinition`（身份 / 长期指令 / 引擎 / 插件 /
上下文绑定）、`Automation`（触发器 → 动作 → 输出）、`AgentRun`（daemon 拥有调度、
claim、投递、对账、回收）。移动端**不复制任何一条**，只做三件事：

1. **投影** daemon 已有的状态（定义目录、自动化目录、Run 历史、对话）。
2. **转发** 用户意图给 daemon（批准 / 回复 / 启停 / 运行一次 / 新开对话）。
3. **在没有桌面时兜住需要人的那一刻**（等审批、等输入、失败）。

由此推出三条硬约束，后面所有取舍都从这里来：

- **不在手机上做创作。** 定义编辑、触发器编辑、插件勾选、上下文目录绑定
  ——这些是「坐在 Mac 前想清楚一次」的动作，手机上只读展示 + 「去桌面编辑」提示。
  强行塞进手机会得到一个既难用又要长期跟着桌面改的表单。
- **手机上没有本地调度、没有本地 Run 状态机。** Run 的一切状态来自投影；
  手机发出的每个动作都是一次幂等命令，结果等 daemon 回帧，不做乐观状态机。
- **不展示令牌。** 外部触发只显示「外部触发」，与桌面目录同口径。

## 1. IA：智能体进哪里

现状底部导航：`Console / Projects / Settings`。

桌面上「智能体」和「自动化」是两个一级入口，但那是给创作场景的分法。手机上
用户的问题只有两个：**「有事等我吗」** 和 **「我那些跑着的东西现在怎么样」**。
所以不照搬两个一级入口。

```
底部导航（4 项）
├── 指挥台 Console   ← 默认首屏，不变
│   ├── 等我处理     ← 现有卡片 + 新增「自动化来源」标识
│   ├── 正在跑       ← 现有会话 + 新增自动化 Run
│   └── 刚完成       ← 现有 + Run 终态摘要
├── 智能体 Agents    ← 新增。顶部分段：对话 / 自动化
│   ├── 对话         ← 按智能体分组的对话列表 + 新建对话
│   └── 自动化       ← 自动化目录（启停 / 立即运行）+ Run 历史
├── 项目 Projects    ← 不变
└── 设置 Settings    ← 不变
```

**为什么合成一个 tab 而不是加两个。** 底部导航超过 4 项就开始摊薄每一项的可达性，
而「自动化」在手机上的日常访问频率远低于指挥台——真正紧急的东西已经被指挥台接走了，
留在这里的是「翻一下昨晚那条跑成什么样」。两者共享「智能体」这个心智对象，
用分段控件区分**同一对象的两种时间形态**（我主动开的对话 / 它自己跑的运行），
不是两种信息结构——这一点和 `mobile-ux-redesign.md` 批评过的
「SegmentedButton 伪装成筛选器」不同，那里切出来的是两种布局，这里两侧都是列表。

**为什么不塞进 Projects。** 智能体对话的工作目录是 daemon 分配的 space，
不属于任何项目。挂进项目树会造出一个假的归属关系。

## 2. 屏 A · 指挥台：自动化闯进来的那一刻

这是整个功能在手机上**唯一不可替代**的价值：自动化在无人值守时停下来等人，
桌面锁屏了，手机得能接住。

### A-1 「等我处理」卡片新增来源标识

现有审批卡片（`widgets/approval_card.dart`）结构不变，头部增加一行来源：

```
┌────────────────────────────────────┐
│ ⚙ 每日晨报 · 自动化 · 08:00 触发    │  ← 新增来源行（自动化才有）
│ ─────────────────────────────────  │
│ 🤖 Pi 想执行                        │
│    bash -lc "git push origin main" │
│ ─────────────────────────────────  │
│ 这次运行的输入：拉取昨日 PR 列表…    │  ← 可展开，取 Run 固化输入
│ ─────────────────────────────────  │
│ [ 拒绝 ]          [ 允许 ]          │
│ 查看运行详情 ›                      │
└────────────────────────────────────┘
```

- 来源行只在 Run 关联的会话上出现；用户手开的对话保持现状（不加噪音）。
- 「这次运行的输入」默认折叠成一行。无人值守场景下，用户没有上下文，
  必须能在**不离开卡片**的前提下知道「它为什么要 push」——这是 roadmap
  「不进入会话就能决策」那条约束在自动化场景的延伸。
- 「查看运行详情 ›」是逃生口，不是主路径，弱化成文字链。

### A-2 「正在跑」接纳自动化 Run

同一列表内，自动化 Run 行与会话行同构（复用 `widgets/session_row.dart`），
差异只在前缀图标（⚙ vs 项目色点）和副标题：

```
⚙ 每日晨报        运行中 · 已 2分14秒      [停止]
⚙ 库存巡检        等待输入 · 已 6分        →
```

排序：等我处理 > 等待输入 > 运行中，组内按开始时间倒序。
自动化 Run 与普通会话**混排不分区**——用户关心的是「什么在动」，
不是「它是被谁起的」。

### A-3 「刚完成」的 Run 终态

```
⚙ 每日晨报   ✓ 完成 · 12分钟前
   已汇总 7 条 PR，产出写入 report.md
⚙ 库存巡检   ✗ 失败 · 1小时前
   ACP runtime 已退出
```

摘要取 `AgentRun.output`（有界，桌面已限 16KB）首行；失败取 `error`。
点进去是 Run 详情（屏 C-2）。

## 3. 屏 B · 智能体 › 对话

### B-1 列表

按智能体定义分组，组头是智能体本体，组内是对话：

```
┌ 搜索 ─────────────────────────────┐

▍晨报助手                    Pi   ⋯
   ● 周报草稿          运行中 · 2分钟前
   ○ 竞品调研          空闲 · 昨天
   [ + 新对话 ]

▍代码审查员                  Pi   ⋯
   （还没有对话）
   [ + 新对话 ]
```

- 组头右侧 `⋯` → 底部弹层：**查看配置**（只读）、**新对话**。
- **没有「新建智能体」按钮。** 空状态文案直接说明去处：
  「智能体在桌面 Smelt 里创建。创建后会自动出现在这里。」
  ——与其放一个点了报错的按钮，不如明说边界。
- 一个定义可以同时有多段对话，这是桌面既有语义，列表结构原样保留。

### B-2 智能体配置（只读页）

从组头 `⋯ → 查看配置` 进入。**纯展示，无任何输入控件**：

```
   ⬤ 晨报助手
     引擎 Pi

  工作方式
    你是一个每日晨报助手，负责……          （全文，可滚动）

  插件            skill:web-search · extension:feishu
  绑定的上下文     ~/work/reports
                  https://example.com/spec

  ─────────────────────────────────────
  ⓘ 配置在桌面 Smelt 中修改
```

理由：这些字段决定智能体的行为，用户在手机上排查「它为什么这么干」时需要看到；
但改它属于创作动作，见 §0。

### B-3 新对话

点 `+ 新对话` → 直接创建并进入会话（复用现有 ACP 会话页）。
不弹参数表单：智能体的身份、指令、插件、上下文全部来自定义，
用户唯一要输入的是第一句话，那句话在会话页的输入框里写。

会话页顶部标题显示 `晨报助手 · 周报草稿`，让用户知道自己在跟谁说话。

## 4. 屏 C · 智能体 › 自动化

### C-1 目录

```
▍每日晨报                              [开关 ●]
   工作日 09:00 · 晨报助手
   上次 今天 09:00 ✓ 完成

▍库存巡检                              [开关 ○]
   外部触发 · 晨报助手
   上次 昨天 22:14 ✗ 失败                    ⚠

▍夜间备份                              [开关 ●]
   每 6 小时 · Shell 脚本
   运行中 · 已 3分钟
```

每行三层：名字 / 「何时 → 谁做」/ 最近一次结果。和桌面目录同一口径
（触发器只写「外部触发」，不带地址不带令牌）。

允许的写操作只有两个，都是幂等命令：

- **启停开关**：直接切，失败回滚并 toast。
- **立即运行一次**：长按行或详情页按钮。手动运行不推进日程游标（桌面既有语义），
  暂停状态下仍可用——这条要在按钮旁用一行小字说清，否则用户会以为暂停了按不动。

**没有新建、没有编辑、没有删除。** 空状态同 B-1：指向桌面。

### C-2 自动化详情 / Run 历史

进入后是单页滚动，不再分栏（桌面是左右分栏，手机拆成上下）：

```
  每日晨报                        [开关 ●]
  工作日 09:00 · 晨报助手 · 逐次审批
  下次运行 明天 09:00

  [ 立即运行一次 ]
   手动运行不影响下次定时

  ── 运行历史 ────────────────────
  今天 09:00   ✓ 完成 · 用时 3分12秒       ›
  昨天 09:00   ⚠ 等待审批 → 超时取消       ›
  周五 09:00   ✓ 完成 · 用时 2分48秒       ›
```

单条 Run 详情（下一层页）按**时间顺序**排，回答「它当时干了什么」：

```
  每日晨报 · 今天 09:00
  ✓ 完成 · 用时 3分12秒 · 定时触发

  这次的输入
    拉取昨日 PR 列表并汇总…              （固化值，非当前定义值）

  执行上下文
    智能体 晨报助手 (Pi) · 权限 逐次审批
    工作区 ~/.smelt/workspaces/automations/…

  时间线
    09:00:00  已排队
    09:00:01  已投递
    09:00:04  运行中
    09:01:30  等待审批 → 已允许（来自手机）
    09:03:12  完成

  结果
    已汇总 7 条 PR…                      （有界全文）

  [ 打开对话 ]                            ← 有 session_id 时才出现
```

「这次的输入」必须标明是**固化值**——自动化定义改过之后回看旧 Run，
显示当前定义会直接误导排查。桌面已经这么做，手机不能偷懒。

## 5. 状态与边界

| 场景 | 表现 |
|---|---|
| 未配对 / 未连接 | 智能体 tab 显示与其他 tab 一致的连接引导，不单独造一套 |
| 断线（有缓存） | 顶部 `CachedConnectionBar` 沿用；列表灰化 + 「数据为 X 分钟前」；**所有写操作禁用**，因为幂等命令也需要回帧确认 |
| daemon 未运行 | 「桌面 Smelt 未运行，智能体由桌面守护进程执行」 |
| 定义列表为空 | 指向桌面创建，不给假按钮 |
| 自动化列表为空 | 同上 |
| Run 历史为空 | 「还没有运行过」+ 立即运行一次 |
| 写操作失败 | 就地 toast + 行内保持原值；不静默 |
| 提交中 | 按钮转 loading，禁止连点（沿用 `_submitting` 那套） |

## 6. 视觉与 token

全部沿用 `theme/smelt_theme.dart`，**不新增颜色**：

| 概念 | token |
|---|---|
| 等待审批 / 等待输入 | `waitingApproval`（红）/ `needsAttention`（黄） |
| 运行中 | `running`（蓝） |
| 完成 | `done`（绿） |
| 失败 / 取消 | `danger`（红，与 waitingApproval 同色不同义） |
| 空闲 / 已暂停 | `idle`（灰） |

`AgentRunStatus` 十态 → 移动端收成五档展示，映射固定在一处：

| AgentRunStatus | 移动端展示 |
|---|---|
| `Starting` / `Queued` / `Dispatching` | 排队中（灰） |
| `Running` | 运行中（蓝） |
| `AwaitingApproval` | 等待审批（红，进指挥台） |
| `WaitingForUser` | 等待输入（黄，进指挥台） |
| `Completed` | 完成（绿） |
| `Failed` | 失败（红） |
| `Cancelled` / `Skipped` | 已取消 / 已跳过（灰） |

智能体头像复用桌面的 `render_agent_avatar` 取色规则（名字 + id 派生），
两端并排看必须是同一个色——否则用户会怀疑是两个智能体。

## 7. 这份设计需要网关补什么

移动端是展示层，但改造前**网关根本没投影自动化**
（`smelt-remote-gateway` 把 `DaemonStateEvent::Automations` 直接丢掉，`WorkspaceCatalog`
只有 `projects` + provider 级 `agents`）。所以这一版必然要动契约。补充的都是投影和幂等
命令，不下沉任何逻辑。

### 分片 1 已落地的部分

- **网关订阅自动化。** `DaemonStateEventClient::remote_gateway()` 加上
  `automations.changed` 与 `SubscriptionShape { automations: true }`；相应地
  `FirstPartyClientKind::RemoteGateway` 的能力集补了 `automation.read`。
  **任务读依然不给**——移动端没有任何任务界面，给了就是白扩授权面。
- **hidden 的 Run 会话补进移动端菜单。** Run 的 ACP 会话在 daemon 目录里是
  `hidden: true`（桌面侧栏不该被后台 Run 刷屏），`mobile_workspace_menu` 的
  `is_visible()` 过滤会把它挡掉。`append_automation_run_sessions` 按运行档案单独把它们
  补进移动端菜单，而不是去掉 daemon 的 `hidden`——那会连桌面侧栏一起改。
  补进来的行 `project_root = None`、`project_order = u32::MAX`。
- **会话摘要带 `automation` 子对象**：`automation_id / automation_name / run_id /
  run_status / run_source / prompt（固化输入）/ started_at`。指挥台的来源行只靠它，
  因此分片 2 不依赖自动化目录投影，可以独立上线。
- **手机不能删 Run 的会话。** Run 的生命周期归 daemon（claim / 投递 / 对账 / 回收），
  `deleteSession` 在网关层直接拒绝，不让它删一半再由 daemon 发现会话没了。

传的是机器码（`awaiting_approval` / `scheduled`），不是拼好的自然语言——文案落在
`mobile/lib/widgets/automation_source.dart`，i18n 才有地方接。

### 分片 4/5 还欠的契约

**读**
- 智能体定义投影：`id / name / agent_id / prompt / plugins / context_folders / context_links`
- 自动化投影：`id / name / enabled / trigger 摘要（脱敏）/ action 摘要 / 下次运行 / 最近 Run`
- Run 投影：`AgentRun` 有界字段 + 时间线
- 会话增补：`agent_definition_id`

**写（Control API 短命令，全部幂等，需 `command_id`）**
- `automation.set_enabled`
- `automation.run_once`
- `agent.conversation.create`（入参只有 `agent_definition_id`）
- 审批 / 回复复用现有 ACP 通道，不新增

定义与自动化的**增删改一律不开放给移动端**——不是暂缓，是边界。

## 8. 分片

按「每片独立可验证」排，和 `mobile-ux-redesign.md` 同一条原则：

| # | 分片 | 依赖 | 价值 |
|---|---|---|---|
| 1 | 网关投影 Run 会话 + 会话来源字段 | — | 后面全部的前提。✅ 已落地 |
| 2 | 指挥台接纳自动化 Run（A-1/A-2/A-3） | 1 | **本功能在手机上的全部不可替代价值**，做完就能单独上线。✅ 已落地 |
| 3 | 智能体 tab 骨架（两个分段） | 1 | 后两片的落点。✅ 已落地 |
| 4 | 自动化目录 + 启停 + 立即运行 | 3 | 轻量运维。✅ 已落地 |
| 6 | 智能体配置只读页 | 3 | 排查「它为什么这么干」。✅ 已落地 |
| 5 | Run 历史 + Run 详情 | 4 | 事后排查。目录行只带**最近一次** Run |
| 7 | 对话列表 + 新对话 | 3 | 手机上主动用智能体。`agent_definition_id` 投影已具备 |

分片 3/4/6 一起落地：只有目录没有智能体定义，行上就写不出「谁做」；
只有定义没有目录，这一栏又回答不了「它什么时候会自己动」——两者拆开发
都不构成一个能用的屏。原表里的分片 3 含「对话列表 + 新对话」，实现时拆了
出去（记为 7）：当时会话摘要上还没有 `agent_definition_id`，没法把对话归到
智能体名下。现在归属已经从桌面存档投下来了，这一片的前置依赖具备。

落地时补充的契约（都在 `crates/smelt-remote-gateway/src/lib.rs`）：

- `listAutomations` → `{type: "automations", automations: [...], agents: [...]}`。
  自动化和定义**一起**下发，目录行才能把 `agent_id` 解析成展示名。
- `setAutomationEnabled` / `runAutomationOnce`：都过 `write_enabled`，
  都把 daemon 回吐的最新存档整份重投影成同一个 `automations` 响应。不做
  本地乐观更新——daemon 是自动化的所有者，它可能拒绝（Run 重叠）或把命令
  解释成别的结果，回权威快照才不会出现「开关拨过去了、实际没生效」。
- 启停做成**幂等设值**而不是 toggle：桌面可能刚改过同一条，toggle 会翻反。
- webhook 的 `endpoint` / `secret` 不出现在投影里（有测试钉住）。手机上
  没有任何需要它们的操作，多带一份凭据只是白白扩大泄露面。
- 触发方式一律降解成机器码（`schedule` / `webhook` / `event` + 原样的
  `AgentSchedule`），文案在 `mobile/lib/widgets/automation_source.dart` 落地。
- 智能体定义列表**不过滤** `is_ready()`：定义不完整恰恰是用户要在列表里
  看见、回桌面补的东西。同理，绑定的定义被删掉时目录行照常显示，只是
  「谁做」写成 `Missing agent`。
- 会话摘要上的 `agent_definition_id` 来自**桌面工作区存档里的绑定**
  （`workspace.json` 的 `sessions[].acp.agent_definition_id`，兼容旧存档的
  `agent_runs[].definition_id`），由
  `smelt_core::agent_definition_store::load_session_agent_definition_ids` 读出。

  一度想从 cwd 反推（`~/.smelt/agents/<id>` 的目录名就是定义 id，零 IO，
  正好躲开热路径）——**是错的**：智能体对话的工作目录不固定，既可以是智能体
  自己的 space，也可以是任意一个普通项目仓库。反推只认得出前一半，开在项目
  里的对话会整批失去归属。

  存档读在 `spawn_blocking` 里，只在**菜单形态的事件**（Snapshot /
  WorkspaceMenu / RemoteSessions）到达时刷新，结果缓存进 hub；`summaries()`
  只查这份内存表——它是每条会话事件都跑一遍的热路径且持有 mutex，不能读 SQLite。
  桌面每次开关会话都会重发菜单，所以这就是「新开的对话该有归属了」最早的
  可靠信号。
- 只投 id 不投名字，同样是热路径不读存档的结果。名字由移动端拿
  `listAutomations` 的定义表配；配不上退回通用标签，不编名字。

**分片 2 单独上线是有意义的**：即使没有智能体 tab，用户也已经拿到了
「自动化半夜卡住、我在手机上放行」这个完整闭环。分片 3-6 是把桌面能力
搬过来看，优先级低于它。
