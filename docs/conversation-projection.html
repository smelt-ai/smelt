技术方案

装满窗口，或者取到第一条

Mac 和手机都从最近内容开始，只加载当前窗口需要的历史；画完按真实高度判断是否还要往前取。历史页与实时更新属于同一段对话，但走不同的交付规则：历史必须连续，未发送的实时状态可以合并。不要假设所有 agent 都把历史存成同一种 JSONL。

先看现状：数据实际上怎么走

下图上半部是逐段对照代码后的当前实现，下半部是尚未实现的目标设计。Smelt 把 ACP 内容事件归约成服务端内存投影，再把连续区间包装成 ConversationSnapshot；当前同步单位是 AcpEntry 下标，不是对话轮次。虚线框表示进程边界，因此可以看清每个队列究竟属于发送 daemon、Gateway 还是客户端。

8 MiB OutputMailbox 在发送方 daemon 的数据分发层，不在 Mac GUI 或手机 UI。Direct 模式的 acp_open / 每个 acp_watch attachment 由 main smeltd 持有；Hosted 模式还会先经过 session-host 内部 acp_open 的同款邮箱。红色问题也不止这一层：Hosted reader、Mac 客户端和 Gateway 当前分别还有无界或有界的下游队列，都会延后反压并保留过时帧。

Smelt 知道自己正处于历史恢复阶段：generic ACP 会在 session/load 前产生 HistoryReplayStarted，投影里有 replaying_history，恢复 Ready 也有专门类型；部分驱动还有显式结束标记。但 AgentChunk、ToolCall 等内容事件本身仍走同一种通道，不能仅凭“历史”身份丢弃，它们就是重建投影的数据。

ConversationSnapshot 的状态字段描述当前会话，但其中的 entries 只是带全局位置的连续区间。实时更新通常发送“本批最早变化的 entry 到当前末尾”；纯 phase 或审批状态更新可以不带 entries。当前实现也没有稳定的 turn 容器，迟到的工具终态可能修改旧 entry，因此现状图不能画成只追加轮次。

“虚拟列表”目前只代表行组件按需创建，不代表所有工作都懒做：Mac 对变化区间仍会建 Markdown 缓存、解码图片；手机 AcpSnapshot.fromJson 也会把本帧携带的 entries 全部解析成对象。

先分清数据，不强行统一格式

Agent 的历史源

恢复历史仍以 agent 自己的存储和协议为准。各 agent 的格式、分支和恢复语义不同；Smelt 不规定一份通用 JSONL，也不把完整 transcript 再复制进 SQLite。

ACP 投影

服务端把 ACP 事件归约为 AcpEntry 列表。entries_offset 是这份投影里的条目下标，不是 JSONL 行号或字节位置；现有历史页从这份投影切片。

客户端窗口

Mac 和手机各自只持有最近已加载的一段。窗口不够高时向前取页；短对话自然取到第一条，长对话不必在首屏传完。

会话列表和查询索引仍在 SQLite，不存 transcript 正文。分页能限制客户端传输和渲染量；当前服务端仍把完整 ACP 投影留在内存中，因此这不是服务端内存分页方案。

实时更新：按变更范围合并，不按最后一帧覆盖

每条实时连接只需要一份正在写的不可变帧，以及一份尚未开始写的变更摘要。摘要记录最早发生变化的 ACP 条目、最新投影版本和需要替换的状态字段；writer 取出摘要时，从当前投影重新生成一份连续快照。不能只把最后一条已序列化 JSON 留下来。

客户端已收到的投影覆盖 [900, 1000)。下一批变化包括 1000 的新内容和 998 的工具状态更新，就从 998 重新生成到当前末尾。若 998 在上一帧写完后又变化，下一帧仍须回到 998。会话清空、重放或分叉时换投影代数，并要求全量同步。

  • 待发期间多次变化取最早的变更下标，合并到最新状态；旧条目被修改时，左边界可以向前退。
  • 只有一帧正在写时不能改写它；后续变化进入单个待发摘要，不继续排快照队列。
  • revision 表示投影版本，不要求每个中间版本都传到客户端；合并帧必须说明覆盖范围，接收方不能把正常跳号当成丢失并永久等待。
  • 权限卡片等当前状态可以从最新投影恢复；必须逐次送达的动作回执、提醒和持久化副作用不能依赖可丢弃的实时帧。

“写完”只表示这一帧已完整写入当前有序连接，不表示 UI 已经画完。凡是中间还有可丢帧队列的下一跳，也必须按自己的消费进度合并或在发现缺口时 resync。

怎么知道满了

消息、工具、展开、合并，都要等画出来才知道有多高。不事先算几条能装满，也不先判断这是长对话还是短对话。

历史页按 ACP 投影里的绝对条目下标接在前面，接入时保持当前可见行的位置。打开后先取最近一批；布局完成后，若已加载内容的真实高度还不到视口加约一屏，就再取更早的一批，直到够高或到第一条。向上翻到边界时继续取页；失败留在边界并显示重试。页与实时更新并发时，用投影代数和 revision 判断是否仍可拼接，不匹配就重新对齐，不能静默丢页。

Mac 和手机使用同一套页接口，由各自实际视口决定何时继续取；手机可以采用更小的传输批次，Mac 可预取一页，但都不默认后台下载整段历史。约一屏余量是减少连续请求的缓冲，不是“装满”的固定条数。展开、合并、字号或窗口尺寸变化后重新量；只有尚有更早条目且内容不足时才补页。

现在的两个故障

历史恢复时输出积压

ACP 的历史恢复会产生事件；服务端虽会把当时已到达的一批事件合并，但分批到达的多批仍可能各自产生快照。每份快照进入连接自己的 FIFO 邮箱，慢 writer 来不及排空时，8MB 上限会关闭 attachment。问题是“重复状态快照排队”，不是应该把终端邮箱调大。约 200KB/帧若作为依据，应附实际采样条件和大小分布。

收到的历史，窗口却不连续

首屏的 100 是 ACP 条目数，不是 100 轮，也不保证覆盖一个视口。再加上虚拟列表未测量条目的高度估值、分页边界和滚动锚点处理，可能出现内容不足或旧页无法接上的情况。单加“加载更多”按钮不能修复高度估算和拼接问题。

终端的 8MB FIFO 是保护终端字节流的策略，不能直接套给 ACP 状态快照。手机 watcher 背压应只影响手机订阅；不能据此推断桌面 ACP 会话或 provider 应结束。Hosted host → daemon 的内部控制连接另有生命周期约束，不能因“邮箱满”而被关闭。

要改成什么样

怎么做
历史源继续使用 agent 自己的持久化和恢复协议；不假定统一 JSONL，也不把 provider 文件偏移当作 ACP 条目游标。
打开Mac、手机都先取最近一段并尽快显示。短对话自然到第一条；长对话不在首屏传完整本。
历史分页通过独立的有界历史请求，按 ACP 投影条目范围取页。客户端画完后按真实高度继续补到视口加约一屏，或到第一条。
往上翻旧页按绝对条目位置接在前面并保持滚动锚点。页失败可见、可重试；跨重放/分叉的旧游标显式失效并重新对齐。
实时更新历史页不进实时邮箱。每连接只保留正在写的帧和一份待发变更摘要；摘要按最早变更位置合并，从当前投影重新生成。
版本与重置更新携带投影代数和 revision。正常合并允许 revision 跳号；清空、重放、分叉切代数并发全量同步。
慢客户端积压帧被合并，不作为断线理由。持续写入停滞或真实 I/O 错误时可摘掉该 observer；provider 会话不能因普通 observer 背压而结束。
移动端按手机视口和传输预算分页；后台冻结期间不追补每个中间帧，恢复时重新订阅并同步当前状态。网关内部队列也必须支持合并或 resync。
单帧大小历史页同时限制条目数和编码字节数。单条超大图片/工具负载另设上限或资源引用；“队列只有一帧”不等于内存有界。
终端终端原样保留自己的 8MB 有界 FIFO；ACP 使用独立的状态快照邮箱，不改变终端字节流语义。

资源边界与非目标

  • 这次分页限制客户端的首屏传输、持有条目和渲染工作；服务端当前仍持有完整的 AcpSessionState.entries。若后续要限制 daemon 内存，必须另做 provider 历史分页或规范化存储方案，不能把客户端分页说成服务端分页。
  • 流式输出队列必须按流类型分策略：终端是不能丢字节的有界 FIFO，ACP 是允许合并状态的邮箱。不能修改一个共用队列后让终端输出也被覆盖。
  • Hosted host → daemon 与 daemon → GUI/mobile 是不同故障边界。内部宿主连接不能因为客户端快照队列达到字节阈值而被摘除；移动端 watcher 断开也不能终结桌面会话。
  • 当前快照在入队前已被构造和序列化。若只在字节邮箱里替换旧帧，虽能减少积压字节，却仍会重复做快照复制与 JSON 编码；合并应尽可能发生在序列化之前。
  • 持久化提交与可丢弃的实时广播分开。若暂时仍通过帧携带持久化意图，合并时必须累积标记，不能被最后一帧覆盖；审批回执等一次性事实也不能只存在于可合并快照中。

验收条件

  • 短历史一次补到第一条；长历史首屏达到真实高度目标后停止，向上翻可连续取完，滚动锚点不跳。
  • 分页与实时追加、旧工具状态更新并发时，没有缺条、重复条或静默丢页；过期代数明确触发重新对齐。
  • 对同一慢读端持续产生超过 8MB 的 ACP 更新，待发内存保持有界，收到的最终投影完整；其他 observer 与 provider 不受影响。
  • 覆盖 hosted host → daemon、桌面控制连接、手机 watcher 和 gateway 队列；验证慢连接、真实断开、前后台恢复及重连 resync。
  • 构造更新覆盖已写帧中的旧条目、清空/重放/分叉、runtime debug 变更、持久化标记，以及单个超大条目的测试。

实施顺序

  1. 先定协议不变量。明确 ACP 投影下标、投影代数、revision 覆盖范围、重置语义，以及哪些状态允许合并、哪些事件必须可靠送达；先写出旧条目更新和重置的失败测试。
  2. 再改实时出口。把 ACP 邮箱与终端 FIFO 分开；待发区保存变更摘要而非多份 JSON 字节，writer 在取帧时从 reducer 物化当前状态。覆盖直接连接和 hosted host → daemon 镜像连接。
  3. 实现客户端按高度补页。沿用 ACP 投影范围读取，先让 Mac 首屏与 prepend 锚点正确，再接入手机相同的接口；页面布局决定是否继续取，页失败显示并允许重试。
  4. 打通远端恢复。网关和 WebSocket 的积压队列采用同样的状态合并 / resync 语义；手机前后台切换后根据投影代数和 revision 重新订阅，而不是追补所有中间快照。
  5. 最后压测资源边界。测量典型与极端条目的序列化大小、并发 watcher 数和阻塞写时长，再定单帧字节上限、停滞超时和总内存预算；不通过增大 FIFO 上限来掩盖过载。

不改的事

  • 窗口仍不解析 Pi、Claude 等 provider 私有历史格式；agent 的历史所有权和恢复协议不变。
  • SQLite 继续保存 Smelt 自己需要查询的会话目录和索引，不新增一份重复 transcript。
  • 审批 responder 仍由持有 ACP 连接的进程处理；客户端看到当前待处理状态并发送动作。

100 是单次请求的批量上限，不是视口高度；8MB 是终端 FIFO 的保护线，不是 ACP 是否可打开的门槛。历史按真实布局逐页读取，实时流按语义变更范围合并；是否结束会话由真实生命周期和传输错误决定，而不是陈旧快照排了多少张。
