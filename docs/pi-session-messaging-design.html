smelt Pi↔Pi 会话消息技术方案

日期：2026-10-20（Asia/Taipei） · 受众：smelt 仓库维护者（Rust smeltd + Pi agent） · 状态：建议草案（非已实现 API）
项目： smelt-ai/smelt （macOS AI coding cockpit · smeltd + Pi / Bun） · 依据调研： 2026-10-20-pi-and-industry-session-messaging.md 等
Pi transcript 即收件箱 零新 SQL 账本 仅 Pi → Pi 建议 · 非现网 API

1.背景与目标 / 非目标

1.1 为何要做

smelt 是 macOS 上的 AI coding cockpit：侧栏可见的 durable Pi 会话由 smeltd（Rust）托管， 会话内 agent 为 Pi（Bun）。产品需要对等 peer messaging：一个正在跑的 Pi 对话 能在 mid-run 向另一个 durable Pi session 发送提醒 / 任务 / 完成通知， 并让对方在既有 turn 路径上被唤醒、消费。

这与现有 subagent（后台子进程、只向父报告、不进侧栏）是不同层： subagent 保持不变；peer send 面向侧栏 durable Pi 会话之间的协作。

1.2 目标

  • Pi↔Pi：发现其他 durable Pi 会话，并向其投递 peer 消息。
  • 投递权威落在目标 Pi 的原生 transcript：消息进入 transcript 并被 turn 消费即视为送达。
  • smeltd 仍做校验与入队门卫（身份、目标、跳数、权限天花板、inbox 深度），但不引入协作账本表。
  • P0 只暴露 session_list + session_send；spawn 可选、靠既有建会话路径。

1.3 非目标

  • 不做跨引擎 ACP 总线（Claude / Codex / 其他 runtime 互通）。
  • 不复活已删除的 schema-23 MCP peer 总线（smelt-agent-mcp / peer_message_*）。
  • 不把 Task 级 A2A / 兄弟子 agent 互聊作为产品模型（与 PI Desktop ADR 0165 同向：子 agent 仍是报告型）。
  • 不新增 session_messages / session_links 等 SQL 协作账本，也不为该功能在 smelt.sqlite3 上加新 schema 字段。
产品偏好（用户强制）
协作状态放进 Pi transcript framing，而不是 host SQL ledger。 接受相对 PI Desktop 更薄的持久化与幂等保证，换取零新表、与 Pi 原生会话模型对齐。

2.设计原则

  1. Pi transcript 即收件箱。 对等消息以与 user/assistant 同结构族的一条（或一组）transcript 条目呈现， 带可辨认的 provenance framing；UI 与模型都能从 transcript 本身读到「谁发来的」。
  2. 零新 SQL 协作账本。 不新增 session_messages、session_links，不为 peer 功能扩展 smelt.sqlite3 schema。source_session_id、kind、 remaining_hops、permission_ceiling、idempotency_key、 reply_to 等元数据住在transcript 消息信封里。
  3. smeltd 仍是门卫。 发现、校验、入队走 daemon；source 从 tool-host 上下文注入（禁止客户端伪造）； 目标必须是已有 durable Pi session；source ≠ target；可选跳数与权限天花板在进程内检查。
  4. 复用既有 session / turn 路径。 投递 = 把 framed 输入推进目标 session 的既有 turn / input queue，再由 Pi 写入自身 transcript； ack 对齐同 session 既有的至少一次模式（如 claim_model / acknowledge_model 风格）。
  5. 与 subagent 分层。 subagent：后台子、报告型、不进侧栏。Peer send：侧栏 durable Pi 之间，可 mid-run 唤醒。

4.与 PI / 业内对照

4.1 PI Desktop：host SQL collaboration ledger

PI Desktop（ADR 0239 / 0240）对 durable Agent Session 采用host 拥有的协作账本：

  • session_collaboration_messages：按 message ID / idempotency key 幂等；kind ∈ {task, message, completion}
  • session_collaboration_links：仅记录 spawn 创建的 parent–worker 关系
  • 投递经 turn queue（忙则排队）；inbox 深度、hops、permission_ceiling 均有 SQL / host 侧权威
  • 崩溃恢复与 exactly-once completion 回调由 ledger 支撑

这是「厚 host」路线：协作事实先落 SQL，再投影进模型 framing。

4.2 smelt 选择：更薄的 Pi-native 路径

产品明确拒绝「为协作再开一套 SQL 表」——认为不够优雅，也与「Pi 会话本身就是真相」的心智不一致。 因此 smelt 对照 PI Desktop 后刻意不照搬 ledger：

维度PI Desktopsmelt（本稿）
收件箱权威 host SQL ledger 行 目标 Pi transcript 中的 peer-framed 条目
关系图 session_collaboration_links 约定（标题 / 初始 framing / 软 parent hint），无表
幂等 UNIQUE(plugin, source, idempotency_key) 信封内 key + 进程内去重；无跨重启全局唯一约束
崩溃恢复 queued 行可重放 依赖既有 turn queue 持久化；未入 transcript 者可能丢失
schema 成本 新表 + 迁移 零新协作表 / 零新 runtime DB 字段
刻意取舍
smelt 用更弱的「未入 transcript 前」持久化，换取与 Pi 原生 transcript 对齐、零 SQL 账本。 护栏（深度、hops、ceiling）仍在 smeltd 进程内执行，只是不落协作表。

4.3 业内简述

  • 报告型子 agent（模式 a）：Claude Code Task、PI Task——子结束交结果，无兄弟 peer；smelt subagent 属此类，保持不变。
  • 带账本的对等投递（模式 b）：PI Desktop session collaboration——smelt 产品语义同属 (b)，实现落点改为 transcript。
  • 黑板 / 共享状态（模式 c）：非本次范围。

5.总体方案

三个角色：发起方 Pi（A）、门卫 smeltd、目标 Pi（B）。 发现复用既有 session 列表；发送经 daemon 校验后进入 B 的既有 turn/input 路径； B 将 framed peer 消息写入自身 transcript，再按既有 claim/ack 风格消费。

6.「数据」放哪：transcript framing

协作元数据住在目标会话 transcript 的消息信封中。 结构族与 user/assistant turn 相同（便于渲染与上下文窗口纳入），但带可区分 provenance， 避免模型/用户误以为是人类直接输入。

明确不做
  • 不新增表 session_messages
  • 不新增表 session_links
  • 不为该功能给 smelt.sqlite3 加列 / 新 migration

6.2 字段说明（建议）

字段位置用途
channel: "peer_session" transcript 条目 UI / 模型区分「人类输入」与「peer 投递」
source_session_id 信封 来源；由 smeltd 从 tool-host 上下文写入，不可客户端伪造
kind 信封 message | task | completion（语义标签，非 SQL enum 表）
remaining_hops 信封 自治链预算；每跳递减；耗尽则门卫拒绝再转发
permission_ceiling 信封快照 目标在本 turn 跑工具时不得抬高至此快照之上
idempotency_key 信封 发送方提供；smeltd 进程内对近期 key 去重（见 §12）
reply_to 信封 可选；指向先前 peer 条目的 id / key，表达线程，无 link 表

6.3 关系如何表达（无 session_links）

可选 session_spawn（P1）创建的是普通 durable Pi session，关系仅靠约定：

  • 标题前缀 / 命名约定（如 ← sess_a · flaky e2e）
  • 首条 transcript 的 framing 写明「由 sess_a 请求创建」
  • 可选 soft parent hint 字段放在那条初始 framing里，不进 SQL

侧栏身份、列表、删除生命周期继续走既有 session 路径——spawn 不发明第二种会话类型。

7.API / 工具（建议）

工具挂在 Pi tool-host 上，由 smeltd 实现门卫与入队。下列形状为建议，非现网契约。

7.1 P0：session_list

列出可投递的 durable Pi 会话（复用 smeltd 已掌握的 session / 侧栏身份）。无新 DB。

建议
session_list({
  "query"?: string,          // 可选：标题模糊匹配
  "include_self"?: boolean   // 默认 false
}) → {
  "sessions": [
    {
      "session_id": "sess_b_02",
      "title": "Tests · login e2e",
      "engine": "pi",
      "busy": true,
      "updated_at": "2026-10-20T01:10:00+08:00"
    }
  ]
}
  • 仅返回 Pi engine 的 durable session（排除非 Pi / 已删除）。
  • 不返回「假会话」或仅存在于内存的临时 subagent id。

7.2 P0：session_send

建议
session_send({
  "target_session_id": "sess_b_02",
  "kind": "message",           // message | task | completion
  "body": "请重跑 flaky e2e…",
  "idempotency_key": "a01:remind-b:v1",
  "reply_to"?: string,
  "remaining_hops"?: number    // 通常由门卫从入站信封继承并递减；首跳可给默认
}) → {
  "status": "enqueued",        // enqueued | duplicate | rejected
  "target_session_id": "sess_b_02",
  "reason"?: string            // rejected 时：AGENT_BUSY | LIMIT_EXCEEDED | …
}

门卫规则（进程内）

  • Pi→Pi only：双方均为 durable Pi session。
  • source：仅从当前 tool 调用的 host context 取得，忽略客户端自报 source。
  • source ≠ target。
  • inbox depth：统计目标 transcript 中近期未 ack 的 peer-framed 条目，和/或内存 / 既有 turn queue 深度；超限则 AGENT_BUSY（建议默认阈值对齐业界常见值，如 8，可配置）。
  • hops：信封内递减；≤0 拒绝。
  • permission_ceiling：快照写入信封；目标本 turn 工具权限取 min(自身, ceiling)。
  • idempotency_key：同 source + key 在进程内近期窗口视为 duplicate（见 §12 弱点）。

7.3 P1（可选）：session_spawn

经既有 create-session 路径新建 durable Pi session，再可选地向其 session_send 一条 kind=task 的初始 framing。 不写 session_links。

建议
session_spawn({
  "title": "← sess_a · flaky e2e",
  "initial_task": "重跑 login e2e 并汇总失败用例",
  "permission_ceiling"?: object
}) → {
  "session_id": "sess_c_03",
  "enqueued_initial": true
}

P0 不要求 spawn；发现 + 向已有会话 send 即可闭环「互提醒」。

8.1 Ack / 送达语义

  • enqueued：已通过门卫并进入目标既有 turn/input 路径（对发送方的 RPC 成功）。
  • delivered（权威）：peer-framed 条目已 append 进目标 transcript。
  • consumed：目标 turn 按既有 claim_model / acknowledge_model 风格至少一次认领并处理。

发送方默认只保证观察到 enqueued；若需要端到端确认，由目标主动 session_send(..., kind=completion) 回源（信封可带 reply_to）， 不依赖 SQL settle 行。

9.护栏与权限

9.1 护栏（无 ledger 表时如何实现）

护栏实现落点说明
Inbox 深度 目标 transcript 近期未 ack peer 条数，和/或内存 / 既有 turn queue 深度 满则拒绝；不靠 status='queued' SQL 计数
Hops 信封 remaining_hops 递减 门卫读入站信封、写出站信封；耗尽拒绝
Permission ceiling 信封快照 + 目标 turn 工具执行时取 min 防止「低权限会话借高权限会话提权」
Source 防伪 tool-host 上下文 客户端不可自报 source_session_id
Engine 边界 门卫 仅 Pi→Pi；拒绝跨引擎
幂等窗口 smeltd 进程内近期 key 集合 非全局 UNIQUE；重启后窗口清空（见 §12）

9.2 权限模型（建议）

  • 发送：调用方须是当前活跃 Pi turn 的工具调用（与 PI Desktop「plugin context」同思路）。
  • 接收：目标 session 无需事先「加好友」；发现即潜在可投（产品若要收紧，可用标题约定 / 用户设置，仍不建 link 表）。
  • 工具执行：本 turn 若由 peer 消息触发，有效权限 ≤ 信封 ceiling ∩ session 自身策略。
  • 人类始终可在 UI 中停止 / 删除目标会话；peer 消息不提升为「系统级」权限。

10.UI

  • 侧栏：继续渲染既有 durable session 列表；无需为 peer 功能新表或新列。未读感若需要，可从该会话 transcript 尾部是否存在未消费 channel=peer_session 推导（客户端投影），而非 SQL unread 计数。
  • 对话区：peer 消息与人类 user 气泡区分样式——例如左侧色条、角标「来自 · {title/session_id}」、kind 标签（message / task / completion）。文案需标明「另一 agent 发送，非用户直接输入」（对齐 PI Desktop framing 精神）。
  • 发送方 UI：P0 可不做独立面板；agent 通过工具完成 list/send。可选后续：在会话菜单提供「提醒另一会话…」快捷入口，仍走同一 tool/RPC。
  • subagent：不出现在侧栏 peer 选择器中。

12.风险与取舍

相对 PI Desktop SQL ledger 的诚实弱点
  • 幂等非全局：无 UNIQUE(source, idempotency_key) 表约束；daemon 重启后进程内去重窗口丢失，可能导致重复 enqueue（transcript 可能出现两条相同 peer 条目）。
  • 崩溃窗口：已通过门卫、尚未 append 进 transcript、且未坐落在「既有 turn queue 持久化」上的条目，重启后可能丢失。
  • inbox 深度近似：扫 transcript 尾部 / 内存队列，不如 SQL status='queued' 计数精确，极端并发下可能短暂漂移。
  • 无 exactly-once completion 账本：回执靠目标再 send；重复 completion 需接收方自辨（信封 key / reply_to）。

12.1 用 transcript + 既有队列尽量补

  • 优先落 transcript：一旦 append，消息即成为会话历史的一部分，随 Pi 既有持久化存活——这是本设计的主恢复面。
  • 复用既有 turn queue 持久化（若 smeltd / Pi 已有）：enqueue 后、跑 turn 前的条目应尽量走同一持久化，而不是另造协作表。
  • 消费侧去重：Pi 在纳入上下文前，可对近期 idempotency_key 相同的 peer 条目折叠显示 / 跳过重复工具副作用（建议行为，P2 硬化）。
  • 发送侧重试：工具层对 enqueued / duplicate 给出明确结果；发送方用同一 key 重试是安全的仅在进程内窗口仍有效时——文档与 SDK 注释需写清。

12.2 为何仍选这条路

产品认为「再开一套协作 SQL」与 Pi-native 心智冲突，且维护成本（migration、投影、与 transcript 双写一致性）高于其带来的恢复收益。 smelt 选择薄 host 门卫 + 厚 transcript 真相；接受上述弱点，并在 §13 保留「若生产事故证明不够，再评估最小持久化」的退路——但那不是 P0 默认。

13.开放问题

  1. Peer 条目的精确 transcript schema。 是扩展现有 user message 的 metadata 字段，还是引入并列 role/channel？ 需与 Pi（Bun）transcript 写入路径对齐后定稿。
  2. 既有 turn / input queue 的持久化强度。 决定「门卫通过后、入 transcript 前」的丢失面有多大；需对照 smeltd 现状代码确认，而非假设。
  3. Inbox 深度默认阈值与统计窗口。 扫 transcript 多深？是否计入已 claim 未 ack？建议先对齐 8，用指标验证。
  4. Hops 默认初始值。 PI Desktop 约从 9 递减；smelt 是否同值，或按产品更保守。
  5. 人类是否可在 UI 手动「注入 peer 样式」消息。 建议否——peer channel 仅 daemon 门卫可写，避免伪造 provenance。
  6. P1 spawn 是否限制「worker 不可再 spawn」。 PI Desktop 有此限制；无 link 表时只能靠信封 hint / 标题约定软限制，或门卫读目标 transcript 初始 framing——需产品拍板。
  7. 若 P0 线上重复投递不可接受，最小补丁是什么。 例如：仅一张极瘦的 idempotency_keys（非完整 ledger）——当前产品偏好仍是尽量不走 SQL；列为应急选项而非计划。
