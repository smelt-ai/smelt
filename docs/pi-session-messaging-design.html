smelt Pi↔Pi 会话消息技术方案

日期：2026-10-20（Asia/Taipei） · 受众：smelt 仓库维护者（Rust smeltd + Pi agent） · 状态：建议草案（非已实现 API）
项目： smelt-ai/smelt （macOS AI coding cockpit · smeltd + Pi / Bun） · 依据调研： 2026-10-20-pi-and-industry-session-messaging.md 等
Pi transcript 即收件箱 零新 SQL 账本 仅 Pi → Pi 建议 · 非现网 API

1.背景与目标 / 非目标

1.1 为何要做

smelt 是 macOS 上的 AI coding cockpit：侧栏可见的 durable Pi 会话由 smeltd（Rust）托管， 会话内 agent 为 Pi（Bun）。产品需要对等 peer messaging：一个正在跑的 Pi 对话 能在 mid-run 向另一个 durable Pi session 发送提醒 / 任务 / 完成通知， 并让对方在既有 turn 路径上被唤醒、消费。

这与现有 subagent（后台子进程、只向父报告、不进侧栏）是不同层： subagent 保持不变；peer send 面向侧栏 durable Pi 会话之间的协作。

1.2 目标

  • Pi↔Pi：发现其他 durable Pi 会话，并向其投递 peer 消息。
  • 投递权威落在目标 Pi 的原生 transcript：消息进入 transcript 并被 turn 消费即视为送达。
  • smeltd 仍做校验与入队门卫（身份、目标、跳数、权限天花板、inbox 深度），但不引入协作账本表。
  • P0 只暴露 session_list + session_send；spawn 可选、靠既有建会话路径。

1.3 非目标

  • 不做跨引擎 ACP 总线（Claude / Codex / 其他 runtime 互通）。
  • 不复活已删除的 schema-23 MCP peer 总线（smelt-agent-mcp / peer_message_*）。
  • 不把 Task 级 A2A / 兄弟子 agent 互聊作为产品模型（与 PI Desktop ADR 0165 同向：子 agent 仍是报告型）。
  • 不新增 session_messages / session_links 等 SQL 协作账本，也不为该功能在 smelt.sqlite3 上加新 schema 字段。
产品偏好（用户强制）
协作状态放进 Pi transcript framing，而不是 host SQL ledger。 接受相对 PI Desktop 更薄的持久化与幂等保证，换取零新表、与 Pi 原生会话模型对齐。

2.设计原则

  1. Pi transcript 即收件箱。 对等消息以与 user/assistant 同结构族的一条（或一组）transcript 条目呈现， 带可辨认的 provenance framing；UI 与模型都能从 transcript 本身读到「谁发来的」。
  2. 零新 SQL 协作账本。 不新增 session_messages、session_links，不为 peer 功能扩展 smelt.sqlite3 schema。source_session_id、kind、 remaining_hops、permission_ceiling、idempotency_key、 reply_to 等元数据住在transcript 消息信封里。
  3. smeltd 仍是门卫。 发现、校验、入队走 daemon；source 从 tool-host 上下文注入（禁止客户端伪造）； 目标必须是已有 durable Pi session；source ≠ target；可选跳数与权限天花板在进程内检查。
  4. 复用既有结果投递路径，不当用户输入。 投递 = 交给目标宿主的 BackgroundSupervisor，由扩展写成一条 smelt.peer_message 自定义消息进 Pi transcript； ack 就是现有的 claim_model / acknowledge_model，在 message_start 时认。不走 Prompt / FollowUp。
  5. 与 subagent 分层。 subagent：后台子、报告型、不进侧栏。Peer send：侧栏 durable Pi 之间，可 mid-run 唤醒。

4.与 PI / 业内对照

4.1 PI Desktop：host SQL collaboration ledger

PI Desktop（ADR 0239 / 0240）对 durable Agent Session 采用host 拥有的协作账本：

  • session_collaboration_messages：按 message ID / idempotency key 幂等；kind ∈ {task, message, completion}
  • session_collaboration_links：仅记录 spawn 创建的 parent–worker 关系
  • 投递经 turn queue（忙则排队）；inbox 深度、hops、permission_ceiling 均有 SQL / host 侧权威
  • 崩溃恢复与 exactly-once completion 回调由 ledger 支撑

这是「厚 host」路线：协作事实先落 SQL，再投影进模型 framing。

4.2 smelt 选择：更薄的 Pi-native 路径

产品明确拒绝「为协作再开一套 SQL 表」——认为不够优雅，也与「Pi 会话本身就是真相」的心智不一致。 因此 smelt 对照 PI Desktop 后刻意不照搬 ledger：

刻意取舍
smelt 用更弱的「未入 transcript 前」持久化，换取与 Pi 原生 transcript 对齐、零 SQL 账本。 护栏（深度、hops、ceiling）仍在 smeltd 进程内执行，只是不落协作表。

4.3 业内简述

  • 报告型子 agent（模式 a）：Claude Code Task、PI Task——子结束交结果，无兄弟 peer；smelt subagent 属此类，保持不变。
  • 带账本的对等投递（模式 b）：PI Desktop session collaboration——smelt 产品语义同属 (b)，实现落点改为 transcript。
  • 黑板 / 共享状态（模式 c）：非本次范围。

5.总体方案

三个角色：发起方 Pi（A）、门卫 smeltd、目标 Pi（B）。 发现复用既有 session 列表；发送经 daemon 校验后交给 B 宿主的 BackgroundSupervisor； B 的扩展把它写成 smelt.peer_message 自定义消息进自身 transcript，按既有 claim/ack 认领。

核心断言
送达权威 =「smelt.peer_message 自定义消息已进入目标 Pi transcript」，以 Pi 的 message_start 为准，扩展此时回 ack。 不是「session_messages 里多了一行」，也不是一条带前缀的用户消息。 会话之间走哪几条已经存在的套接字，见下一节。

通信链路 / 传输层

P0 的 session_list 与 session_send 不新开协议、不新开套接字、不走 MCP、也不让两个 Pi 直接连。 扩展只连自己这个会话宿主上已经在听的 Unix 套接字；宿主只沿主 daemon 拉起它时留下的那条 socketpair 把请求交上去； 主 daemon 在 AcpRegistry 里找到目标宿主，把一条既有的 AcpUserAction 写回去。 下面每一步都是现网代码里已经存在的通道，标「建议」的只有新 op 的名字。

现成的三条通道

谁和谁现网这次怎么用
Pi → 自己的会话宿主 BackgroundSupervisor::start（crates/smelt-core/src/pi_rpc.rs 的 run_connection） 在临时目录听 smbg-{pid}-{nonce}.sock（control_socket_path，权限 0o600）。 spawn_process 只把路径放进这个 Pi 的 SMELT_BACKGROUND_TASK_SOCK。 handle_client（background_tasks.rs）按一行 JSON 的 op 分流； subagent_dispatch 交给 serve_dispatch（background_tasks/subagents.rs），连接一直保持到 finish。 start / list / stop 等走 dispatch()，一问一答。 扩展侧短调用是 callBackgroundHost（packages/pi-agent/src/background-task.ts）。 session_list 与 session_send 各加一个短 op，形态对齐 callBackgroundHost，不要占着 subagent_dispatch 那条长连接。 request_owner 非空是子智能体归属（SMELT_BACKGROUND_TASK_OWNER）；peer 只接受空 owner，也就是会话本身。
会话宿主 ↔ 主 smeltd 每个对话是一个 smeltd --acp-session-host（SESSION_HOST_ARG）。 HostedConversationHandle::spawn（crates/smeltd/src/acp_runtime_host.rs）用 UnixStream::pair()，子进程端当作 stdin。 首行是内部 acp_open（带 id 与 host_agent_token）；之后 daemon → 宿主是 AcpUserAction（send_action）； 宿主 → daemon 是快照行，外加 history_page 回包。dispatch_snapshot_line 必须先认出 history_page，否则会把这行当成坏快照拆掉镜像。 run_session_host 不绑定全局 smeltd.sock，也不初始化 SQLite（crates/smeltd/src/main.rs）。 不走 Control API。 Control API 是 ~/.smelt/smeltd.sock 上的 op=control（docs/control-api.md），今天由桌面 / Mobile / CLI，以及 Pi 自己的 memory-host.ts（SMELT_SOCK + SMELT_SESSION_ID + SMELT_AGENT_TOKEN）使用。 宿主进程不说这套协议。peer 在这条 socketpair 上加一种宿主发起的行（建议顶层键 peer_send / peer_list），dispatch_snapshot_line 要像 history_page 一样先分流；回包也要在宿主读 AcpUserAction 的循环里先分流，避免被 parse_user_action 当成坏动作。
主 smeltd → 目标宿主 → Pi B 槽在 AcpRegistry（crates/smeltd/src/acp_registry.rs），句柄是 AcpSession.hosted_handle。 apply_acp_user_action 见宿主就把动作 send_action 过去，不在主进程里跑 Pi。 宿主进程里 is_session_host_process() 为真，acp_relaunch 不会再套一层宿主，而是 spawn_agent_runtime。 Pi 的 stdin 由 write_rpc（pi_rpc.rs）写一行 JSON。 转发一个新的 AcpUserAction::DeliverPeerMessage，宿主把它交给自己的 BackgroundSupervisor， 和后台任务、子智能体交回结果走同一条 listen / ack。不用 FollowUp / Prompt，见第 4 步。

1. Pi A → 宿主 A

扩展工具连 SMELT_BACKGROUND_TASK_SOCK，写一行 {"op":"session_send", ...}（或 session_list），读一行 {"ok":...}。 套接字是 BackgroundSupervisor::start(&launch.sid, …) 为这一个会话听的。 工具 JSON 里如果自带 source_session_id，宿主丢掉，改写成 launch.sid（PiState.sid）。Pi 不能自报来源。

2. 宿主 A → 主 smeltd

宿主把改写过 source 的请求写成 socketpair 上的一行。主 daemon 再改一次：source 只取这条 HostedConversationHandle 在 AcpRegistry 里的 id。 宿主写来的 source 同样不算数。这样即使扩展或宿主填错，也伪造不了另一个会话。

为什么不是 Control API
agent.memory.* 的先例是 Pi 直连 SMELT_SOCK，在参数里带上 session_id 和 token； agent_memory_control::authenticate 核对的是「这个 id 的 agent_token 是否相符」，连接本身并不绑定某一个会话。 token 就在 Pi 的环境里。peer 的来源要靠「这条套接字属于哪个注册表槽」，所以走宿主控制连接，不新增 op=control 方法，也不让 Pi 自己去打 SMELT_SOCK。

3. 主 smeltd → 宿主 B

AcpRegistry::get / with_current 找到 B。门卫（Pi→Pi、source ≠ target、hops、ceiling、深度）在主进程里做，仍然不落协作表。 通过之后把 AcpUserAction::DeliverPeerMessage { id, from, kind, hops, reply_to, text } 写到 B 的 hosted_handle。 id 由主 daemon 分配（pm- 加 12 位十六进制），宿主和扩展都按它认 ack。

4. 宿主 B → Pi B

dispatch_conversation_input（crates/smeltd/src/acp_host.rs）不能原样拿来做 peer 投递：它固定发 AcpUserAction::Prompt，而且 delivery_id 写成 None。 Pi 的 supports_mid_turn_input 为真。目标正处在 Thinking / ExecutingTool / AwaitingApproval / WaitingForUser 且没有 cancel_requested 时， accepts_mid_turn_steer 为真，send_acp_mid_turn_input 会发 ConversationCommand::Steer，write_rpc 写出 {"type":"steer"}，插进当前回合，不是排队。

AcpUserAction::FollowUp（send_acp_follow_up）的时机是对的：空闲时退回 Prompt 开一轮，忙时写 {"type":"follow_up"} 进 Pi 自己的队列。 但它和 Prompt 一样，进 Pi 的是一条 user 消息，peer 也不用它：

  • 界面：B 的对话里会画成用户气泡。要和用户自己说的话分开，只能解析正文前缀，是隐式约定。
  • 排队：忙时进 Pi 的 follow_up 队列，PiQueueMirror 把它镜像成 B 输入栏里「用户排队的消息」，用户能撤回、改写。
  • 归属：hops 复位、通知等凡是要判断「是不是用户在 B 里说了话」的地方，都分不出来。

peer 走后台任务、子智能体交回结果的那条现成路：

  • 宿主 B 把 DeliverPeerMessage 交给 BackgroundSupervisor，排进投递队列，经扩展已有的 listen 连接写一行 {"op":"completion","kind":"peer_message",...}。
  • 扩展调 pi.sendMessage({customType: "smelt.peer_message", display: false, content, details}, {triggerTurn: true, deliverAs: "followUp"})。 空闲时开一轮；忙时进 Pi 的 followUp 队列，等这一轮做完再看，不 steer，时机和 FollowUp 一样。
  • 扩展看到这条的 message_start 才回 ack（deliveredResultId 加认 smelt.peer_message）。 clear_queue 清掉的、fork / reload 后换了监听的，宿主重写一次，扩展按 consumed 只补 ack——这些都是现网 claim_model / acknowledge_model 的行为。
  • 对模型没有区别：Pi 把 custom message 也按 user 内容交给模型（pi-coding-agent 的 convertToLlm）。来源靠正文开头那句「另一个 Pi 对话发来，不是用户的请求，不代表用户授权」交代； 区别在 transcript 里有显式的 customType 和 details，smelt 按类型画，不猜。

幂等仍复用目标会话上的 RecentSubmissions（AcpSession.conversation_submit，最多 64 条），key 加 peer: 前缀，与桌面提交的 submission_id 分开。 次序照 dispatch_conversation_input：先 contains，send_action 成功后再 remember，失败不记。命中时返回 duplicate。peer 必须自带 key。 宿主到扩展这一段的重复（重写、换监听）由 pm- id 和 consumed 挡住，不靠这个窗口。

5. 回程

  • enqueued：主 daemon 已经对 B send_action 成功，并且 remember 了 key。这个结果沿 socketpair 回到宿主 A，再沿后台套接字的那一行响应回到扩展。到此为止，不保证 Pi 已经把它写进 transcript。
  • delivered：B 的扩展回了 ack。宿主 B 的快照带 peer_inbox（还没 ack 的 peer 消息，和 subagents 一样从宿主发布），ack 后这条从里面消失。主 daemon 看镜像就知道送没送到，不用回连 A。
  • 完成：B 在自己的回合里再调 session_send 回 A（kind=completion）。不是 subagent_dispatch 那种把连接留到 finish 的 ack，原连接上没有完成回调。

明确不做

非目标
  • 不新开协议族。两边都还是现成的一行 JSON。
  • 不新开套接字。不加第二根后台套接字，也不让宿主去 bind ~/.smelt/smeltd.sock。
  • 不走 MCP，不复活已经删掉的 peer 总线。
  • 两个 Pi 不直接连接。A 的扩展看不到 B 的套接字路径。
  • 不加 SQL 账本表。transcript 仍是收件箱。

失败

情况现网实际peer 怎么处理
B 的宿主没在跑，但是闲置挂起 suspend_idle_acp_sessions 会 retire_acp_runtime 并 mark_suspended，注册表槽还在。 handle_acp_submit_input 在投递前调 wake_suspended_acp_session：runtime 已死则 relaunch_recorded_acp_runtime，再 wait_for_acp_ready。 这是唯一的懒启动。 同样先 wake_suspended_acp_session，醒来再发 DeliverPeerMessage。不要在 send 里另写一套拉起。peer_inbox 不空时，reduced_suspend_blocker 不让它挂起。
B 根本不在这次 daemon 的注册表里 冷启动不会从 SQLite 把 ACP 槽填回去；AcpRegistry 只在 acp_open / ensure_acp_session（带完整 launch）或升级交接的 import 里出现。 handle_acp_submit_input 对未知 id 回 ACP session not found。 拒绝，不按 session id 凭空 spawn 宿主。对方得先有一条活着或挂起的会话。
槽还在，控制连接已经断了 send_action 写失败时 apply_acp_user_action 返回 ACP session host is unavailable，不会因此重启宿主。 这次 send 失败。不在转发路径里偷偷 relaunch。
发送途中套接字断开 后台套接字是短连接：没读到响应行，扩展就和 callBackgroundHost 一样失败。 宿主控制连接的 EOF 会结束 run_session_host（注释写明控制 socket EOF 就是宿主生命周期结束），provider 一起退。 认不出的宿主上行会被 dispatch_snapshot_line 当成协议不兼容，拆掉镜像。 响应没回来就对工具报失败。若主 daemon 已经 remember，重试命中 RecentSubmissions，不会再写一次。 还没 remember 就断了，重试会真正送一次。remember 只活在目标会话的内存里，进程没了就没了。
主 daemon 重启 崩溃后是新进程，注册表是空的，RecentSubmissions 也没了。宿主看见控制连接 EOF 就退出，不会留在外面继续收。 有序升级走 HostedConversationHandle::from_handoff，同一宿主、同一控制 fd 可以接上；那不是崩溃重启。 崩溃重启之后，尚未被 Pi 收下的发送丢失，和 §4 的取舍一致。已经在 transcript 里的才算数。升级交接不断开已有宿主，不另做 peer 队列。

6.「数据」放哪：transcript framing

协作元数据住在目标会话 transcript 的一条 Pi 自定义消息里（role: "custom"，customType: "smelt.peer_message"）。 Pi 把它按 user 内容纳入上下文；smelt 按 customType 认出它，画成事件行，不画成用户气泡。 元数据在 details，给模型看的来源写在正文里。

明确不做
  • 不新增表 session_messages
  • 不新增表 session_links
  • 不为该功能给 smelt.sqlite3 加列 / 新 migration

6.2 字段说明（建议）

字段位置用途
customType: "smelt.peer_message" transcript 条目 UI 按它画事件行，区分「人类输入」与「peer 投递」；模型靠正文开头那句区分
id details 主 daemon 分配的 pm- id；ack、peer_inbox、reply_to 都认它
source_session_id 信封 来源；由 smeltd 从 tool-host 上下文写入，不可客户端伪造
kind 信封 message | task | completion（语义标签，非 SQL enum 表）
remaining_hops 信封 自治链预算；每跳递减；耗尽则门卫拒绝再转发
permission_ceiling 信封快照 目标在本 turn 跑工具时不得抬高至此快照之上
idempotency_key 信封 发送方提供；smeltd 进程内对近期 key 去重（见 §12）
reply_to 信封 可选；指向先前 peer 条目的 id / key，表达线程，无 link 表

6.3 关系如何表达（无 session_links）

可选 session_spawn（P1）创建的是普通 durable Pi session，关系仅靠约定：

  • 标题前缀 / 命名约定（如 ← sess_a · flaky e2e）
  • 首条 transcript 的 framing 写明「由 sess_a 请求创建」
  • 可选 soft parent hint 字段放在那条初始 framing里，不进 SQL

侧栏身份、列表、删除生命周期继续走既有 session 路径——spawn 不发明第二种会话类型。

7.API / 工具（建议）

工具挂在 Pi tool-host 上，由 smeltd 实现门卫与入队。下列形状为建议，非现网契约。

7.1 P0：session_list

列出可投递的 durable Pi 会话（复用 smeltd 已掌握的 session / 侧栏身份）。无新 DB。

建议
session_list({
  "query"?: string,          // 可选：标题模糊匹配
  "include_self"?: boolean   // 默认 false
}) → {
  "sessions": [
    {
      "session_id": "sess_b_02",
      "title": "Tests · login e2e",
      "engine": "pi",
      "busy": true,
      "updated_at": "2026-10-20T01:10:00+08:00"
    }
  ]
}
  • 仅返回 Pi engine 的 durable session（排除非 Pi / 已删除）。
  • 不返回「假会话」或仅存在于内存的临时 subagent id。

7.2 P0：session_send

建议
session_send({
  "target_session_id": "sess_b_02",
  "kind": "message",           // message | task | completion
  "body": "请重跑 flaky e2e…",
  "idempotency_key": "a01:remind-b:v1",
  "reply_to"?: string,
  "remaining_hops"?: number    // 通常由门卫从入站信封继承并递减；首跳可给默认
}) → {
  "status": "enqueued",        // enqueued | duplicate | rejected
  "target_session_id": "sess_b_02",
  "reason"?: string            // rejected 时：AGENT_BUSY | LIMIT_EXCEEDED | …
}

门卫规则（进程内）

  • Pi→Pi only：双方均为 durable Pi session。
  • source：仅从当前 tool 调用的 host context 取得，忽略客户端自报 source。
  • source ≠ target。
  • inbox depth：数 B 快照里的 peer_inbox（未 ack 的 peer 消息）加在途条数；超限则 AGENT_BUSY（建议默认阈值对齐业界常见值，如 8，可配置）。
  • hops：信封内递减；≤0 拒绝。
  • permission_ceiling：快照写入信封；目标本 turn 工具权限取 min(自身, ceiling)。
  • idempotency_key：同 source + key 在进程内近期窗口视为 duplicate（见 §12 弱点）。

7.3 P1（可选）：session_spawn

经既有 create-session 路径新建 durable Pi session，再可选地向其 session_send 一条 kind=task 的初始 framing。 不写 session_links。

建议
session_spawn({
  "title": "← sess_a · flaky e2e",
  "initial_task": "重跑 login e2e 并汇总失败用例",
  "permission_ceiling"?: object
}) → {
  "session_id": "sess_c_03",
  "enqueued_initial": true
}

P0 不要求 spawn；发现 + 向已有会话 send 即可闭环「互提醒」。

8.1 Ack / 送达语义

  • enqueued：已通过门卫，主 daemon 对宿主 B 的 send_action 写成功（对发送方的 RPC 成功）。
  • delivered（权威）：B 的扩展在 message_start 回了 ack，条目已进 transcript、模型这一轮看得到。 在 Pi 里「进 transcript」和「交给模型」是同一刻，所以不再单列 consumed。

发送方默认只保证观察到 enqueued；若需要端到端确认，由目标主动 session_send(..., kind=completion) 回源（信封可带 reply_to）， 不依赖 SQL settle 行。

9.护栏与权限

9.1 护栏（无 ledger 表时如何实现）

护栏实现落点说明
Inbox 深度 B 快照里的 peer_inbox 条数，加上主 daemon 刚投出、快照还没回来的条数 满（默认 8）则拒绝；不靠 status='queued' SQL 计数，也不读 transcript
Hops 信封 remaining_hops 递减 门卫读入站信封、写出站信封；耗尽拒绝
Permission ceiling 信封快照 + 目标 turn 工具执行时取 min 防止「低权限会话借高权限会话提权」
Source 防伪 tool-host 上下文 客户端不可自报 source_session_id
Engine 边界 门卫 仅 Pi→Pi；拒绝跨引擎
幂等窗口 smeltd 进程内近期 key 集合 非全局 UNIQUE；重启后窗口清空（见 §12）

9.2 权限模型（建议）

  • 发送：调用方须是当前活跃 Pi turn 的工具调用（与 PI Desktop「plugin context」同思路）。
  • 接收：目标 session 无需事先「加好友」；发现即潜在可投（产品若要收紧，可用标题约定 / 用户设置，仍不建 link 表）。
  • 工具执行：本 turn 若由 peer 消息触发，有效权限 ≤ 信封 ceiling ∩ session 自身策略。
  • 人类始终可在 UI 中停止 / 删除目标会话；peer 消息不提升为「系统级」权限。

10.UI

智能体之间的消息不是用户对话，也不是助手回答，是「发生了一件事」。对话区里用居中的事件行表示， 和用户气泡（靠右）、助手回答（靠左）都分开。参考 Grok 对话里的「已传讯息给 〈对象〉」。

建议 · 对话区
A 的对话                                     B 的对话

  助手：我让测试那边重跑一下。                    ── 〈修登录〉发来任务 ──
                                              ┃ 请在测试会话里重跑 flaky e2e，
       ── 已发任务给 〈测试 · e2e〉 ▸ ──           ┃ 跑完把失败用例发给我。
                                              ┃ …展开
  助手：好，等它回来。
                                                助手：开始跑 e2e……
       ── 〈测试 · e2e〉交回结果 ▸ ──
                                                 ── 已发结果给 〈修登录〉 ▸ ──

10.1 事件行：统一一种样式

「非用户、非助手」的条目全部用居中事件行，包括现有的后台任务和后台子智能体交回结果（AcpEntry::TaskNote， 今天是靠左一行灰字，crates/smelt-acp-view/src/acp_view/render/conversation.rs）。不并存两种样式。

  • 一行：居中、次要文字色、小字号；前面一个图标（对话 / 任务 / 子智能体），后面是动作和对象。
  • 对象可点：〈对话标题〉是 Button（quiet），点了跳到那段对话。应用内跳转，不用 Link。
  • 有正文就能展开：行尾 ▸，点开在下方显示正文，限高滚动；展开状态沿用 TaskNote 现在的做法。
  • 失败看得出来：警示图标加文字原因，例如「发给〈B〉失败：桌面没开，拉不起这段对话」，不只靠变色。

10.2 各条目怎么画

条目事件行正文
A 里的 session_send 工具调用 「已发消息 / 任务 / 结果给〈B〉」；被拒时「发给〈B〉失败：原因」 默认收起。正文是 A 自己写的，人要看再点。替代通用工具卡片。
A 里的 session_spawn 工具调用 「新建对话〈C〉并交代任务」 默认收起
B 里的 smelt.peer_message 「〈A〉发来消息 / 任务 / 结果」 默认展开，左边框引用块，超过 4–5 行折叠。B 接下来做什么由它决定，人得直接读到。
后台任务结果（smelt.background_task） 沿用 TaskNote::summary()，例如「后台任务 … 已完成」 默认收起，同今天
后台子智能体结果（smelt.subagent_result） 沿用 TaskNote::summary()，例如「子智能体 sa-…（标题）完成」 默认收起，同今天

工具调用画成事件行靠工具名认（session_send / session_spawn，常量，和 PI_SUBAGENT_TOOL 同一做法）， 收到的消息靠 customType 认，都是显式字段，不解析正文。

10.3 其它

  • 侧栏：继续渲染既有 durable session 列表；无需为 peer 功能新表或新列。新建的对话就是一条普通对话，点进去第一条就是「〈A〉发来任务」。未读感若需要，从会话快照的 peer_inbox 等内存状态推导，render 不读 transcript。
  • 发送方 UI：P0 不做独立面板；agent 通过工具完成 list/send。可选后续：在会话菜单提供「提醒另一会话…」快捷入口，仍走同一 tool/RPC。
  • subagent：不出现在侧栏 peer 选择器中。
  • 手机：先按自定义消息的通用样式出现，事件行之后再做。

P0 · 最小闭环

  • session_list
  • session_send
  • 门卫：Pi→Pi、source 防伪、≠、depth、hops、ceiling
  • DeliverPeerMessage → BackgroundSupervisor → smelt.peer_message → message_start ack
  • 对话区居中事件行，TaskNote 一起改成同一样式

P1 · 可选 spawn

  • session_spawn（既有 create-session）
  • 标题 / 初始 framing 约定
  • soft parent hint（仅 transcript）
  • completion 回源约定文档化

P2 · 体验与硬化

  • 侧栏未读投影（读快照，不读 transcript）
  • 发送快捷 UI
  • 更稳的进程内幂等窗口 / 与既有 queue 持久化对齐
  • 可观测性：门卫拒绝指标

  • SQL collaboration ledger
  • 跨引擎 ACP 总线
  • 复活 schema-23 MCP peer
  • Task / subagent 级 A2A

状态与结果的精度代价（无账本取舍）

没有 session_messages / session_links，也就没有一份按消息记账的权威状态。 发送方要知道「送到了 / 正在跑 / 做完了 / 失败了」以及「结果是什么」，只能从两边拼： 目标会话在 AcpRegistry 里的回合相位（DaemonPhase：Idle、忙着的 Thinking / ExecutingTool / AwaitingApproval / WaitingForUser，以及 acp_idle 的挂起）， 加上目标 transcript 里那条信封，以及 B 后来用 session_send 送回 A 的 kind=completion（信封上的 reply_to）。 宿主不替这条 peer 消息单记一行。

对照：PI Desktop pi.session-orchestrator 0.6.0

那条插件的 host 账本就是状态、结果和 completion 的权威。写入按 key 幂等，自带 hop 预算，每个目标最多排队 8 条。 SessionTask 提供 status / result / wait。wait 每 1 秒看一次账本，默认等到 25 秒，最长 45 秒。 smelt 不复制这套表，于是也没有这套精度。

orchestrator 0.6.0smelt（本稿）
状态权威 账本行 B 的回合相位 + B 的 transcript + 回到 A 的 completion
结果 SessionTask.result completion 正文，自由文本
幂等 账本上的幂等写 RecentSubmissions，最多 64 条，只在目标会话的内存里
排队上限 每目标最多 8 条，跨重启仍在 宿主 B 的 peer_inbox，每目标 8 条，只在内存里，不跨宿主重启
等待 wait：1 秒一轮，默认 25 秒，最长 45 秒 宿主不等。超时由 A 自己看

落到 smelt 上的五件事

  1. enqueued 只表示主 daemon 对宿主 B 的 send_action 写成功；delivered 要等 B 的扩展在 message_start 回 ack，peer_inbox 去掉这条。 这一段是准的，但只在内存里：宿主 B 在 ack 前退出，消息就没了，没有一行把状态改成失败，发送方也不会收到通知。
  2. done 只有两种看起来像做完的信号：B 的 kind=completion 已经写进 A 的 transcript；或者这条 peer 消息 ack 之后的那一轮结束，B 回到 DaemonPhase::Idle。 后者分不出成功和放弃。Idle 同样会出现在人停掉回合、取消、或闲置挂起之后。Succeeded / Failed 是这一轮 runtime 的相位，不是这条 peer 任务的结果。
  3. RecentSubmissions（AcpSession.conversation_submit，容量 64）和在途状态都在进程内存里。 smeltd 崩溃后窗口清空。崩溃前没来得及写进 B 的 transcript 的那次，重试会再送一遍。
  4. 没有跨重启、按目标计数的队列深度。 peer_inbox 只活在宿主 B 的 BackgroundSupervisor 里，不落库。 宿主退出后，排着的 peer 消息和这个计数一起没了。
  5. result 就是 B 那条 completion 的正文，不是账本上的结构化字段。没有 SessionTask.result 这种列。

仍保持 Pi 原生的补法

  • completion 是约定，不是表。 工具说明要求 B 用 session_send 回一条 kind=completion，带上 reply_to。 A 以这条出现在自己的 transcript 里当作「做完了，结果是这段文字」。
  • 回合状态用 session_list 看。 列表读的是注册表里已有的相位和是否挂起，不另造 peer 状态枚举。A 由此知道 B 是空闲、忙，还是被 acp_idle 挂起。
  • 崩溃后的重复靠 transcript 认。 details 带上这次的 idempotency_key（RecentSubmissions 记的是加了 peer: 前缀的同一个值）。 内存窗口没了之后，扫 B 的 transcript 仍能看出这条是不是已经收过。宿主崩溃重启时不会自动扫。
  • 超时在 A。 宿主不实现 wait，也不替 A 轮询。A 若要放弃，自己看时钟，再决定要不要再发或改问 B 的相位。
何时再考虑账本
上面这些精度是用掉的，用来换零新表、以及和 Pi transcript 对齐。 真出现「要精确状态、要 wait、要在界面上监督一批工人」的需求时，账本才重新进入讨论。 在那之前，发送方从回合相位和 completion 推断，就是这条设计的边界。

12.风险与取舍

相对 PI Desktop SQL ledger 的诚实弱点
  • 幂等非全局：无 UNIQUE(source, idempotency_key) 表约束；daemon 重启后进程内去重窗口丢失，可能导致重复 enqueue（transcript 可能出现两条相同 peer 条目）。
  • 崩溃窗口：已通过门卫、还没 ack 的条目只在宿主 B 的内存里（现网没有可借用的 turn queue 持久化），宿主退出就丢。
  • inbox 深度近似：读 peer_inbox 镜像加在途计数，不如 SQL status='queued' 计数精确，极端并发下可能短暂漂移。
  • 无 exactly-once completion 账本：回执靠目标再 send；重复 completion 需接收方自辨（信封 key / reply_to）。

12.1 用 transcript + 既有队列尽量补

  • 优先落 transcript：一旦 append，消息即成为会话历史的一部分，随 Pi 既有持久化存活——这是本设计的主恢复面。
  • 复用既有投递机制：ack 前的条目和后台任务结果走同一个 BackgroundSupervisor 队列，clear_queue、fork、reload 后照样重写；不另造协作表。
  • 消费侧去重：Pi 在纳入上下文前，可对近期 idempotency_key 相同的 peer 条目折叠显示 / 跳过重复工具副作用（建议行为，P2 硬化）。
  • 发送侧重试：工具层对 enqueued / duplicate 给出明确结果；发送方用同一 key 重试是安全的仅在进程内窗口仍有效时——文档与 SDK 注释需写清。

12.2 为何仍选这条路

产品认为「再开一套协作 SQL」与 Pi-native 心智冲突，且维护成本（migration、投影、与 transcript 双写一致性）高于其带来的恢复收益。 smelt 选择薄 host 门卫 + 厚 transcript 真相；接受上述弱点，并在 §13 保留「若生产事故证明不够，再评估最小持久化」的退路——但那不是 P0 默认。

13.开放问题

  1. Peer 条目的精确 transcript schema。 已定：Pi 自定义消息，customType: "smelt.peer_message"，元数据在 details（§6）。
  2. 既有 turn / input queue 的持久化强度。 已查：没有持久化。pending_prompts 和 BackgroundSupervisor 都只在内存里，丢失面见 §12。
  3. Inbox 深度默认阈值。 统计口径已定为 peer_inbox（未 ack）。阈值建议先用 8，用指标验证。
  4. Hops 默认初始值。 PI Desktop 约从 9 递减；smelt 是否同值，或按产品更保守。
  5. 人类是否可在 UI 手动「注入 peer 样式」消息。 建议否——peer channel 仅 daemon 门卫可写，避免伪造 provenance。
  6. P1 spawn 是否限制「worker 不可再 spawn」。 PI Desktop 有此限制；无 link 表时只能靠信封 hint / 标题约定软限制，或门卫读目标 transcript 初始 framing——需产品拍板。
  7. 若 P0 线上重复投递不可接受，最小补丁是什么。 例如：仅一张极瘦的 idempotency_keys（非完整 ledger）——当前产品偏好仍是尽量不走 SQL；列为应急选项而非计划。
决策摘要
P0 = session_list + session_send；Pi transcript 即收件箱； smeltd 做校验与入队；零新协作 SQL 表 / 字段；spawn 可选且无 link 表； 与 PI Desktop ADR 0239/0240 对照后有意选择更薄路径。
