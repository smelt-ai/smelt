smelt Pi↔Pi 会话消息技术方案

日期：2026-10-20（Asia/Taipei） · 受众：smelt 仓库维护者（Rust smeltd + Pi agent） · 状态：P0 实现中（PR #55）。本稿和代码一致，名字以代码为准
项目： smelt-ai/smelt （macOS AI coding cockpit · smeltd + Pi / Bun） · 依据调研： 2026-10-20-pi-and-industry-session-messaging.md 等
Pi transcript 即收件箱 零新 SQL 账本 仅 Pi ↔ Pi 先收下，再投递

1.背景与目标 / 非目标

1.1 为何要做

smelt 是 macOS 上的 AI coding cockpit：侧栏里的 Pi 对话由 smeltd（Rust）托管， 对话里的 agent 是 Pi（Bun）。产品要让 Pi 对话之间自由通信：一个正在跑的 Pi 对话 能给侧栏里另一个 Pi 对话发消息、交代任务、交回结果，对方在自己的回合里处理； 也能起一个新的 Pi 对话，把一块独立的活交给它。

这和现有 subagent（后台子进程、只向父报告、不进侧栏）是不同层： subagent 保持不变；这里说的是侧栏里那些普通 Pi 对话之间的协作。

1.2 目标

  • 发现：列出侧栏里的其它 Pi 对话，在跑的、挂起的、这次还没打开的都算。
  • 发送：给其中一个发消息、任务或结果。对方没在跑就先把它拉起来。
  • 起新对话：在同一个项目里新建一个 Pi 对话，模型、权限和发起方一样，第一条就是交代给它的任务。
  • 送达权威在目标 Pi 的 transcript：消息作为自定义消息进了 transcript 才算送到。
  • 工具调用立刻返回：smeltd 当场只做便宜的检查，收下之后在后台拉起对方、建对话、投递；后台失败了给发送方退信。
  • 不引入协作账本表。

1.3 非目标

  • 不做跨引擎 ACP 总线（Claude / Codex / 其他 runtime 互通）。
  • 不复活已删除的 schema-23 MCP peer 总线（smelt-agent-mcp / peer_message_*）。
  • 不做子智能体之间互聊：子智能体仍然只向父会话交结果（与 PI Desktop ADR 0165 同向）。
  • 不新增 session_messages / session_links 等 SQL 协作账本，也不为该功能在 smelt.sqlite3 上加新 schema 字段。
产品偏好
协作状态放进 Pi transcript，而不是 host SQL 账本。 接受相对 PI Desktop 更薄的持久化保证（见 §12），换取零新表、与 Pi 原生会话模型对齐。

2.设计原则

  1. Pi transcript 即收件箱。 对方收到的是一条 Pi 自定义消息（customType: "smelt.peer_message"），元数据在 details。 界面和模型都从 transcript 本身读到「谁发来的」。
  2. 零新 SQL 账本。 不新增 session_messages、session_links，不为这个功能扩展 smelt.sqlite3。 sourceSessionId、kind、hops、replyTo 住在那条自定义消息的 details 里； 发件队列、链预算只在主 daemon 内存里。
  3. 来源只认连接。 来源是「这条宿主控制连接属于注册表里哪个对话」，请求里不带来源，也不带跳数。 模型在 bash 里读得到自己的环境，请求里写什么都能伪造。
  4. 先收下，再处理。 session_send / session_spawn 只等主 daemon 做完便宜的同步检查，拿到「已收下」和 id 就返回。 拉起对方、建新对话、写配置这些慢事在主 daemon 后台做，做不成就给发送方退信。 工具调用不会因为对方慢而超时，也就没有「超时了，到底送没送」的歧义。
  5. id 由这次调用决定。 消息 id、新对话 id 都由（来源对话，Pi 的 toolCallId）算出来。 同一次调用不管重放几次，都落到同一条消息、同一个对话。模型不用自己出幂等 key。
  6. 目录和运行时分开。 能发给谁看对话目录（§5.1）；对方此刻有没有在跑，交给一个统一的「拉起」函数：挂起的唤醒，没打开的请桌面打开。 peer 投递、手机提交、手机旁观都用这一个函数，不各写一套。
  7. 复用既有结果投递路径，不当用户输入。 投递就是交给目标宿主的 BackgroundSupervisor，和后台任务、子智能体交回结果走同一条 listen / ack。 不走 Prompt / FollowUp。
  8. 与 subagent 分层。 subagent：后台、只报告、不进侧栏。peer：侧栏里的 Pi 对话之间。

4.与 PI / 业内对照

4.1 PI Desktop：host SQL collaboration ledger

PI Desktop（ADR 0239 / 0240）对 durable Agent Session 采用host 拥有的协作账本：

  • session_collaboration_messages：按 message ID / idempotency key 幂等；kind ∈ {task, message, completion}
  • session_collaboration_links：仅记录 spawn 创建的 parent–worker 关系
  • 投递经 turn queue（忙则排队）；inbox 深度、hops、permission_ceiling 均有 SQL / host 侧权威
  • 崩溃恢复与 exactly-once completion 回调由 ledger 支撑

4.3 业内简述

  • 报告型子 agent：Claude Code Task、PI Task——子结束交结果，无兄弟 peer；smelt subagent 属此类，保持不变。
  • 对等投递：PI Desktop session collaboration——smelt 产品语义同类，实现落点改为 transcript。
  • 异步命令 + 发件箱（outbox）：受理和处理分开、按确定的 id 去重、失败回执给发送方，是消息系统和 saga 的常规做法。本稿的发件队列就是这个模式，只是放在内存里。

5.总体方案

三个角色：发起方 Pi（A）、主 smeltd（门卫 + 发件队列）、目标 Pi（B）。 A 的工具经自己的会话宿主把请求交给主 daemon；主 daemon 当场检查、收下、回 id； 再在后台把 B 拉起来，把消息交给 B 宿主的 BackgroundSupervisor； B 的扩展把它写成 smelt.peer_message 进 transcript，按既有 claim / ack 认领。

5.1 对话目录与拉起

目录：能发给谁

目录是这两处的并集，不含自己：

来源算哪些state
主 daemon 的 AcpRegistry 启动规格是 Smelt 的 Pi、不归自动化、runtime 在跑或被闲置挂起的对话 busy / idle / suspended
桌面发来的侧栏菜单（WorkspaceMenuSnapshot） kind = acp、agent = "pi"、不在注册表里的对话：侧栏上有，这次 daemon 还没打开过 dormant
  • 注册表里有、但 runtime 已经退出又不是挂起的（agent 崩了，等用户点重启），不进目录。拉起它要用户决定。
  • 标题按侧栏上的名字：先取菜单里的（含用户改过的），再取远程目录里的，再取对话自己的标题。
  • 菜单按运行时分开发，daemon 拿到的只是这台运行时上的对话，不会列出别的机器上的。
  • 远程目录（daemon 自己建的对话，手机建的、session_spawn 建的）只记在跑的；冷启动时没有 runtime 的记录会被删掉。桌面把这些对话收进侧栏之后，它们就和别的侧栏对话一样出现在菜单里。

拉起：一个函数

acp_host.rs 里两个函数，分别回答「有没有这个对话」和「它在不在跑」： 

/// 注册表里有就直接给；没有但在侧栏菜单里，请桌面打开，等槽出现（最多 15 秒）。
fn conversation_slot(id) -> Result<Slot, String>

/// 在 conversation_slot 之上，挂起的再唤醒，等 runtime 就绪。
fn ensure_conversation_runtime(id) -> Result<Slot, String>
调用方用哪个改动
手机旁观（handle_acp_watch） conversation_slot 原来内联的「没有就请桌面打开」挪进去。旁观不唤醒挂起的 runtime，镜像够看
提交输入（handle_acp_submit_input） ensure_conversation_runtime 原来只认注册表 + 唤醒挂起。现在手机给没打开的对话发消息也会请桌面打开，不再报 ACP session not found
peer 投递（发件队列） ensure_conversation_runtime 新增

拉不起来时的原因原样给调用方：桌面没开、桌面没在时限内打开、对话已经不在侧栏、挂起的 runtime 起不来。 手机看到的是错误提示，peer 发送方收到的是一封退信。

通信链路 / 传输层

不新开协议、不新开套接字、不走 MCP、也不让两个 Pi 直接连。 扩展只连自己这个会话宿主上已经在听的 Unix 套接字；宿主只沿主 daemon 拉起它时留下的那条 socketpair 把请求交上去； 主 daemon 找到目标宿主，把一条 AcpUserAction 写过去。

现成的三条通道

谁和谁现网这次怎么用
Pi → 自己的会话宿主 BackgroundSupervisor::start 在临时目录听 smbg-{pid}-{nonce}.sock（权限 0o600），路径放进这个 Pi 的 SMELT_BACKGROUND_TASK_SOCK。 handle_client（background_tasks.rs）按一行 JSON 的 op 分流。扩展侧短调用是 callBackgroundHost。 加 session_list / session_read / session_send / session_spawn 四个短 op，一问一答。 owner 非空是子智能体，一律拒绝：peer 只给会话本身用。
会话宿主 ↔ 主 smeltd 每个对话是一个 smeltd --acp-session-host，和主 daemon 之间一条 UnixStream::pair()。 daemon → 宿主是 AcpUserAction（send_action）；宿主 → daemon 是快照行和 history_page 回包。 宿主 → daemon 加一种行 {"peer_request": {"request_id", "op", "body"}}，dispatch_snapshot_line 和 history_page 一样先分流； daemon 用 AcpUserAction::PeerReply { request_id, reply } 回答，宿主的动作循环先截下来交给 peer_link::complete。 不走 Control API：那是 smeltd.sock 上靠参数里的 session id 和 token 认人的，token 就在 Pi 的环境里。
主 smeltd → 目标宿主 → Pi B 槽在 AcpRegistry，句柄是 AcpSession.hosted_handle。Pi 的 stdin 由 write_rpc 写。 新动作 AcpUserAction::DeliverPeerMessage { message }，宿主交给自己的 BackgroundSupervisor。

1. Pi A → 宿主 A

工具写一行 {"op": "session_send", "toolCallId", "to", "text", "kind", "replyTo"}，读一行回答。 宿主只托管这一个对话，不改写也不添加来源；去掉 op / owner 后原样转给主 daemon，等 15 秒。 主 daemon 只做同步检查，正常几毫秒就回。

2. 宿主 A → 主 smeltd：门卫

主 daemon 每收一行 peer_request 单开一个线程回答。来源就是这条控制连接所属的注册表 id； 连接已经被换掉（同一个 id 有了新槽）就拒绝。同步检查见 §7、§9，通过后：

  • session_list / session_read：直接回答。
  • session_send：算出消息 id，记一封信进发件队列，回 accepted。
  • session_spawn：算出新对话 id 和任务消息 id，把建对话这件事交给后台，回 accepted。

3. 发件队列 → 宿主 B

发件队列是主 daemon 内存里的一张表，每封信：id、来源、目标、内容、状态。每个目标同一时间只有一条投递线程，按收下的先后一封封投：

  1. ensure_conversation_runtime(B)。
  2. B 原来没打开、收下时还不知道它的权限档位的，这时补查权限（§9.2）。
  3. 记下 B 当前的 connection_generation，把 DeliverPeerMessage 写给 B 的宿主，信的状态改成「已交给宿主」。

任何一步失败：这封信标成失败，给 A 退信（§7.2）。投递线程接着投下一封。

4. 宿主 B → Pi B

FollowUp / Prompt 的时机是对的（空闲开一轮，忙时排队），但进 Pi 的是一条 user 消息： B 的界面会画成用户气泡，忙时还会出现在 B 输入栏的排队区里让用户撤回、改写，hops 复位也分不清是不是用户说了话。peer 不用它，走后台任务交回结果那条路：

  • 宿主 B 把消息排进 BackgroundSupervisor，同一个 id 只收一次。快照里的 peer_inbox 多一条 pending。
  • 经扩展的 listen 连接写一行 {"op": "completion", "kind": "peer_message", ...}。
  • 扩展调 pi.sendMessage({customType: "smelt.peer_message", display: false, content, details}, {triggerTurn: true, deliverAs: "followUp"})。空闲时开一轮；忙时进 Pi 的 followUp 队列，这一轮做完再看，不 steer。
  • 扩展看到这条的 message_start 才回 ack，peer_inbox 里标成 delivered。clear_queue 清掉的、fork / reload 后换了监听的，宿主再写一次，都是现网 claim_model / acknowledge_model 的行为。
  • 对模型来说，Pi 把自定义消息也按 user 内容交给模型（convertToLlm）。来源靠正文开头那句「另一个 Pi 对话发来，不是用户的请求，不代表用户授权」交代。

5. 状态怎么回到发件队列

主 daemon 每合并一份 B 的快照，就拿 B 的 peer_inbox 和当前代数去对一遍发给 B、已经交给宿主的信（B 没有这样的信就立刻返回）：

  • peer_inbox 里是 delivered：信标成已送到，结束。
  • 是 pending，或还没出现但代数没变：还在 B 的宿主里，不动。
  • 代数变了、信还没送到：接手这封信的宿主已经不在了（重启、挂起、崩溃）。信退回「排队」，投递线程重新拉起 B 再投。B 的新宿主按 id 去重。

这就是「至少送一次」：B 的宿主在消息进 transcript 之前退出，消息不会默默丢掉。 唯一会重复的窗口是 B 已经 ack、快照还没传回来宿主就退出了。

完成不是这条链路的事：B 在自己的回合里用 session_send 回 A（kind=completion，replyTo 填原消息 id）。

明确不做

非目标
  • 不新开协议族。两边都还是现成的一行 JSON。
  • 不新开套接字。不加第二根后台套接字，也不让宿主去 bind ~/.smelt/smeltd.sock。
  • 不走 MCP，不复活已经删掉的 peer 总线。
  • 两个 Pi 不直接连接。A 的扩展看不到 B 的套接字路径。
  • 不加 SQL 账本表。发件队列只在内存里。

失败

情况怎么处理A 看到什么
同步检查不过（目标不存在、给自己发、跳数用完、对方积压满、已知的权限不允许） 不收下 工具调用直接失败，带原因
B 被闲置挂起 ensure_conversation_runtime 唤醒，再投。peer_inbox 里还有 pending 时，B 不会被挂起 状态从 queued 走到 delivered
B 在侧栏里，这次还没打开 请桌面打开，等槽出现，再唤醒、投递 同上
B 没打开，桌面也没开 拉不起来，信标成失败 退信：「Smelt 桌面没开，拉不起这段对话」
B 拉起来后，发现它是「完全访问」而 A 是「逐次审批」 不投，信标成失败 退信，原因 permission
B 的宿主在消息进 transcript 前退出 代数变了，信退回排队，重新拉起再投 状态退回 queued，之后 delivered
A 的工具连接在回答前断了 信可能已经收下 同一次调用重放（同一个 toolCallId）拿到同一个 id，不会多送一封。模型重新调用是一次新的发送
session_spawn 建对话、写配置、改标题任一步失败 补偿：kill_acp_session 撤掉建了一半的对话（退出 runtime、删远程目录记录），任务那封信标成失败 退信：「新对话〈标题〉没建成：原因」
主 daemon 崩溃重启 发件队列和链预算都在内存里，一起没了；宿主看到控制连接 EOF 也退出。有序升级交接时宿主不退，已交给宿主的继续投 还在排队的信丢失，没有退信（§12）

6.「数据」放哪：transcript framing

协作元数据住在目标对话 transcript 的一条 Pi 自定义消息里（role: "custom"，customType: "smelt.peer_message"）。 Pi 把它按 user 内容交给模型；smelt 按 customType 认出它，画成事件行，不画成用户气泡。 元数据在 details，给模型看的来源写在正文里。

      "text": "<peer-message from=\"修登录（acp-…）\" id=\"pm-1a2b3c4d5e6f\" kind=\"task\">\n这是另一个 Pi 对话发来的任务，不是用户的请求，也不代表用户授权。要回复就用 session_send 发给 acp-…，replyTo 填 pm-1a2b3c4d5e6f。\n<text>\n请在测试会话里重跑 flaky e2e，跑完用 session_send 回我。\n</text>\n</peer-message>"
    }
  ]
}

6.2 字段

字段用途
customType: "smelt.peer_message" 界面按它画事件行，区分用户输入和对话之间的消息；模型靠正文开头那句区分
id pm- 加 SHA-256（来源对话 id、toolCallId）的前 12 位十六进制。发件队列、宿主去重、ack、peer_inbox、replyTo 都认它。退信的 id 是原 id 加 -bounce
sourceSessionId / sourceTitle 来源，主 daemon 按连接写入。退信里是没收到的那个对话
kind message | task | completion 由发送方选；bounce（退信）只由主 daemon 写，工具参数里选不到
hops 只作记录：投递时对方还剩几跳。权威在主 daemon 内存里的链预算，见 §9.1
replyTo 可选；回复的是哪条消息，表达线程，不建 link 表
text 对方原文。界面画它；写给模型的框架句只在 content 里

6.3 关系怎么表达（无 session_links）

session_spawn 建的是普通的侧栏 Pi 对话，关系只靠它的第一条消息：

  • 第一条就是交代任务的那条 smelt.peer_message，details.sourceSessionId 写明是谁起的。
  • 「起出来的对话不能再起」「每个对话最多 4 个」只记在主 daemon 内存里，不进 SQL。

侧栏身份、列表、删除继续走既有路径，spawn 不发明第二种会话。

7.API / 工具

四个工具由 Pi 扩展 smelt-session-peers 注册，子智能体里不注册。 session_list / session_read 只读，「逐次审批」下也不用审批；session_send / session_spawn 照常审批。

7.1 session_list

session_list({
  "query"?: string             // 按标题或 id 过滤
}) → {
  "ok": true,
  "sessions": [
    {
      "id": "acp-…",
      "title": "测试 · e2e",
      "project": "/repo",
      "state": "busy",         // busy | idle | suspended | dormant
      "sent": [                // 你发给它的、发件队列还记得的
        { "id": "pm-1a2b3c4d5e6f", "kind": "task", "status": "delivered" },
        { "id": "pm-7f8e9d0c1b2a", "kind": "message", "status": "failed", "error": "Smelt 桌面没开…" }
      ]
    }
  ]
}
  • 目录见 §5.1。dormant 告诉模型：发消息会让桌面把它打开，可能要等一会。
  • sent 取自发件队列：queued 还在主 daemon 里等对方拉起；pending 已在对方宿主里、还没进 transcript； delivered 已进 transcript；failed 带原因，同时已经退信。 每个来源留最近 64 封已结束的。主 daemon 重启过，之前的就不在了。

7.2 session_read（只读拉取）

session_read({
  "sessionId": "acp-…",
  "limit"?: number             // 最近几条助手回复，默认 1，最多 5
}) → {
  "ok": true,
  "sessionId": "acp-…",
  "title": "测试 · e2e",
  "state": "idle",
  "replies": ["e2e 跑完了，失败 2 个：…"]
}
  • 先读主 daemon 里的会话镜像；宿主模式下镜像只留当前回合，不够时向还活着的宿主要一页历史。不唤醒、不打开对方，也不进对方的 transcript。
  • 挂起的只给镜像里有的；dormant 的拒绝（not_running）：为了读而把对话拉起来不值得，要它干活就发消息。
  • 只返回助手的文字回复，每条截到 4000 字符；不返回用户消息、工具输出和思考。

7.3 session_send

session_send({
  "to": "acp-…",
  "text": "请重跑 flaky e2e…",
  "kind"?: "message",          // message（默认）| task | completion
  "replyTo"?: "pm-…"
}) → {
  "ok": true,
  "status": "accepted",
  "id": "pm-…",
  "to": { "id": "acp-…", "title": "测试 · e2e" },
  "hops": 7
} | {
  "ok": false,
  "reason": "inbox_full",      // not_found | self | permission | inbox_full | hops_exhausted | invalid
  "error": "对方还有 8 条消息没收，等它处理完再发"
}
  • 扩展把这次的 toolCallId 一起交上去，模型不填。参数里没有来源，也没有跳数。
  • accepted 只表示主 daemon 收下了。之后送没送到用 session_list 的 sent 看；送不到会收到退信。
  • 同一个 toolCallId 再来一次，回同一个 id 和同样的 accepted，不多送。

退信

一封信失败时，主 daemon 给发送方投一条 kind=bounce 的 smelt.peer_message： 来源是没收到的那个对话，正文写明哪条消息、为什么没送到，附原文开头。 退信走同一个发件队列，但不过门卫、不耗跳数、不算积压；退信自己再失败只记日志，不再退。 它会叫醒发送方开一轮：模型需要知道，才能换个对象或者告诉用户。

7.4 session_spawn

session_spawn({
  "title": "跑 e2e",
  "task": "重跑 login e2e 并把失败用例发回来"
}) → {
  "ok": true,
  "status": "accepted",
  "id": "pm-…",                // 交代任务的那条消息
  "to": { "id": "acp-…", "title": "跑 e2e" }
}
  • 同步检查：发起方不是别人起的；跳数没用完；它起的、还开着或正在建的对话不到 4 个；找得到它的启动规格、工作目录和 Pi 配置。
  • id：新对话 id 是 acp- 加 SHA-256（来源、toolCallId、"spawn"）的前 32 位十六进制，任务消息 id 照 §6.2 算。同一次调用重放，拿到同一个对话，不会建第二个。
  • 后台步骤，每一步等 agent 确认再走下一步：
    1. 照发起方的启动规格（智能体、环境、工作目录）create_daemon_acp_session，记进远程目录，桌面把它收进侧栏；
    2. copy_session_config：模型、推理强度、权限模式和发起方一样；
    3. SetSessionTitle；
    4. 把任务作为一封信交给发件队列，之后和 session_send 一样。
  • 补偿：1–3 任一步失败，kill_acp_session 撤掉这个对话，从「它起的对话」里去掉，给发起方退信。侧栏上不会留下一个没任务、配置不对的空对话。
  • 跳数：交代任务那条消息照常耗一跳，在同步检查时就扣掉。

9.护栏与权限

9.1 护栏

护栏实现落点说明
只在 Pi 对话之间 对话目录 双方都是 Smelt 的 Pi、不归自动化；子智能体拿不到这四个工具，宿主也拒绝非空 owner
来源防伪 宿主控制连接 来源 = 连接所属的注册表 id；请求里不带来源
积压 发件队列里发给这个对话、还没送到的信（queued + pending） 到 8 封就拒收新的（inbox_full）。发件队列是唯一往宿主投 peer 消息的地方，这个数是准的，不用再估在途
跳数 主 daemon 内存里每个对话一个链预算（初始 8） A 发一条，消息带 A 的预算减一，减到 0 拒绝（hops_exhausted）；B 的预算记成 min(现值, 消息带的)；用户在 B 里说话时复位。daemon 重启回到初始值，仍然有界
权限 比较两边的权限模式 见 9.2
去重 id 由（来源，toolCallId）算出 发件队列见过这个 id 就回原结果；宿主 B 同一个 id 只排一次
起新对话 主 daemon 内存 每个对话同时最多 4 个它起的（含正在建的）；起出来的不能再起。daemon 重启后清空

9.2 权限

Pi 只有「逐次审批」「完全访问」两档、整个对话共用一份。消息触发的回合在对方自己的档位里跑，审批照样弹给人。规则只有一条：

规则
对方是「完全访问」、发送方是「逐次审批」，就不送（permission）。否则会变成：发送方不经审批，借对方之手执行本来要审批的操作。
  • 什么时候判：对方在跑或挂起时，档位在会话镜像里，收下前当场判、当场拒。对方还没打开时不知道档位，拉起之后、投递之前判，不过就退信。
  • 「完全访问」发给「完全访问」：允许，不加限制。 发送方自己已经能不经审批做对方能做的任何事：同一台机器、同一个系统用户、同样不审批，工作目录也拦不住它 cd 到别处。 借对方之手不会多出任何权限。这条规则防的是权限升级，不是协作本身。
  • 「逐次审批」发给「逐次审批」、「完全访问」发给「逐次审批」：允许，对方要做的事照样一件件等人点头。
  • 对方不用事先「加好友」：在目录里就能收。人始终可以在界面上停掉、删掉任何一个对话。

对话之间的消息不是用户说的话，也不是助手回答，是「发生了一件事」。对话区里用居中的事件行表示， 和用户气泡（靠右）、助手回答（靠左）都分开。参考 Grok 对话里的「已傳訊息給 〈对象〉」。

10.1 事件行：统一一种样式

「非用户、非助手」的条目全部用居中事件行，包括现有的后台任务和后台子智能体交回结果（AcpEntry::TaskNote）。不并存两种样式。

  • 一行：居中、次要文字色、小字号；前面一个图标，后面是动作和对象。
  • 对象可点：〈对话标题〉是 Button（quiet），点了跳到那段对话。应用内跳转，不用 Link。
  • 有正文就能展开：行尾 ▸，点开在下方显示正文，限高滚动。
  • 失败看得出来：警示图标加文字原因，不只靠变色。当场被拒的，画在发送那一行上（「发给〈B〉失败：原因」）；后来才失败的，是一条退信。

12.风险与取舍

相对 SQL 账本的弱点
  • 主 daemon 崩溃会丢信：发件队列只在内存里。崩溃时还在排队的信没了，发送方收不到退信；它 session_list 时会发现 sent 里没有这条。有序升级交接不受影响。
  • 至少送一次，不是恰好一次：B 已经 ack、快照还没传回来宿主就退出，这条会再投一次，B 的 transcript 里出现两条同 id 的消息。
  • 没打开的对话要靠桌面：启动规格归桌面，桌面没开就拉不起来，只能退信。
  • 「谁起的」不跨重启：daemon 重启后，「起出来的不能再起」「最多 4 个」从零算。

12.1 为何仍选这条路

「再开一套协作 SQL」与 Pi-native 心智冲突，维护成本（迁移、投影、与 transcript 双写一致）高于它带来的恢复收益。 上面的丢失窗口只在主 daemon 崩溃时出现，而那时所有对话的宿主也一起退出，正在跑的回合本来就断了。 如果使用中证明这不够，再评估把发件队列落进 SQLite；那是按字段建的表，不是 JSON。

13.开放问题

下面两条要在真机上看，代码读不出来：

  1. 忙时排进 followUp 的自定义消息，会不会出现在 B 输入栏的排队区。 PiQueueMirror 镜像的是 Pi 的 follow_up 队列；如果它把自定义消息也当成「用户排队的消息」显示，用户能撤回、改写，就要在镜像里按类型滤掉。
  2. clear_queue 后的静默重写会不会丢。 用户按停止清掉队列后，宿主把没 ack 的 peer 消息再写一次，但不叫醒模型；扩展这时立刻 ack。 如果 Pi 那一刻还没把它放进 transcript，就会出现「已 ack、没进 transcript」。

已定的不再列为开放问题：信封格式（§6）、积压上限 8 与跳数初始 8（先按这个用，看实际再调）、人不能手动发 peer 样式的消息、起出来的对话不能再起、重复投递用确定的 id 解决（§2 第 5 条）。

决策摘要
Pi transcript 即收件箱；主 daemon 做门卫和内存发件队列：先收下、后台拉起对方再投、失败退信； id 由（来源，toolCallId）算出；对话目录含没打开的侧栏对话，拉起统一走 ensure_conversation_runtime； session_spawn 失败就撤掉建了一半的对话；零新协作 SQL 表 / 字段。
