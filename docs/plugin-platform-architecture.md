# Smelt 全应用插件化技术方案

**状态**：插件 API、Host、SDK 和受管运行时已落地。
**日期**：2026-08-31

## 1. 目标

插件化的目标是让外部集成和可选功能能独立新增、升级、停用和删除，同时不改变
终端、ACP、会话、工作区和存储这些核心能力的行为。

Smelt 采用“微内核 + 共享运行时插件”：

1. 核心负责不可拔出的本地执行、数据一致性、安全边界和 UI 外壳。
2. 插件通过版本化的公开契约观察状态、请求受控操作并声明可渲染的能力。
3. 核心不为某个集成增加专用字段、路由、数据库表或 IPC 操作。

这不是把全部代码移出核心。需要高频、本地、低延迟协作的功能保留在核心；外部
服务、任务来源、提供方集成、通知和可选工具面板适合通过插件提供。

## 2. 核心与扩展边界

### 核心拥有

- 终端、PTY、ACP 连接和会话生命周期；
- Workspace、项目、Git worktree 与本地文件操作；
- SQLite 事务、事件日志、任务和会话的通用投影；
- 插件发现、包完整性验证、capability 授权、共享运行时监管和重试策略；
- GPUI 外壳、插件管理和通用贡献面渲染；
- 本地密钥存取、受控日志与诊断。

### 插件拥有

- 外部服务协议、账号状态、业务映射和同步策略；
- 插件私有数据、游标、重试队列和远端幂等状态；
- 对公共事件的订阅处理；
- 通过公开 Action 发起的受限本地操作；
- 设置、菜单、实体装饰、输入路由、智能体身份和工具面板等贡献。

核心只保存稳定的通用标识，例如 `PluginResourceRef`。插件私有语义、凭据和远端
状态不得投影成核心关系表或持久化结构。

## 3. 目录与包结构

```text
crates/
  smelt-plugin-api/    # 版本化 wire DTO、manifest、capability、事件和 Action
  smelt-plugin-host/   # 包发现、校验、认证、运行时与受管生命周期
packages/
  plugin-sdk/          # TypeScript/Bun 插件 SDK
plugins/
  <plugin>/            # bundled 插件包
```

每个插件包都必须有 `plugin.json`。按需要可附带：

- `plugin-ui.json`：设置、账户、菜单、实体装饰和资源创建等原生 UI 声明；
- `plugin-input.json`：会话输入路由声明；
- `plugin-agent.json`：产品级 Agent 与会话控制器声明；
- `assets/`：静态图标和其他包内资源；
- `web/`：受控 WebView 工具面板资源。

包内入口、sidecar 和资源都由 Host 从包根解析；不得通过任意绝对路径或软链接逃逸到
包外。

## 4. 四类公开契约

### Event / Snapshot

Event 表达已经提交的事实，例如任务生命周期、会话状态和工作区变更。插件订阅
durable 事件时，必须先持久化自己的处理进度或 outbox，再 ACK 给核心。这样插件
崩溃或网络失败不会让已提交的本地事实丢失。

Snapshot 是当前投影的只读视图，适合启动补齐、状态重建和 UI 刷新。Event 与
Snapshot 都是公开 DTO，不能泄露核心内部句柄或凭据。

### Action

Action 是插件向核心提出的有副作用请求。每个 Action 都需要：

- manifest 声明的 capability；
- 经过认证的插件实例；
- 有界、可校验的请求参数；
- 稳定的 `command_id`，用于幂等去重和结果恢复。

Action 只表达通用领域操作，例如创建任务、解析项目、创建隔离工作区或提交会话操作。
不提供万能 JSON 通道，也不按插件 ID 分支。

### Invocation

Invocation 是核心同步调用插件的已声明能力，例如执行设置页按钮、获取账号头像、
解析输入路由或读取工具面板数据。Host 验证调用目标属于当前实例、参数符合声明，
并对超时和失败做显式处理。

### Contribution

Contribution 让插件声明宿主能够理解的 UI 或会话能力。声明是有限的 schema，而不是
可执行 UI 代码；动态数据通过 Invocation 返回受限 view model。宿主负责渲染、焦点、
权限和生命周期，插件只提供内容与已声明命令。

## 5. 生命周期

1. Host 发现 bundled 或已安装包，解析并校验 manifest、入口和所有 sidecar。
2. Host 根据运行时类型启动受管共享运行时，并验证其可执行文件和包完整性。
3. Host 根据用户授权和 manifest 建立 capability grant。
4. Host 只向已声明的 contribution 分发 Invocation。
5. 停用、升级、崩溃或卸载时，Host 停止共享运行时、移除贡献并按策略清理进程。

插件缺失、损坏、完整性验证失败、启动超时和连续崩溃都不能阻止 Smelt 的核心功能启动。
失败状态应在插件管理界面可见，而不是静默降级成成功。

## 6. 数据与安全边界

### 私有数据

每个插件只使用自己的 `plugin-data/<plugin-id>` 目录。插件不能直接打开核心
`smelt.sqlite3`，也不能读取其他插件的数据目录。插件需要的持久化游标、外部映射和
outbox 都保存在私有目录中。

### 凭据

凭据由核心密钥服务按 `(plugin_id, account_id, secret_name)` 隔离。插件只能通过授权的
secret Action 访问自身命名空间。日志、事件、崩溃报告、Snapshot 和 UI 投影不得包含
token、cookie 或私有绝对路径。

### Capability

Capability 约束的是 Smelt API，而不是操作系统权限。插件跑在受管 Bun 里，拥有当前
用户的文件系统、网络和进程权限；安装确认必须把这一点说清楚，不能把 capability
清单当成 OS sandbox。

## 7. 通用会话与 UI

### 会话输入

会话可由 `ConversationBinding` 绑定到已声明的输入路由。提交文本或附件时，daemon 只调用
该绑定对应的插件能力；路由失败必须通过明确的重试或错误状态处理，不能偷偷改走另一条
投递路径而造成重复执行。

### 原生贡献

设置页、侧栏账户、资源创建、实体装饰、菜单和会话动作都使用受限 DTO。动态 action
只能引用当前包已经声明的 Command；宿主重新验证命令、capability 和输入上下文后才执行。

工具面板使用独立的 web 资源或 Host 支持的运行时。插件不能把任意组件树或宿主内部对象
传入 UI 线程。

## 8. 运行时与分发

插件入口由受管 Bun 执行。Host 统一负责包内容校验、版本兼容、启动路径
和实例生命周期；GUI 与 daemon 不直接依赖某个插件的实现 crate。

bundled 包随 App 一起 staging，安装包使用原子插件集合切换，避免运行中的实例读取半更新
内容。用户安装与更新必须展示来源和 capability 差异，并在用户确认后生效。

共享 Bun Host 的完整性、来源和 capability 审核仍由 Host 负责；不能因其不是
独立二进制而放松校验。

## 9. 开发与验收

新增或迁移一个插件功能前，应确认现有公开契约是否足够。只有真实需求无法通过现有
Event、Action、Invocation 或 Contribution 表达时，才新增版本化 API。

最低验收包括：

- manifest、sidecar、入口和资源路径的有效性测试；
- capability 未声明、未授权或资源范围不匹配时的拒绝测试；
- 启用、停用、崩溃、升级和卸载时的生命周期测试；
- durable 事件 ACK、重启恢复和幂等 Action 的测试；
- 无插件、插件损坏或插件停用时核心终端、ACP、项目和设置仍可用的测试；
- 打包布局、运行时入口和包内容校验测试。

任何实现若要求在核心添加特定插件的字段、条件分支、私有数据库访问或专用 wire 操作，
都应先重新审视扩展点，而不是以兼容补丁绕过边界。
