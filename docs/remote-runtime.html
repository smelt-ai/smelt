1. 目标与非目标

目标

  • smeltd 成为运行时：项目、会话、终端、ACP、git、文件、智能体、自动化都归它管。
  • 运行时可以无头跑在 Linux 上（x86_64 / aarch64），不依赖 GUI 拉起。
  • 桌面 GUI 和手机 App 都是客户端，说同一套协议。
  • 一个桌面窗口可以同时挂多个运行时，例如本机 Mac 和一台 Linux 开发机。
  • 本机和远程走同一条代码路径：本机运行时也只是一个恰好在本地的运行时。

非目标

  • Linux 桌面 GUI。
  • 任何跨运行时的操作：把会话拖到另一台机器、跨机 agent 互发消息、跨机搜索。
  • 多人共用同一个运行时。模型仍然是「一个用户，多台设备」。
  • 离线编辑：运行时掉线时，它名下的内容只读。
  • 在远程路径上「用本机 IDE 打开」。以后另议，见第 15 节。

2. 现状：拆了一半

smeltd 实际上已经是运行时了：它持有全部 PTY、ACP 会话（每个对话一个 session host 子进程）、自动化与 webhook、EventHub（落在 SQLite 的 outbox 与游标）、手机网关和 iroh 隧道。GUI 通过 ~/.smelt/smeltd.sock 上的首帧 op 协议（smelt-core/src/daemon_protocol.rs，约 40 个 op）和版本化的 Control API（control_api.rs）和它通信。

问题出在 GUI 在进程里直接做的那些事。运行时一旦换到另一台机器，这些都会失效：

另外三处结构性问题：

  • 鉴权只适用于本机。大多数 op 只靠 socket 文件权限 0600（smeltd/src/main.rs 的 secure_daemon_socket），也就是「同一个用户」；只有 event_subscribe 额外认对端进程身份：macOS 上是签名身份，Linux 上是 SO_PEERCRED 加「与 smeltd 同目录的二进制」（smeltd/src/protocol/auth.rs、protocol/subscribe.rs）。两者都要求对端在同一台机器上。
  • 两套协议。桌面直接说 op 协议；手机说 gateway 自定义的 JSON-WebSocket（smelt-remote-gateway/src/lib.rs），由 gateway 翻译成 op。同一件事维护两份。
  • 生命周期归 GUI。smeltd 由 GUI 拉起、升级，菜单栏只在 GUI 拉起时（SMELT_MENUBAR）才启用。没有 launchd 或 systemd 单元。
已经有雏形但没接上的接缝：smelt_core::fs::FileSystem 和 smelt_core::subprocess::Subprocess，注释里写明了是为「远程或沙箱执行环境」准备的。目前只有 smelt-git 和 session_history 用到它们。它们适合留作运行时内部的抽象，不适合直接搬上网络，原因见 D4。

4. D1 运行时与客户端的边界

判断标准只有一条：换一台设备来看，这份数据还应不应该一样？应该一样的就属于运行时；每台设备可以不同的就属于客户端。

数据 / 能力归属说明
项目列表、会话分组（project、session_group）运行时项目路径只在那台机器上存在。手机端的 listWorkspace 本来就需要它。

分屏树与尺寸（layout_node）、当前标签、折叠、侧栏宽度客户端手机没有分屏；两台桌面完全可以不同。存储键改为 (runtime_id, group_id)。

系统通知、Dock 角标、状态栏图标客户端运行时只负责产生「需要关注」事件；呈现由各客户端自己做，并汇总所有运行时。

5. D2 一套协议，两种传输

协议分两层：连接和消息。

连接层

现有协议的本质是「一条连接 = 一个操作」：首帧 JSON 带 op，之后要么一问一答，要么变成长流（open/watch 是 PTY 字节，acp_watch 是快照流，event_subscribe 是事件投影流）。这个模型保留不动。两种传输都能原生提供「很多条独立连接」，所以不需要自己做多路复用：

传输一条连接是用于
unix socket一条 socket 连接，和今天一样本机：GUI、CLI、hook、MCP 适配器
iroh一条 QUIC 双向流。运行时直接接收 iroh 流，交给和 unix socket 同一个分发器，不再经过回环 TCP 和 gateway 转一道所有远程：桌面连 Linux、手机连任何运行时
决定
  • 远程只用 iroh，不用 SSH。桌面和手机走同一条远程路径、同一套鉴权（D3），只维护、测试一种。iroh 隧道、配对、打洞、relay 回退都已经在用。
  • iroh 能穿过 NAT：同一局域网或有公网地址时直连，否则先打洞，失败再走 relay。家里或办公室里没有公网地址的 Linux 机器也能连上，这一点 SSH 做不到。
  • 运行时不新增 TCP 监听端口，只有 iroh endpoint，符合 control-api.md 里「不轻易加网络服务」的约束。
  • 每个操作开一条 QUIC 流，流之间互不阻塞，终端输出不会把文件读取堵在后面（队头阻塞）。
  • 默认使用 n0 的公共 relay 和 DNS 地址发现，即 iroh 的默认预设，替换现在的 Minimal（smelt-iroh/src/lib.rs:165-172）。这样跨网连接开箱可用，运行时 IP 变了也能重新找到它。数据端到端加密；n0 看得到的是元数据：DNS 发现会公布每个 endpoint id 当前的地址，relay 看得到哪两个 endpoint、什么时候、流量多大。设置里仍然可以换成自建 relay（iroh-relay-deployment.md）。

iroh 流怎么接进现有分发器

smeltd 现在是「每条连接一个线程」的同步模型：listener.incoming() 之后 thread::spawn（smeltd/src/main.rs:2395-2407），约十个处理函数直接拿 UnixStream，对端身份也是从这个 socket 上读出来的。iroh 是 tokio 上的异步 QUIC 流。

做法：每接到一条 QUIC 流，就建一对 UnixStream::pair()，由一个 tokio 任务在 QUIC 流和其中一端之间搬数据；另一端交给现有分发器，同时在进程内附上这条连接的 Principal（D3），不再去读对端进程身份。现有处理函数一行都不用改；回压沿着 socketpair 自然传回 QUIC 的流控。

不选 SSH：它要求机器能被直接 SSH 到（或配好跳板），还要处理用户各自的密钥、~/.ssh/config、服务器是否允许转发，而且鉴权会多出一套（转发过来的对端是 sshd，过不了现有的进程身份检查）。SSH 只在首次安装时由用户手动用一次，见 D7。只能经跳板机进入、UDP 出不去的内网是唯一的例外，见第 15 节。

消息层

  • 继续沿用首帧 op 分流，加上 Control API 的 JSON-RPC 风格信封。短请求统一收进 Control API，长流保留各自的 op。这正是 control-api.md 已经定下的分工。
  • system.describe 增加返回 runtime_id、运行时版本、平台、能力清单。客户端据此决定显示哪些功能，例如 Linux 上没有菜单栏、额度查询暂时不可用。
  • gateway 的 JSON-WS 废弃。运行时直接接收 iroh 流（见上），gateway 的翻译层随之删除。
  • 编码：控制和事件消息用 JSON，PTY 数据用现有的二进制帧 [type][u32 len][payload]，图片和大文件走分块。
  • 不区分管理面：remote_*、iroh_*、upgrade、shutdown、设备管理和其它操作一样，本机连接和已配对设备都能调用（见 D3）。

终端输出的流控

原来服务端把 PTY 字节原样推给每个客户端，积压超过 8MB 就把这个客户端摘掉。远程链路每秒只有零点几到一两 MB，刷屏时每秒能产生几十 MB，所以一刷屏必断，重连再拉一份约 1MB 的快照。实测（Mac 到洛杉矶，n0 公共 relay）：刷屏几秒内被摘，只收到 1.3MB；快、慢两个客户端看同一会话时两个都被摘。

决定
  • 按客户端确认做流控，跟不上就合并成关键帧，不断开。这是 tmux（慢客户端丢积压、稍后整屏重画）和 muxy（一帧在途 + 合并）的同一思路。不选 SSH、VS Code 那种背压：它会让程序被最慢的客户端拖住，而同一会话常常有本机、远程桌面、手机同时在看。
  • 客户端每解析完一批输出就回确认：上行帧 type 2，载荷是从快照第一个字节起的累计字节数（u64 BE）。写端只保留最新值，排队中的多次确认合并成一帧。
  • 服务端限制「已发出、未确认」的实时输出 ≤ 512KB。超了就不再发给这个客户端（合并）；它确认到只剩 ≤ 128KB 在途时，补一帧当前屏幕；完全追平后，再补一帧带滚动历史的，把合并期间跳过的内容补回来。关键帧本身不占窗口，否则补一次完整历史就会把紧随其后的输出挤成合并。
  • 关键帧 = 几何标记 + RIS（ESC c）+ 现有的附着快照。RIS 让客户端回到全新终端的状态，所以关键帧可以随时插进字节流，效果和重新附着完全一样。客户端的终端解析和渲染不用改。
  • 只读的旁观连接（watch）不回确认，仍按 8MB 邮箱上限兜底。
  • 本机 unix socket 确认几乎即时，在途远到不了窗口，平时行为和原来一致；只有程序输出比桌面解析还快时才会合并，原来那种情况同样会被断开。

暂不做、各自单独评估的：下行也改成分帧并下发事件帧（通知、响铃、剪贴板），等 P4 手机需要时再做；终端查询（光标位置、设备属性等）改由服务端统一应答，它顺带修掉「两个客户端同时附着时重复应答」的老问题，但和这次无关；客户端只画行的瘦客户端（muxy 的做法），以后要做也可以在分帧协议上加一种行帧。

实测（合并后）：刷屏的各个场景都不再断开、都看到结尾；刷屏时另一个会话的回显稳定在 170–210ms；快慢两个客户端同看一个会话也都不断开。这次测量的连接被 Surge 带上了一条带宽极差的直连路径（见第 15 节），速度数字不可比，换稳定路径后要重测。

对话快照的增量同步

对话会话的长连接原来每帧都把「当前回合」整段重发：正在流式增长的那条消息每长一点就全文重发一遍，工具调用的输出也跟着反复发；每帧还原样带着约 1.5KB 的快照头。本机 socket 看不出来，远程链路上传输量随回复长度平方增长，远远落后于生成。

决定
  • 连接两端各持一份整帧镜像（smelt_model::acp_wire::FrameMirror），双方用同一个 apply 演进，不会漂移。发送方的镜像记着「对方手里有什么」。
  • 只发变化：快照头按 live.*、snapshot.* 逐字段比，没变的不发；变了的字段和变了的条目都按序列化后的 JSON 求公共前缀，只发「保留前几个字节 + 新尾巴」。正文、工具输出、子代理记录在哪里长都是同一个机制。
  • 线路上两种帧：整段帧（附着时的首帧、Refresh 之后的帧，形状不变）和增量帧 {"delta": …}。接收方还原出完整的快照帧再照常解析，视图和 ConversationSnapshot 不变。
  • 同步规则：接收方镜像接不上增量帧时这一帧作废；桌面客户端随即发 Refresh，守护交接后接手的读端由父进程要整段帧。Refresh 由收到它的守护自己答，不转给宿主。

实测（Linux，一条 300 片、正文 0.02MB 的流式回复）：线路字节 1.36MB → 0.45MB（只发条目增量）→ 0.07MB（快照头也只发变化）；按真实节奏生成 7.5 秒的回复，从 48.6 秒收完变成 7.86 秒；约 1MB 的极快回复从 64 秒变成 5 秒。时间这几行最后一次走的路径比前几次好，线路字节和链路无关。

协议客户端：桌面和手机共用一份 Rust 实现

决定
  • 新建 smelt-runtime-client crate，桌面 GUI 和手机共用：连接器、带类型的调用、流的解码、断线重连都只写一份，协议改动只改一处。
  • 手机侧，现有的 smelt-mobile（flutter_rust_bridge 外壳）改成包一层 smelt-runtime-client，把调用和流以 FRB 的 async 函数和 Stream 暴露给 Dart。今天「Rust 在 127.0.0.1 开端口、Dart 自己说 WebSocket」的做法删除，Dart 不再解析任何协议。
  • 依赖约束：smelt-runtime-client 必须能编进 iOS / Android，所以不能依赖 GPUI、smelt-store（移动端不编 native SQLite），也不能依赖桌面专属的东西。unix socket 连接器放在桌面一侧的 cfg 或 feature 后面；iroh 连接器两边共用。
  • 代价：Flutter 侧要把现有的 WebSocket 客户端（ACP 会话、终端流、工作区列表等页面的数据层）整体换成 FRB 接口，是 P4 的主要工作量。

6. D3 鉴权：按设备，不按共享 token

只认「是不是自己的设备」，不分权限。连上的客户端拥有全部能力，和今天本机桌面一样。原因：能开终端或给 agent 发消息，就等于拿到了 shell，再细分「可写」「管理」挡不住一台被冒用的设备，只会多出一套开关和状态。真正的安全边界是配对本身，以及丢失后能立刻撤销。

每种传输各自有一个鉴权器，产出同一种 Principal { kind, device_id }。device_id 只用于撤销、日志和「最近操作的客户端」这类区分（例如终端尺寸，见第 15 节），不参与授权判断。

传输怎么认
unix socket和今天一样：socket 文件 0600，event_subscribe 另认对端进程身份
iroh配对时把对端的 endpoint id 记进运行时库的 paired_device 表，之后只认白名单。QUIC 握手本身证明了对端持有该 endpoint 的私钥
配对一台设备 = 给它这台机器上你这个用户的 shell 权限。设置页和 smeltd pair 的提示里都要这样写明。
  • 配对串：smelt+iroh://<endpoint_id>/?code=<一次性码>[&relay=…]，在现有格式（smelt-pairing）上把长期 token 换成一次性码。默认用公共 relay 和地址发现，只有 endpoint id 就能找到运行时；只有用了自建 relay 时才带上 relay 参数。码用一次、或者过了几分钟，就作废。
  • 配对流程：新设备按 endpoint id 连上运行时，此时它还不在白名单里，只能调用 pair 这一个操作，提交一次性码；码对了，运行时把这台设备的 endpoint id 写进 paired_device，之后才放行其它操作。其余所有操作对未配对设备一律拒绝，连 system.describe 也不例外。
  • 配对串从哪来：本机 Mac 运行时在桌面设置页生成（二维码给手机扫）；Linux 无头运行时用 smeltd pair 在终端打印配对串和终端二维码，桌面粘贴、手机扫码。
  • 现在 ~/.smelt/remote-token 那个长期共享的 bearer token 删除，架构评审里它本来就是 P0。全局的 write_enabled 只读开关也删除，连上即全部权限。
  • 设置页（以及 smeltd devices）列出已配对设备和最近连接时间，可以单独撤销；撤销时立即断开该设备现有的全部连接。

7. D4 运行时 API：只提供业务能力

现在 GUI 在自己进程里直接读写磁盘、起子进程、开 SQLite（第 2 节）。运行时一旦在另一台机器上，这些都要改由运行时提供。这一节定的是以什么形状提供。

业界的两种做法

做法代表接口长什么样为什么这样选
通用文件系统接口VS Code Remote / Codespaces、Theia、JupyterVS Code 服务端提供按 URI 读写的远程文件系统，搜索和文件监听在服务端，扩展整体跑在服务端。Jupyter 的 Contents API 是限定在根目录内的文件增删改查，保存时带 last_modified 判断冲突。有开放的扩展生态。成千上万的第三方扩展都按「文件」编程，产品没法替它们一个个定义业务接口。
按项目和领域定义接口Zed 远程开发、JetBrains GatewayZed 的服务端负责目录扫描、git、LSP、任务，协议里是项目级的消息：目录树增量更新、按路径打开 buffer、带版本号保存、项目搜索，没有 read / stat 这类调用。JetBrains 更进一步，后端连界面模型都同步过来，客户端只渲染。功能都由自己掌控。粗粒度接口延迟低，规则只写一份，多端一致和协作都容易做。
决定

smelt 走第二种。功能基本都是自己写的，还有一个跑不了业务逻辑的手机客户端。唯一的开放生态是 gpui-shell 插件，单独处理，见 D8。

协议原则

  1. 只提供业务能力，不提供通用原语。不暴露文件系统、执行任意命令、SQLite 访问。每个方法对应一个业务动作，业务规则在运行时里执行。例如 git 暴露 git.status、git.commit，不暴露 run_git。
  2. 计算放在数据旁边。搜索、git、目录扫描、历史扫描都在运行时跑，客户端只拿结果。一个界面动作一次往返。
  3. 状态靠推送，不靠逐个请求。先给一份快照，之后通过 event_subscribe 的主题推增量；断线重连后重新取快照对齐。客户端不轮询。
  4. 保存做乐观并发控制。带上读取时的版本，文件在这期间被改过（多半是 agent）就拒绝写入，不悄悄覆盖。
  5. 路径以项目或会话为范围。参数是「某个项目里的某个文件」，不是这台机器的任意路径。少数天然越界的场景逐个定规则，见下文。
  6. 版本和能力协商。system.describe 带方法清单；协议只做增量变更，手机版本会错位（D7），客户端按清单决定显示哪些功能。
不选通用文件系统接口，原因不是安全：连上的设备本来就拥有全部权限（D3）。原因有三个：
  • 延迟：把 smelt_core::fs::FileSystem 搬上网络，展开一层目录、做一次搜索就是上百次往返，走 relay 时每次约 100ms。
  • 一致性：ignore 规则、大小上限、保存冲突会散落在每个客户端里，桌面和手机各写一遍、各有偏差。
  • 手机：手机端只能做展示，必须拿到现成的业务结果。
代价：界面加功能时，协议往往也得加方法。方法按领域对象来定，不按控件来定，避免变成一个按钮一个接口。

9. D6 RuntimeId 与多运行时

  • runtime_id：运行时第一次启动时生成一个 UUID，存在运行时库里，之后永久不变。它和传输无关：socket 路径、iroh endpoint id 都只是「怎么到达它」。
  • runtime_connection（客户端库）：runtime_id、显示名、排序、传输配置（local { socket } 或 iroh { endpoint_id, relay? }）。桌面自己的 iroh 身份密钥也存在客户端这一侧。
  • 客户端里凡是指向运行时实体的键，都改成 (runtime_id, entity_id)：视图路由、焦点、布局、未读、通知跳转。
  • RuntimeHub（GPUI Entity）：持有 N 个 RuntimeClient。每个客户端独立连接、独立退避重连、独立做版本协商，状态是 connecting、online、offline、incompatible 之一。所有 UI 都从 Hub 的缓存里读。
  • 离线：该运行时的项目灰掉并标「离线」，只保留内存里最后一次的快照，只读。重连后重新拉快照、再重新订阅，和今天桌面的做法一样：桌面的事件订阅是临时的，每次随机生成订阅 id，不带游标（smelt-core/src/daemon_state.rs:560-580）。「需要关注」是状态而不是事件流，拿到最新快照就够了，不需要按设备持久化游标。
  • 界面：侧栏在项目上面加一层运行时分组；只连本机时这一层不显示，单机用户看到的界面和今天一样。通知和角标汇总所有运行时，点击直接跳到对应运行时的会话上。
现在 GUI 里有二十来个 impl Global，例如 RemoteSessionCatalogGlobal、AcpRuntimeState、DaemonStatesSubscription。凡是跟具体运行时相关的，都要挪进 Hub 里按运行时管理；纯客户端的（外观、窗口句柄）继续保留为全局。

10. D7 生命周期与升级

  • 运行时独立存活。在 Mac 上，GUI 仍然可以替用户安装、启动本机运行时，但要通过一个和远程共用的「运行时管理」接口，不再在 terminal.rs 里直接管理进程。
  • Linux 首次安装（唯一需要用户自己 SSH 登录的一步）：一条命令装好，见下面的「决定：一键安装」。装完运行时以 systemd --user 服务常驻，开着 iroh，打印配对串。
  • 升级：运行时自己完成交接，复用现有的 handoff_v2。触发方式是 runtime.upgrade。
  • 版本错位：桌面不会错位，手机会。桌面每次连上就对齐版本（见下面的决定），所以桌面只依赖冻结契约。手机走应用商店，更新节奏不受控，它和运行时之间的错位是常态：运行时要接受上一个版本的手机客户端，手机也要能面对更新的运行时。办法是协议只做增量变更，新能力靠 system.describe 的能力清单探测；真不兼容时标成 incompatible，提示更新 App。
  • system.describe 和 runtime.upgrade 是冻结契约：永远不改形状，incompatible 状态下也必须能调用。否则版本一旦错开太多，就连升级都发不过去，只能让用户重新 SSH 上去手动装。
决定：桌面推送
  • 桌面连上运行时，发现运行时版本比自己旧，就通过 runtime.upgrade 把匹配平台的二进制分块传过去（带校验和），运行时校验后用 handoff_v2 交接。本机 Mac 运行时也走这条路，和今天「GUI 带着 smeltd 升级」是同一回事。
  • 桌面安装包附带 linux x86_64 / aarch64 两份 smeltd。
  • 只升不降：运行时比桌面新时，桌面不推送，把该运行时标成 incompatible 并提示更新桌面。两台不同版本的桌面连同一个运行时时，运行时最终跟随较新的那台。
  • 交接期间所有客户端都会断开一次，按普通断线重连处理。推送前在界面上提示，有 agent 正在跑时等用户确认。
  • 不做运行时自更新（updater.rs 的发布渠道）。代价：只用手机、从不连桌面的运行时不会自动升级，只能重新运行安装脚本。
决定：一键安装
  • 安装包发布在 GitHub Release：每个版本附 smeltd-<版本>-linux-x86_64.tar.gz、…-linux-aarch64.tar.gz 和校验和，各在对应架构的 Linux 机器上原生构建（ci/linux/ci.sh package），不交叉编译。
  • 一条命令：curl -fsSL <Release 地址>/install.sh | bash。脚本按 uname -m 下载对应的包、核对校验和，再走现有的 install.sh（装到 ~/.smelt/bin、smeltd install、smeltd pair）。
  • 只在必须时用 sudo：开 loginctl enable-linger、装系统包。没有 sudo 就照旧提示，运行时本身不需要 root。
  • 不依赖额外的系统命令：准备受管 Pi 运行时现在要调用系统的 unzip，全新 Debian 没有，改成 smeltd 自己解压。
  • 可选组件 --with-desktop：装远程桌面和常驻浏览器，见 D9。
  • 模型和密钥不进安装脚本：装完在桌面能力库里配，能力库按运行时切换（P2 第 5 步）。

11. D8 插件放在哪一侧

部分运行在改动
插件（gpui-shell + QuickJS，跑在 UI 线程）客户端脚本和界面都在客户端。插件 API 本来就是异步的（官方 fs/promises、smelt-fs 都返回 Promise），不存在同步改异步的问题。

真正的问题是插件操作的是哪台机器的磁盘。技能插件用官方的 fs/promises 读写目录（plugins/skills/core.js:10），它直接读客户端本机的磁盘；smelt-workspace.pick_directory 弹的也是本机的选择框。而我们定了不 fork gpui-kit，没法把官方模块改道到运行时。可选做法：

  • B. 插件只作用于本机运行时：当前选中的是远程运行时时，插件面板不可用并说明原因。改动很小。
  • A. 插件的文件操作全部走宿主模块：smelt-fs 补齐读、写、列目录、建删目录，并按当前运行时转发到运行时给插件单独定的一组文件接口。这组接口限定在插件自己声明的目录内（例如技能插件的 ~/.claude/skills），不是通用文件系统，也不给第一方界面用（D4 原则 1）；连远程运行时时用 Policy 拒绝官方 fs，避免误读本机；技能插件整体迁到 smelt-fs。pick_directory 改用运行时目录浏览器（见 P1）。
决定

P1 到 P3 先做 B，P3 之后再做 A。技能插件管理的 ~/.claude/skills 等目录在运行时那台机器上，做 A 时指向运行时的 home 是对的。

12. D9 远程桌面：agent 用浏览器，人看整块屏幕、可接管

Linux 运行时的一个主要用途是当个人助理：上面常驻一个 Chrome，agent（例如 Pi）用它查机票、填表、看后台；遇到验证码、二次验证、付款确认，人随时接管，处理完交还。浏览器用一个持久的用户目录，人登录过的网站 agent 直接沿用登录状态。

机器没有显示器也可以：TigerVNC 的 Xvnc 本身就是一个只在内存里的 X 服务器（取代 Xvfb），上面跑 XFCE 和有界面的 Chrome。不用 --headless，部分网站能识别出 headless，登录时更容易被风控。

决定：agent 经 CDP 用浏览器，人经 VNC 看整块屏幕
  • 人看的是整块屏幕，不只是网页：先做过「只推网页」（smeltd 当 CDP 客户端，Page.startScreencast 推画面、Input.dispatch* 转输入），对着真 Chrome 跑通了，但 Chrome 自己的界面（标签栏、地址栏、权限气泡、系统文件框）和别的程序都看不到，已整套删除。
  • 画面走 VNC：业内 agent 沙盒（Daytona、E2B、Bytebot、Cua、Anthropic 的 computer use 示例）都是虚拟屏幕 + XFCE + VNC + 网页版 noVNC，人看和接管走 VNC，agent 的操作接口另走一条。WebRTC（neko、Selkies）画质好，但要视频编解码和打洞/TURN，不做。
  • 运行时只转发不解析：新连接 desktop_attach 回 ok 之后就是到本机 VNC（127.0.0.1:5999）的原始 RFB 字节流。VNC 只听本机，外面只能经过运行时，也就是只有配对过的设备能连；走现有的 iroh，不另开端口。
  • 客户端用网页视图里的 noVNC：smelt-runtime-client 在 127.0.0.1 的随机端口开转发口（websockify 的角色），提供 noVNC 页面，把页面的 WebSocket 换成 desktop_attach；WebSocket 必须带启动时生成的令牌、来源必须是这个口自己的页面。noVNC 用 Debian 包里的 1.6.0，编进二进制，桌面和手机共用。桌面用 gpui-wry 0.7.3（默认跑在 gpui-pre 上，不引入 GPUI Fast）。
  • 中文另走一条：VNC 只能逐键发，本机输入法拼出来的字过不去。页面下方有输入框，文字整段交给 desktop.type_text，运行时用 xdotool 注入到当前聚焦的窗口（对键盘上没有的字临时改一个空闲键码的映射），远端不用装输入法。
  • 默认只看：点「接管」才把鼠标键盘交给远端，「交还」后又只看。这个开关在客户端：能连上的都是配对过的设备，本来就有完整权限。
  • 进程交给 systemd：浏览器不做 smeltd 的子进程，smeltd 会经常无缝升级。三个系统服务，都以普通用户运行：smelt-display（Xvnc :99，1440×900，只听本机 5999）、smelt-desktop（XFCE 会话）、smelt-chrome（调试端口只绑 127.0.0.1:9222，--password-store=basic）。
  • agent 控制：Pi 用 Playwright MCP 的 --cdp-endpoint 连本机 9222，和人看的是同一个 Chrome。

实测（2026-10-18，gs-wynn，Debian 13 / 4 核 / 8GB）：

  • Pi 用浏览器在 Google Flights 上查「台北 → 东京、10 月 30 日、单程」，2 分钟报回最便宜的 3 个直飞航班，和页面截图逐项一致。
  • 换成 Xvnc + XFCE 后，Chrome 自己的界面（包括「恢复页面」气泡）都在画面里；xdotool 往地址栏注入「北京 天气 abc」正常上屏。
  • 整条链路：本机转发口 → 运行时 desktop_attach → Xvnc → noVNC 出画面（在远端的 Chrome 里打开转发口页面，看到自己套着自己）。
  • 系统包：tigervnc-standalone-server xfce4 xfce4-terminal dbus-x11 xdotool fonts-noto-cjk，都在 Debian 官方源里。不装中文字体，中文网页全是方块。

还要做的，按顺序：

  1. 安装：install.sh --with-desktop 装系统包、写三个 systemd 服务、把「本机 Chrome」写进 Pi 的 mcp.json。现在 gs-wynn 上是手写的服务文件。
  2. 交接：Pi 遇到登录、验证码、付款时，用现有的「问用户」工具请人去远程桌面接管，人回答后接着办。运行时有远程桌面时给 Pi 加一段说明。
  3. 能力库按运行时切换（P2 第 5 步），远程运行时的 Pi 模型、密钥、MCP 能在桌面上配。
  4. 手机：Flutter 的网页视图打开同一个转发口（随 P4）。
  5. 安全前提（正式用之前）：Xvnc 加 X 鉴权（现在本机任何进程都能连那块屏幕）；smeltd 不用 root 跑；中继加白名单。
这台机器存着人的各种登录状态，保存的密码和 cookie 在磁盘上只是弱加密（--password-store=basic），机器本身的安全就是这些账号的安全。

所有客户端都不在线时 agent 需要关注漏掉提醒已知限制：手机没有推送（没有接 APNs/FCM），没有人在线就没人收到提醒。运行时保存关注状态，客户端上线拉快照后立刻显示。以后可以用路线图里的飞书卡片补上这个缺口。
多个客户端同时看同一个终端PTY 尺寸互相打架现在手机连上会按自己的视口改共享 PTY 的尺寸。规则定为「最近一次有输入或聚焦的客户端说了算」，其他客户端按这个尺寸显示。
慢客户端拖住别人（走 relay 时大量终端输出）其他客户端卡顿已解决 每个客户端有自己的写队列，PTY 读取和其他客户端本来就不受影响；跟不上的客户端改为按确认合并成关键帧，不再断开（见 D2「终端输出的流控」）。在 n0 公共 relay 上测到的「刷屏时另一会话回显卡 10 秒」是 relay 限速排队造成的，换自建 relay 后回显不受刷屏影响。
插件读写的是客户端本机磁盘（D8）远程运行时上插件不可用先只支持本机运行时，P3 之后让 smelt-fs 转发到运行时给插件单独定的、限定目录的文件接口（D8）。
默认依赖 n0 的公共 relay 和 DNS 发现n0 服务不可用时跨网连不上；n0 能看到连接元数据；公共 relay 限速已接受：内容端到端加密。同网时仍然直连；在意元数据或要保证可用性的用户改用自建 relay。
实测 Mac（台湾）到洛杉矶的 Linux，同一套基准：n0 公共 relay 吞吐 0.19MB/s、控制往返 450ms–1.2s、1MB 重连快照 4.25s；在那台 Linux 上自建 relay（iroh-relay 1.2.0 + Let's Encrypt）后吞吐 0.5–1.6MB/s、往返 320–360ms、快照 0.37s。打洞失败时 relay 是常态而不是例外，公共 relay 的限速会直接变成终端体验。smelt-iroh/src/lib.rs 注释写着「Smelt 不提供默认值」，与实际默认走 n0 不一致，要么改注释，要么改默认，待定。
客户端开着 Surge、Clash 这类增强模式（TUN）打洞失败，或者走上一条很差的路径实测 Surge 增强模式接管 UDP：Mac 侧变成对称 NAT，UDP 和 TCP 的出口 IP 都不一样，打洞失败、一直走 relay。另一次 iroh 打通了「直连」，对端看到的地址是某个代理节点（RTT 168ms），但带宽极差，1MB 快照要 96 秒：iroh 按延迟挑路径，不看带宽。国内用户开增强模式很常见。倾向：文档里写明给 Smelt 设 UDP 直连规则或排除出增强模式；路径选择是 iroh 上游的限制，暂不自己做。
公司内网封了 UDP 出口，或者机器只能经跳板机 SSH 进入iroh 直连和公网 relay 都连不上先在内网自建 relay。还不行，再评估把 SSH 加成第二种远程连接器；连接器接口（P0）留着这个口子，但现在不做。
