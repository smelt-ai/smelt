smelt Pi 运行时单二进制技术方案

日期：2026-10-20（Asia/Taipei） · 受众：smelt 仓库维护者（Rust smeltd + Pi agent） · 状态：已按下面的「落地差异」实现。原稿里和实现不一致的地方以那一节为准
项目： smelt-ai/smelt · 依据：2026-10-20 在 Linux x64 上用 Bun 1.4.0 baseline 对 packages/pi-agent 做的 bun build --compile 实测
单个 Bun 二进制 首启不安装 随 app 签名发布 Mac 签名尚未实测

0.落地差异

这一节是已经进仓库的行为。下面各节是当时的方案，和这里冲突时以这里为准。

  • 编译命令是 bun build --compile --bytecode --format=esm --splitting --no-compile-autoload-dotenv --no-compile-autoload-bunfig。 Bun 1.4.3 上图片 worker 和 codemode worker 的冒烟都过了。 Bun 1.4.0 上拆块之后，图片 worker 里的 photon 绑定变成 exports_photon_rs is not defined，1.4.3 没有这个问题。 ./src/...worker.ts 在 bunfs 里仍然是 Cannot find module，所以编译时还是把这两条说明符改成 /$bunfs/root/...。
  • Bun 不打进应用，也不用 BUN_BE_BUN。MCP 预设的 bun x 和 Claude/Codex 的 bunx 仍用按需下载的 Bun 1.4.3：~/.smelt/runtime 下的 generation（store、current、leases、staging）就是它的家，这些目录不能当成旧运行时清掉。 ~/.smelt/runtime/bin/bun 指向当前 generation。
  • smelt-pi、photon_rs_bg.wasm 和 native/ 按这一整套自己的指纹发布成 ~/.smelt/bin/smelt-pi-<指纹>/，~/.smelt/bin/smelt-pi 链接指向当前那份。和守护映像的指纹无关：只换了 Pi 不用等守护交接。 桌面每次启动从 App 里发布一次，Linux 由 smeltd install 发布。守护起 Pi 时解析链接、exec 真实路径，已经在跑的 Pi 不受换链接影响。没有别的查找路径，也没有环境变量覆盖。
  • photon_rs_bg.wasm 是可执行文件旁边的 sidecar，不打进 bunfs。QuickJS wasm 由静态 import 嵌进二进制。
  • 签名用的 plist 在 scripts/entitlements.plist 和 scripts/jit-entitlements.plist。 没有 ci/ 目录。
  • 会话文件按 cwd 目录名加文件名里的会话 id 定位（session_history::pi_sessions_dir，展开 ~，认 PI_CODING_AGENT_DIR）。 启动前读一遍只为了尽早发布模型名。握手和分叉完成之后、发出 Ready 之前再读这一份来重放。 文件找不到或解析失败就向 Pi 要 get_entries 并记一条日志；两边都失败则恢复失败，不显示空转录。 只有文件头的空会话是真正的空转录。分叉切点在 Pi 里对不上仍是错误；不再在本地把整段历史留下来冒充分叉结果。
  • 模型在拉起进程之前就发 ConversationEvent::Model：恢复时用文件里的最后一次模型，否则用启动参数，再否则用设置里的默认模型。 消息上的 provider 用条目自己的 provider 字段，不把 model id 按 / 切开。 get_state 和 set_model 之后再各发一次，后到的盖住先到的。不用未确认点击那层 overlay。 转录重放完才发 Ready，避免 awaiting_user_echo 吞掉用户消息。不写 ~/.pi/agent/settings.json。

下面的体积和耗时是这台 Linux x64、Bun 1.4.0 baseline 上的实测。 用户在 Bun 1.4.3 上量过：源码 RPC ready 339ms，只 --compile 316ms， --compile --bytecode --format=esm 约 95ms；再加上 --splitting 热启动约 89ms→82ms、冷启动 136ms→124ms。 发布构建用 Bun 1.4.3，并带 --splitting。上面的体积和耗时仍是 1.4.0、不拆块时量的，不是这次的数字。

1.背景与目标 / 非目标

1.1 现在怎么跑

Pi agent 的源码在 packages/pi-agent（@smelt-ai/pi-agent），依赖 @earendil-works/pi-coding-agent、pi-ai、pi-mcp 1.1.0 和 proper-lockfile。crates/smelt-core/build.rs 把入口、扩展、 package.json 和 bun.lock 嵌进二进制。首次准备时， managed_runtime.rs 在 ~/.smelt/runtime/store/pi/<generation>/ 用受管 Bun 执行 bun install --frozen-lockfile --production --ignore-scripts。 Bun 自己放在 ~/.smelt/runtime/store/bun/<generation>/，稳定入口是 ~/.smelt/runtime/bin/bun。会话持有两份 generation lease，并把 lease FD 继承给子进程。

这条路的代价是首启要下载 Bun、解压、再装一整棵 node_modules（production 安装实测 170MB、124 个包）， 还要维护 generation、staging、lease 和文件嵌入表。运行时目录被回收之后，按 import.meta.url 再去读磁盘的 OAuth 刷新会 ENOENT，所以现在启动时还要静态注册 OAuth flow。

1.2 为什么不再用首启 bun install

依赖已经能在发布时打进一个可执行文件，Bun 运行时也在里面。首启安装解的是发布机上就能确定的东西： 锁定的 npm 树和 Bun 本身。把它留到用户机器上，多一次网络、一次磁盘事务、一套租约，换来的运行结果和编译后的二进制相同。 实测里，编译产物在没有旁边 node_modules 的临时目录里完成了 get_state、扩展加载和 MCP 网关健康检查。

1.3 为什么不再用 tar.gz（PR #52）

草稿 PR #52（分支 cursor/pi-runtime-archive-e544）试过把装好的运行时预先打成 tar.gz，首启只解压。 这个方向已经放弃，#52 已关闭，由本方案取代。main 上没有那套代码。它仍然是「用户机器上展开一棵运行时目录」：解压、generation、lease、 磁盘上的 node_modules 都还在，只是把 bun install 换成了解包。 编译方案把代码和 Bun 收进签名过的 app bundle，首启不下载、不安装、不解压。

Linux 发行物 smeltd-<版本>-linux-<架构>.tar.gz 是另一回事，那是 smeltd 的安装包。 实现时这个包里要带上编好的 Pi 二进制和旁路文件。不要把 #52 的 Pi 运行时归档做进这个包。

1.4 目标

  • 用 bun build --compile 把 Pi 依赖和 packages/pi-agent/src 编成一个可执行文件，按平台随 smelt.app / Linux 包发布并签名。
  • 一个二进制，用子命令区分 RPC、登录、MCP、gateway。子智能体再执行自己。
  • 两个 worker（图片缩放、codemode）作为编译入口嵌进去。QuickJS wasm 嵌进二进制。Photon wasm 和 pi-tui 的 .node 作为旁路文件放在可执行文件旁边。
  • 首启直接运行 bundle 里的文件。~/.smelt/runtime/bin/bun 这个已经写进 mcp.json 的路径改成指向 bundle 的启动器，不再下载 Bun、不再 bun install。
  • packages/pi-agent 继续保留源码、package.json 和 bun.lock，用来锁版本和跑测试。运行时不再把它们嵌进 Rust 二进制再写到用户目录。

1.5 非目标

  • 落地实现做在本 PR，按本文直接替换旧路径。
  • 不保留首启 bun install 作为退路，也不把 #52 的 tar.gz 和编译产物并存。
  • 不在这篇方案里做 macOS 签名或公证。那些步骤写清楚，留到 Mac runner 上验收。
  • 不改 Pi RPC 协议，不改 Smelt 扩展的产品行为。
结论
有条件可行。Pi 1.1.0 的发布包自己就带 build:binary，用 bun build --compile 编官方 CLI，并声明 worker 入口和 photon wasm 旁路。2026-10-20 的实测把同一机制用在 Smelt 的源码上，Linux 上 RPC、扩展、codemode、图片缩放和网关都跑通了。条件是：子命令分流、静态 import、worker 路径、旁路文件、进程不能叫 bun、JIT entitlements。后两项里，签名尚未在 Mac 上验证。

2.设计原则

  1. 直接替换。运行中的 Pi 只从 bundle 里的 smelt-pi 拉起。generation 目录、staging、bun install、源码嵌入表一并删掉，不留「编译失败就退回安装」的分支。
  2. 不打补丁硬撑。pi-mcp-runtime.ts 里用 import.meta.resolve 再动态加载 Pi 内部文件的写法，在编译产物里会在启动时失败。改成静态 import，让打包器收进二进制。不要在运行时再去磁盘上找一份 node_modules。
  3. 外部路径和内部实现分开。~/.smelt/runtime/bin/bun 已经写进用户的 mcp.json（MANAGED_BUN_LAUNCHER_HOME_PATH）。路径字符串留下，因为它是外部配置里的命令。路径后面的下载、generation 和 lease 删掉，改成一条指向当前 bundle 的启动器。
  4. 仓库里的包还在。packages/pi-agent 的源码、package.json、bun.lock 继续是版本和测试的依据。bun run check、bun test、production-smoke 仍对着这棵源码树跑。变的是发布物，不是开发时的包。
  5. 证据先于推断。下面每条架构选择都对应 §3 的实测。Mac 上没跑过的，写成待验证，不写成已经成立。

3.实测依据

环境：Linux x64，Bun 1.4.0 baseline。可执行文件 SHA-256 为 33d56b070be6a9e3da0ab013038b43d1645d0534ca811ecdba4472599117eb4b， 与 managed_runtime.rs 里 Linux x64 的 BUN_EXECUTABLE_SHA256 一致。 依赖用 bun install --frozen-lockfile 装在 packages/pi-agent。 实验代码没有进 main。

3.1 Pi 官方已经按二进制设计

@earendil-works/pi-coding-agent@1.1.0 的 build:binary：

bun build --compile --no-compile-autoload-bunfig --no-compile-autoload-dotenv \
  ./dist/bun/cli.js \
  ./src/utils/image-resize-worker.ts \
  ./src/extensions/codemode/worker.ts \
  --outfile dist/pi

copy-binary-assets 把 photon_rs_bg.wasm 拷到产物旁边。 dist/core/extensions/virtual-modules.js 把 @earendil-works/pi-coding-agent、 pi-ai、pi-agent-core、pi-tui、typebox 和 @mariozechner/* 映到打进去的模块，注释写的是 source and compiled binary runtimes。 jiti-static-loader.js 写明编译后的二进制用 jiti/static。 dist/bun/runtime-setup.js 静态 import quickjs-wasi/quickjs.wasm，并调用 setEmbeddedQuickJSWasmPath。npm 包里没有那些 .ts worker 源文件，实测用同路径的 shim 转调 dist。

3.3 进程参数和子命令

编译产物的 process.argv 实测是：

["bun", "/$bunfs/root/smelt-pi", "hello", "--mode", "rpc"]

argv[0] 是字符串 bun，不是路径。process.execPath 才是真实路径。 import.meta.url 是 file:///$bunfs/root/smelt-pi，Pi 的 isBunBinary 为 true。 第二个编译入口不会变成可选的主程序：小二进制里后一个文件的 SECOND_ENTRY 从未打印。

smelt-pi auth list 退出码 0，列出 42 个 provider，第一个是 amazon-bedrock。 smelt-pi mcp list 在临时 PI_CODING_AGENT_DIR 下退出码 0，输出 No MCP servers configured。

子智能体的 getPiInvocation 已经认识 /$bunfs/root/。二进制名叫 smelt-pi 时， 它再执行 process.execPath，参数里不再带脚本路径。实测子进程 argv 为 ["bun", "/$bunfs/root/smelt-pi", "argv"]。把同一文件复制成名为 bun 的路径后再执行， 会去 spawn pi，结果是 Executable not found in $PATH: "pi"。

网关今天用 fileURLToPath(new URL("./mcp-gateway-main.ts", import.meta.url)) 当脚本路径。 编译后这条路径是 /$bunfs/src/mcp-gateway-main.ts，exists 为 false。 按现有代码 spawn，子进程退出码 1：Cannot find module '@earendil-works/pi-coding-agent'。 改成子命令 gateway 之后，同一二进制可以听端口。

src/pi-mcp-runtime.ts 用 import.meta.resolve("@earendil-works/pi-coding-agent") 再动态加载 ./extensions/mcp/runtime.js。打进二进制后这个包名在运行时解析不到， get_state 和网关都会马上失败。改成对 node_modules/@earendil-works/pi-coding-agent/dist/extensions/mcp/runtime.js 的静态 import 之后，RPC 才通过。

3.4 Worker、wasm、原生模块

  • 在空目录里，带上两个 worker 入口的二进制把 8×8 PNG 缩成 4×4，wasResized: true。不带这两个入口时：Cannot find module './src/utils/image-resize-worker.ts'，退出码 1。
  • codemode worker ./src/extensions/codemode/worker.ts 执行 return 1+1，得到 { ok: true, value: 2 }。wasm 路径在 /$bunfs 里。把二进制拷到没有 node_modules 的目录，结果相同。
  • 把 node_modules 里的 photon_rs_bg.wasm 改名之后：可执行文件旁边有这份 wasm 时缩放成功；旁边也没有时 resizeImage 返回空，退出码 1。测完已把原文件放回。
  • 依赖树里的 .node 只有 @earendil-works/pi-tui 的剪贴板预编译库（Linux x64 18,008 字节，darwin-arm64 52,024 字节，另有 linux-arm64、darwin-x64、win32）。没有 koffi，没有 sharp。quickjs-wasi/extensions/*.so 是 wasm，不是 ELF；1+1 没有加载它们。
  • .node 不会打进二进制。从编译后的进程 require Linux x64 那份，hasGetText: true。文件放在可执行文件旁的 native/linux/prebuilds/linux-x64/linux-platform-x11.node 也能加载。文件不在则 MODULE_NOT_FOUND。darwin 的 .node 在包里，这台机器加载不了。

3.5 扩展、安装命令、RPC

--approve --offline --no-session 下，三份扩展同时加载：用户目录里 import @earendil-works/pi-coding-agent 和 typebox 的 user-ext.ts、 项目 .pi/extensions/proj-ext.ts、自带 package.json 和 node_modules/ms 的 with-deps。ms("2 days") 得到 172800000。 get_commands 返回 spike-proj、spike-user、spike-duration、 llama、mcp、shake、handoff、smelt-codemode。 stderr 为空。--no-approve 按 Pi 的项目信任规则跳过项目扩展，spike-proj 消失。 挪走 with-deps/node_modules 后进程退出码 1：Cannot find module 'ms'。

Pi 安装包扩展时，未配置 npmCommand 就调用 npm。假 npm 记到的参数是： 

npm install ms --prefix <agentDir>/npm --legacy-peer-deps

BUN_BE_BUN=1 ./smelt-pi argv 把智能体入口换成 Bun CLI，报 Script not found "argv"，退出码 1。 只加在子进程上时，--version 输出 1.4.0。 /usr/bin/env BUN_BE_BUN=1 ./smelt-pi install ms --cwd <dir> --omit=peer 装上了 ms@2.1.3。 同一条二进制执行 Pi 传给 npm 的 --prefix <dir> --legacy-peer-deps，Bun 报 Invalid dependency name，退出码 1。 Pi 只有在命令 basename 被认成 bun 时才会改传 --cwd 和 --omit=peer。

RPC 冒烟对应 packages/pi-agent/scripts/production-smoke.ts 的 get_state，工作目录旁边没有 Pi 的 node_modules。 约 406ms，退出码 0，success: true，messageCount: 0，sessionFile: null。 启动时有一条 extension_ui_request（setWidget / smelt-codemode）。 没有配模型密钥，没有发一轮对话。

网关子命令在临时 SMELT_HOME 写下 gateway-v2.json，protocol 为 2。 正确 bearer 的 GET /health 返回 200 {"ok":true,"protocol":2,...,"servers":[],"sessions":0}， 错误 token 返回 401。SIGTERM 后日志是 exiting: SIGTERM。

3.6 交叉编译和签名

bun build --compile --target=bun-darwin-arm64 在 Linux 上成功，日志使用 bun-darwin-aarch64-v1.4.0。file 输出： 

Mach-O 64-bit arm64 executable, flags:<NOUNDEFS|DYLDLINK|TWOLEVEL|BINDS_TO_WEAK|PIE|HAS_TLV_DESCRIPTORS>

在 Linux 上运行该文件：cannot execute binary file: Exec format error。 darwin 二进制的 worker、扩展、签名、公证、.node 加载都没有在 Mac 上做过。 Bun 文档写明这个 target： Single-file executable。 codesign 从 Bun 1.2.4 起可用（我们用的是 1.4.0）： Codesign a single-file JavaScript executable on macOS， 实现是 oven-sh/bun#17207。 文档要求的 entitlements 是 allow-jit、allow-unsigned-executable-memory、 disable-executable-page-protection、allow-dyld-environment-variables、 disable-library-validation。Bun 仓库的 entitlements.plist 含前四项。这些是文档，不是这次的签名结果。

4.1 一个二进制，四条入口

调用谁发起二进制看到的用户参数
RPC 会话smeltd、subagent现有的 Pi 参数（--offline、--mode rpc 等）。没有子命令时进入现在的 src/main.ts
auth登录 UI，今天走 src/auth-main.tsauth list|login|logout ...
mcpMCP 登录，今天走 src/mcp-main.tsmcp list|login ...
gateway第一个要用 stdio MCP 的对话gateway。网关逻辑仍是现在的 mcp-gateway-main.ts

bun build --compile 只有第一个文件是主入口。worker 是另外的入口，不能靠 argv 选成主程序。 分流写在主入口里：先丢掉 argv[1] 的 /$bunfs/root/...，再看第一个用户参数。 main.ts 仍然自己前置 --mode rpc。子智能体传过来的参数里已经有一次 --mode rpc， Pi 的解析以后者为准，重复无害，不必为了这个再包一层兼容。

4.2 编译入口

bun build --compile \
  --no-compile-autoload-bunfig \
  --no-compile-autoload-dotenv \
  ./src/compiled-main.ts \
  ./src/utils/image-resize-worker.ts \
  ./src/extensions/codemode/worker.ts \
  --outfile smelt-pi

两个 worker 路径必须和 Pi 写死的字符串一致：./src/utils/image-resize-worker.ts、 ./src/extensions/codemode/worker.ts（dist/config.js 的 resolveCodemodeWorkerSpecifier，dist/utils/image-resize.js）。 发布到 npm 的 Pi 包没有这两份 .ts。在 packages/pi-agent/src 放同路径文件， 内容只 import dist 里的 worker。这是编译入口，不是运行时去磁盘找源码。

compiled-main.ts 在做任何事之前静态 import "quickjs-wasi/quickjs.wasm"， 并调用 setEmbeddedQuickJSWasmPath。这和 dist/bun/runtime-setup.js 相同。 没有这一步，codemode 会用 createRequire 到磁盘上找 quickjs-wasi。

4.3 旁路文件

  • Photon。photon_rs_bg.wasm 放在 smelt-pi 同一目录。Pi 的 dist/utils/photon.js 会在可执行文件目录、photon/ 子目录和 cwd 里找它。CJS 把构建机的绝对路径写进了二进制，所以不能单靠 node_modules 里的那份。
  • pi-tui .node。按加载器的相对路径放在可执行文件旁：native/<platform>/prebuilds/<platform>-<arch>/<platform>-platform[<suffix>].node。文件从依赖包里的预编译产物拷贝，不在发布时现编原生代码。RPC 不加载它；交互式剪贴板才会。Linux 上 require 已成功，darwin 的那份还要在 Mac 上加载一次。
  • QuickJS wasm在二进制里，不另放文件。

4.4 放在哪

  • macOS：smelt.app/Contents/Resources/smelt-pi/smelt-pi，wasm 和 native/ 跟它同一层。Contents/MacOS 只能放签过的代码，wasm 签不了，所以整套放 Resources。App 只是载体，安装和 GUI 启动时发布到 ~/.smelt/bin。和 smeltd 一样先签内层再签 .app。
  • Linux：放进现有的 smeltd-*-linux-*.tar.gz，和 smeltd 同级。首启不下载。
  • ~/.smelt 不再出现 runtime/store/pi 或 runtime/store/bun。

5.packages/pi-agent 怎么改

5.1 留下的

源码目录、package.json、bun.lock、tests/、scripts/production-smoke.ts 都留在仓库里。 版本仍然钉死在 package.json。bun install --frozen-lockfile 只发生在 CI 和开发机上，用来编译和测试，不发生在用户首启。

5.2 分流入口

新增 src/compiled-main.ts 作为编译主入口。src/main.ts、src/auth-main.ts、 src/mcp-main.ts、src/mcp-gateway-main.ts 仍是各自的实现，由分流入口在运行时 import 其中一个。 开发时 bun src/main.ts 继续可用，测试不必先编译。

分流规则：

  • 用户参数以 auth 开头：丢掉这个词，再 import auth-main.ts。该文件用 process.argv.slice(2)，所以 import 前要把 argv 摆成 [argv0, 虚拟脚本, ...其余]。
  • mcp 同理，进入 mcp-main.ts。
  • gateway：import mcp-gateway-main.ts。它不吃子命令参数。
  • 其它参数：原样交给 main.ts。

5.3 pi-mcp-runtime.ts 改静态 import

删掉 import.meta.resolve 和随后的动态 import()。 直接从钉死的文件导入 createDefaultTransport： 

import { createDefaultTransport as piCreateDefaultTransport }
  from "../../node_modules/@earendil-works/pi-coding-agent/dist/extensions/mcp/runtime.js";

这个路径不在包的 exports 里，所以必须是相对文件路径，不能写成包的子路径。 Pi 升级把文件挪走时，编译失败，这和现在「升级后动态 import 大声失败」是同一种约束，只是提前到了打包。 类型仍然用包导出的 McpTransportFactory。

5.4 网关改成 gateway 子命令

mcp-gateway-client.ts 里删掉 GATEWAY_MAIN = fileURLToPath(...)。 spawnGateway 改为 spawn(process.execPath, ["gateway"], ...)。 其余不变：detached、自己的会话、日志、锁、SMELT_MCP_GATEWAY_DIR。 编译产物会自己插入 /$bunfs/root/... 作为 argv[1]，调用方不要再传脚本路径。

5.5 子智能体

getPiInvocation 的 /$bunfs 分支留下。实现要保证拉起会话的路径 basename 不是 bun 或 node（见 §9）。 不要在这里再加一层「如果是 bun 就改去找 smelt-pi」的兼容判断。进程名从一开始就叫对。

6.managed_runtime.rs 怎么收敛

6.1 删掉的运行时模型

下面这些只为「首启下载 Bun + 安装 Pi 树」存在，在本 PR 里删除，不留空函数或开关：

  • build.rs 生成的 PI_AGENT_RUNTIME_FILES、PI_AGENT_PACKAGE_JSON、PI_AGENT_BUN_LOCK 嵌入表。Rust 二进制不再携带 packages/pi-agent 的源码副本。
  • Pi generation：pi_manifest、staging、materialize_pi_files、run_pi_install（bun install --frozen-lockfile --production --ignore-scripts）、managed_pi_agent_dependencies_installed、Pi lease。
  • Bun generation：按平台下载 zip、校验、解压到 store/bun/<generation>、sync_managed_bun 的租约。Bun 1.4.0 的 URL 和 SHA 常量随这套下载一起删。
  • ManagedPiRuntime::process_args 里「bun 路径 + src/main.ts + 其余参数」这种拼法。sync_managed_pi_tool 按相对路径检查脚本文件是否存在的逻辑一起删。
  • 会话继承两份 generation FD 的做法。bundle 里的文件由正在运行的进程映射；替换 app 之后，已启动的进程在 Unix 上继续用旧 inode，直到退出。不再为了防止目录被回收而持有 lease。

6.2 新的 process_args

宿主只知道 bundle 里的 smelt-pi 绝对路径：

  • RPC：[smelt_pi, ...现有尾部参数]。尾部参数就是今天写在脚本路径后面的那些（--offline 等）。
  • 登录：[smelt_pi, "auth", ...]。
  • MCP：[smelt_pi, "mcp", ...]。

不再把 Bun 可执行文件和 TypeScript 路径放进 argv。

6.3 ~/.smelt/runtime/bin/bun

crates/smelt-model 的 MANAGED_BUN_LAUNCHER_HOME_PATH（~/.smelt/runtime/bin/bun） 继续是写进 mcp.json 的 command。Playwright、浏览器类 MCP 今天就是这个命令。 实现改成：smelt 启动时把这个路径写成一条启动器，内容等价于 

export BUN_BE_BUN=1
exec "<当前 bundle 的 smelt-pi>" "$@"

启动器在每次启动时覆盖，指向这一次安装的 bundle。它不是 generation，不下载，不持有 lease。 外部 MCP 因此仍然能执行 bun <script>。智能体进程由 smeltd 直接 exec ~/.smelt/bin/smelt-pi 解析出的真实路径，环境里没有 BUN_BE_BUN。

acp_conn 里为会话保存的 ManagedBunRuntime 改成「当前 smelt-pi 路径」。 不再为了让子进程活过 generation 回收而继承 FD。

7.用户扩展的三方依赖

扩展自己的 import "ms" 这类依赖由 jiti 从扩展目录的 node_modules 解析。 虚拟模块只覆盖 Pi 和 typebox 那一组包。目录里没有 node_modules 时，加载失败，进程退出，这是实测结果，要保持。

Pi 安装 npm: / git 包时走 npmCommand。未配置时命令是 npm，参数是 install <spec> --prefix <agentDir>/npm --legacy-peer-deps。 这些参数交给 Bun 会失败。Bun 能接受的是 install <spec> --cwd <dir> --omit=peer， 而且只有 getPackageManagerName() 认出 basename 为 bun 时，Pi 才会发出这组参数。

因此安装命令就是 §6.3 的启动器，不再另找系统 npm 或系统 bun：

  • Smelt 在 Pi 设置里把 npmCommand 写成 ["~/.smelt/runtime/bin/bun"] 的绝对路径。basename 是 bun，Pi 会用 --cwd 和 --omit=peer。
  • 启动器自己设置 BUN_BE_BUN=1 再 exec smelt-pi。这个环境变量只出现在安装子进程和 MCP 服务器子进程里。
  • 智能体进程不设置 BUN_BE_BUN。设了之后入口会被 Bun CLI 换掉，argv 实测变成 Script not found。

扩展目录里手放的 package.json + 已安装的 node_modules 不经过这条命令，jiti 直接读。 这和 Pi 今天的行为一致。

8.package-mac.sh 和 release.yml

8.1 在哪编译

发布用的 darwin 二进制在 release.yml 已有的 macos-14 job 里编译，然后再交给 scripts/package-mac.sh。 Linux 的两个架构在现有 Linux job 里编译，打进 smeltd 的 tar.gz。 Linux 上交叉出 Mach-O 已经成功，但那份文件没有在 Mac 上运行过，所以不拿它当要签名的发布物。

CI 安装 Bun 1.4.0，与 managed_runtime.rs 今天锁定的版本相同，然后在 packages/pi-agent 执行 bun install --frozen-lockfile 和 §4.2 的 bun build --compile。 macOS 目标是本机编译；Linux x64 / arm64 用对应的 --target。Bun 1.4 文档写明 -baseline 后缀会解析成同一份二进制。 编完把 photon_rs_bg.wasm 和该平台的 pi-tui .node 拷到 smelt-pi 旁边的固定相对路径。

8.2 签名

scripts/package-mac.sh 对 Developer ID 使用 Hardened Runtime、--timestamp。 旧稿写的 ci/mac/entitlements.plist 不在仓库里。现在缺 scripts/entitlements.plist 或 scripts/jit-entitlements.plist 就失败，不再静默跳过。

新增 scripts/jit-entitlements.plist，无 XML 注释，内容按 Bun 的签名文档：

  • com.apple.security.cs.allow-jit
  • com.apple.security.cs.allow-unsigned-executable-memory
  • com.apple.security.cs.disable-executable-page-protection
  • com.apple.security.cs.allow-dyld-environment-variables
  • com.apple.security.cs.disable-library-validation

package-mac.sh 在 Developer ID 路径上要求这个文件存在，缺失就失败。 用它签 Contents/Resources/smelt-pi/smelt-pi，并签旁边的 Mach-O .node。 wasm 不是代码，不签。签名顺序保持现有约定：先内层 Mach-O，再封 .app，不用 --deep。

Rust/GPUI 那条注释写明主程序不需要 allow-jit 或 allow-unsigned-executable-memory。 这组键只放在 Pi 二进制的 plist 上，不并进 GUI 的 entitlements。 disable-library-validation 留在 Pi 的 plist 里，因为 Bun 文档把它和原生 addon 放在一起； Linux 上我们已经确认 .node 是运行时 dlopen 的外部文件。

8.3 公证

公证仍走现在的 Developer ID + Hardened Runtime 路径（package-mac.sh 指向的 notarize 阶段）。 内层 smelt-pi 必须带 runtime，否则包会被拒，这是脚本里已有的说明。 这次没有执行 codesign 或 notarytool。验收放在 §11，在 macos-14 上做。

8.4 release.yml 要加的步骤

  • macOS job：checkout 之后、组装 .app 之前，安装 Bun 1.4.0，编译 smelt-pi，拷贝 wasm 和 darwin-arm64 的 .node，先跑 §11 的冒烟，再进入签名。
  • Linux job：同样编译对应架构，把 smelt-pi、wasm、.node 放进 scripts/package-linux.sh 的目录。不要打 #52 那种 Pi 运行时归档，也不要再打一份 bun。
  • Verify required files exist 加上 packages/pi-agent/package.json、packages/pi-agent/bun.lock、src/compiled-main.ts 和 scripts/jit-entitlements.plist。

9.命名陷阱

进程不能叫 bun
getPiInvocation 在 argv[1] 是 /$bunfs/root/... 时，如果 process.execPath 的 basename 匹配 bun 或 node，就会去 spawn 命令 pi。 实测把二进制复制为名为 bun 的路径后，reexec 得到 Executable not found in $PATH: "pi"。
  • bundle 里的文件名是 smelt-pi。smeltd 用这个路径 exec。子智能体再执行的也是这个路径。
  • ~/.smelt/runtime/bin/bun 只给 MCP 和 npmCommand。它是启动器，里面设置 BUN_BE_BUN=1。不要用这个路径启动会话。
  • argv[0] 在编译产物里是字符串 bun。判断进程身份用 process.execPath，不要用 argv[0]。
  • BUN_BE_BUN=1 出现在启动器和它拉起的子进程上。会话环境里不设置它。

  2. 编译产物在空目录里：get_state 的 success 为 true；auth list 退出码 0；带 typebox 和 @earendil-works/pi-coding-agent import 的用户扩展出现在 get_commands；自带 node_modules 的扩展能加载，挪走 node_modules 则失败。

12.风险与待在 Mac 上验证的项

已在 Linux 上看到、实现时要守住的
  • 编译必须发生在 packages/pi-agent 内，用相对路径。绝对路径的动态 import 不会把依赖打进去。
  • Photon 的 1.8MB wasm 必须跟着二进制走。只有二进制、没有这个文件时缩放失败。
  • 进程名叫 bun 时，子智能体去找系统里的 pi。
  • BUN_BE_BUN=1 设在会话进程上会换成 Bun CLI。
  • Pi 默认的 npm --prefix 参数不能交给 Bun。安装必须走 basename 为 bun 的启动器。
  • import.meta.resolve 进未导出的 Pi 内部文件，在编译产物里启动即失败。这次只碰到 pi-mcp-runtime.ts。实现时如果再出现同类动态 import，同样改成静态 import，不要在旁边放一份 node_modules 去救。
  • Linux 产物动态链接 glibc，这次 objdump 看到的最高版本是 2.17。还要在发布用的 Ubuntu 22.04 容器里跑一次冒烟，确认和现在的 Linux job 一致。

12.1 还没在 Mac 上做的

  1. 运行交叉编出的，或在 macos-14 上编出的 arm64 二进制。这次只有 file 和 Exec format error。
  2. codesign、notarytool、Hardened Runtime 下 JIT 是否真能启动。依据是 Bun 的签名文档和 entitlements 列表，不是一次成功的签名。
  3. darwin-arm64 的 pi-tui .node 能否被签过名的进程 dlopen。
  4. 带 JIT entitlements 的内层二进制放进 .app 之后，现有公证是否仍然 Accepted。

没有真实模型 API 的一轮对话也不在这次实测里。验收里的 get_state 和现有 production-smoke 对齐；模型回合仍由现有测试和手工会话覆盖，不在这篇方案里新定协议。
