# 对话数据模型：轮 + 条目摘要 + 按需取全文

> 状态：方案，待确认（2026-11-25）。没有开工。

## 1. 现象

- **体积。** 本机实测 Claude 会话最大 120 MB（对话内容 26 MB）、P99 60 MB，Antigravity 最大 140 MB；按轮切开，最大一轮 4.2 MB / 206 条，90%–97% 是工具结果、思考、图片。这些内容在界面上默认折叠，却和正文一起整条发、整条存在客户端。
- **翻页周边越长越多。** 为了「客户端只有一段」，已经长出：
  - `smelt_model::entry_window`：按 offset / len / total / 修订号 / 对话身份拼窗口（305 行，手机、桌面共用）；
  - 桌面首帧只带当前一轮（`omit_history`），空就自动补一页（`backfilledAt`）；
  - `conversation.prompt_index`：导航要整段对话的每一问，单开一个方法；
  - `conversation.fork_cut`：分叉要按下标找切点，单开一个方法；
  - 图片引用按「条目下标 + 摘要」定位；`turn_timings` 按 `user_index` 挂；
  - 页边界切在一轮中间，折叠行「用时 + 读/搜/改/命令次数 + 最终回答」按半轮算。

## 2. 根因

1. **对话没有「轮」这一层。** 对话是一条扁平的 `Vec<AcpEntry>`，身份是下标。轮靠扫描用户消息推出来（守护进程 `last_user_index`、插件 `isUserEntry` 各一份，规则还不一致），计时、分叉、图片、导航都只能挂在下标上；客户端手里只有一段下标窗口，于是每个要「整段对话」的功能都得单开方法或补页。
2. **时间线和大块内容是同一个类型。** `AcpEntry::ToolCall.output`、思考正文、图片 base64、子代理 `children` 全内联在条目里。列表要的是「这里有个工具调用、读了什么、成没成」，拿到的是全部输出。

只改传输（翻页对齐、发送时把大块换成占位）是在这两个根因上叠补丁。

## 3. 业内做法

- **OpenAI Codex app-server**：对话 = 轮（turn）→ 条目（item），都有 id。历史按轮、按游标翻（`thread/turns/list`），轮里的条目默认给摘要（`itemsView: summary`），可以不带（`notLoaded`）或要全文（`full`）；`thread/items/list` 按 `turnId` 翻一轮里的条目。实时更新是条目生命周期事件（`item/started`、`…/delta`、`item/completed`），按条目 id。
- **Zed / Cline / Claude Code 扩展**：都是把整段内容一次塞给界面，长对话卡死、内存几个 GB；修法都是往「默认不加载大块、看到再取」走。

## 4. 目标模型

`smelt-model` 定义，守护进程归约、线上格式、桌面插件、手机端用同一套：

```text
对话 Conversation
  身份：history_session_id（没有时 acp_session_id）
  turns_total
  信封：相位、审批、模型、用量、队列……（和现在的快照信封一样）

轮 Turn
  no            对话内序号，从 0 起；分叉、导航、翻页都用它
  origin        用户提问 / 别的对话发来的消息
  prompt        文字 + 图片引用
  started_at_ms / ended_at_ms / outcome
  items         这一轮的条目，按顺序

条目 Item（时间线上的形状，就是摘要）
  no            轮内序号；工具调用另带 ACP 的 tool_call_id
  正文          全文（时间线本身就是它）
  思考          字数 + 开头预览
  工具调用      标题、种类、状态；每段输出：种类、字节数、行数、预览、
                diff 的路径和增删行数、终端退出码
  子代理调用    子过程的轮/条目引用，不内联
  提示          新会话、回合失败、后台任务结束
```

全文不在时间线里：`conversation.item { session_id, turn, item }` 取一条的完整内容（工具输出、思考、diff 原文、图片），`conversation.image` 改成按条目定位。完成了的条目不再变，客户端按 `(turn, item)` 缓存。

全文由守护进程持有（归约器内存，来自智能体历史重放，见第 9 节），时间线形状是它的列表视图、`conversation.item` 是详情视图，和 REST 的列表 / 详情一样，不是连接级的开关。

## 5. 接口

| 现在 | 之后 |
|---|---|
| 订阅帧：信封 + 从 `entries_offset` 起的条目 | 订阅帧：信封 + `turns_total` + 有变化的轮（通常只有最后一轮）；增量照旧用镜像补丁，镜像按轮 |
| `acp_snapshot` 按条目下标往前翻 | `conversation.turns { before, limit }` 按轮往前翻，每轮带条目摘要 |
| `conversation.prompt_index` | 删。`conversation.turns { before, limit, items: false }` 只要轮头（提问、时间），导航用 |
| `conversation.fork_cut` | 删。分叉直接给轮号 |
| `conversation.image { entry, digest }` | `conversation.image { turn, item, part }` |
| `turn_timings`（按 `user_index`） | 删。时间在 `Turn` 上 |
| `omit_history` / `tail_limit` / `known_entries` | 订阅参数 `tail_turns` + 续传用的 `known_turns`、修订号 |

客户端合并：按轮号放进表里，`turns_total` 变小就删掉多出的轮。`entry_window` 整个删掉；不会再有「不相接的窗口」「起点挪到窗口前」「补页只补一次」这类情况。

## 6. 规则归属

- 轮的边界、条目摘要的字段（字节数、行数、增删行数）是数据模型，在 `smelt-model`，只有一份。
- 折叠成几行、哪条算最终回答、哪些工具算「改」、文案，仍在 JS（`buildConversationLayout` / `tallyTools`）。插件拿到的永远是整轮，汇总不会再按半轮算。
- 手机端在 `smelt-mobile` 的 Rust 里做同样的列表视图映射，不复刻折叠规则以外的东西。

## 7. 影响面

| 位置 | 改什么 |
|---|---|
| `smelt-model` | `Turn` / `Item` / 摘要类型；`conversation.turns` / `conversation.item` 参数；删 `entry_window`、`TurnTiming`、prompt_index / fork_cut 类型 |
| `smelt-core` | 归约器 `acp_session`（`apply.rs` 1.9k 行、`mod.rs` 1.7k 行）从扁平条目改成轮 → 条目；挂起时按轮裁 |
| `smeltd` | 订阅帧、翻页、`conversation.item`；读条目的地方都换成按轮：交接、自动化取输出、跨对话消息、子代理过程、标题、分叉、图片（约 20 个文件） |
| `smelt-model::acp_wire` | 镜像从条目列表换成轮 |
| `smelt-acp` / hub / `smelt-nsh` SDK | 订阅、翻页、取条目 |
| `plugins/conversation`、`plugins/automations`（运行详情） | 按轮渲染，展开取全文 |
| `smelt-mobile` + Flutter | 同上；`merge.rs`、`cache_tail` 换成按轮 |

按第 9 节的 C：新增一张每轮事实的小表（时间、结果、失败详情、提示），不存正文；改表前单独列清单确认。运行时协议要升版：订阅帧和翻页的核心格式变了，旧桌面、旧手机读不了新运行时，按现有自升级走；不做新旧两套格式并存。

## 8. 实施顺序

一次切换，不留过渡层；但按依赖从下往上做，每层先跑通再往上：

1. `smelt-model` 类型 + `smelt-core` 归约器产出轮，守护进程内部读条目的地方全部改完，测试过。
2. 线上格式、订阅帧、`conversation.turns` / `conversation.item`，删旧的 op 和方法。
3. 桌面对话插件、自动化运行详情。
4. 手机端。

2 到 4 在同一个分支上，合并前整体可用。完成后拿最大的 Claude 会话实测：打开到首屏的时间、首帧字节数、往上翻一页的字节数、客户端内存。

## 9. 重放与身份（已核实）

**重放怎么做的。** 唤醒挂起的会话、守护进程重启、重新拉起时，智能体用 `session/load` 把它自己的历史重放一遍。归约器在 `HistoryReplayStarted` 时把已发布正文放进 `replay_baseline`，从空缓冲重建草稿；`HistoryReplayFinished` 时整份换上，并从下标 0 整段重发（`apply.rs` 223–230、`mod.rs` 684）。

**重放后会消失的东西**（守护进程自己插的，智能体历史里没有）：

| 条目 / 状态 | 插入处 |
|---|---|
| 回合失败 `TurnFailed` | `apply.rs:1334` |
| 新会话分割线 `NewSession` | `apply.rs:662` |
| 后台任务结束 `TaskNote`（`BackgroundNotice`） | `apply.rs:343` |
| 回合用时、结果 | 只在内存（`turn_timings`、`turn_outcome`） |

另外，对话跨过「新会话」后，恢复身份换成新的智能体会话，重放只能重放这一段：分割线之前的内容在下一次重放后就没了。

**结论：按位置定的身份在重放后不稳定，现在就已经出错。** `turn_timings` 按 `user_index` 挂，重启时不清（`reset_for_restart` 不动它），重放后前面少了几条 `TurnFailed` / `TaskNote`，下标整体前移，用时会挂到别的提问上或丢失（按代码推断，未写用例复现）。轮号同理：跨过「新会话」的对话，重放后前面的轮整段消失，轮号整体变。

**业内怎么解决身份：宿主自己存对话记录。** Codex 自己写 rollout 文件，条目 id 落盘；Cline、Roo Code 把任务消息存在扩展自己的存储里；Zed 自带智能体的对话存在它自己的库里。只有 Zed 接外部 ACP 智能体时靠 `session/load` 重放，和我们一样，也正是它长对话卡死的那条路径（#66457）。

所以两种选法：

- **A. 守护进程持久化对话记录（推荐）。** 轮、条目的摘要和全文由守护进程落盘，带稳定 id；智能体的历史只负责智能体自己的上下文，不再用来给界面重建正文。
  - 解决：身份稳定；看历史不用唤醒智能体；回合失败、新会话分割线、用时、结果都留得住；跨多个智能体会话的对话完整；冷会话打开不用先拉起进程。
  - 代价：新的存储（轮、条目的字段进 SQLite；大块全文的存法要定）；会话在 Smelt 外被继续（例如在 Claude CLI 里 `--resume`）时，两边会分叉，要定以谁为准；从外部导入的历史会话第一次打开时仍要重放一次来建记录。
  - 和「数据只存一处」的关系：智能体历史是给模型的上下文，守护进程记录是给人看的对话（多了失败、分割线、用时、跨会话），两者不是同一份数据的副本；但正文部分是重叠的，这一点要你拍板。
- **C. 正文不存，只存智能体不知道的事实（11-25 用户：不想额外存很多东西，取这个）。**
  - 正文（提问、回答、思考、工具调用和输出）唯一来源仍是智能体历史，照旧重放。
  - 身份：轮 = `(智能体会话 id, 这个会话里的第几轮)`；条目 = 工具调用用 `tool_call_id`，其余用轮内序号。同一个智能体会话的历史只追加，重放结果一致，身份就稳定；编辑重发最后一问只截掉最后一轮。
  - 守护进程只存智能体历史里没有的：每轮的开始/结束时间、结果、失败详情，以及后台任务结束这类提示挂在哪一轮。每轮几十字节，一张小表，按身份关联，重放后贴回去。
  - 「新会话」不再留在同一个对话里：智能体忘了前面的内容，就是一段新对话（Claude Code `/clear`、Codex `/new` 都是开新会话），界面上从新对话可以跳回上一段。这样一个对话永远只对应一个智能体会话，不用存会话链。
  - 不解决：看历史仍要唤醒智能体重放，长会话重放慢的问题还在（Zed 接外部智能体同样如此）；以后要快，方向是直接读智能体的历史文件，不是另存一份。
- **B. 不持久化，身份按「代」作废。** 轮号、条目序号只在一代内有效；每次重放算新的一代，客户端缓存、翻页游标、取全文都带代号，对不上就整段重取。
  - 现在的修订号机制就是这个思路。能用，但上面的丢失问题（失败、分割线、用时、跨会话内容）一个都不解决，看历史也照旧要唤醒智能体。

## 10. 其他待定

- **一轮的上限。** 实测最大一轮 350 条，摘要后每条几百字节。自动化或长任务可能一轮几千条：要不要像 Codex 一样在一轮里再按条目翻页，还是整轮给。
- **子代理过程。** Claude 的子代理过程现在挂在 `children` 里；Pi 子智能体已经是独立子会话（`subagent.transcript`）。统一成「子过程是另一组轮」后，两者走同一条路。
