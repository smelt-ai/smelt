# 整个 app 插件化

> 状态：方向定于 2026-11-09；2026-11-20 改定「插件只有 JS 一种，Rust 只做宿主和能力」，本文据此重写。
>
> 本文先写终态，再写从现在走到终态的顺序。每块拆到时，它的接口细节再写回本文。

## 目标

用户能用 JS 改 app 里的任意一个元素。

- smelt 的每一项功能都是 JS 插件。随 App 带的和用户写的是同一种东西，用同一套接口。
- 用户想改哪项功能，就改那个插件的 JS，或复制一份换个 id 再在布局里换上。
- Rust 只写宿主和能力：宿主提供机制和基础服务，能力给插件数据、动作和组件。宿主和能力都不认识任何具体功能。

上一版（2026-11-09 起）把功能从宿主搬成了 Rust 内置插件。宿主因此变小了，但 Rust 插件画的界面用户改不了：插件化只做到「能删能换」，没做到「能改」。

## 原则

1. **Rust 不认识功能。**
   - 宿主和能力的代码里不出现「会话列表」「文件树」「Git」这类功能名，也没有它们的枚举、字段或专用 action。
   - 判断标准：删掉任何一个插件，Rust 不用改一行。
2. **内置插件没有特权。** 随 App 带的插件和用户写的插件走同一套注册点和接口。内置插件需要的能力，就是开给所有插件的能力。
3. **状态归功能自己，数据只有一个权威。**
   - 一个功能的状态只存在它自己那里：插件的内存和插件自己的库。
   - 运行时的数据以 smeltd 为权威，客户端只留推送来的只读缓存。
   - 几个功能都要的派生事实（会话状态这类），由能力算好给，插件不各自再算一遍。
4. **等待一律事件驱动。** 宿主到插件的通知用事件，不让插件轮询。gpui-shell 的宿主不能回调脚本，所以事件做成插件去 await 的异步函数。
5. **搬走，不加层。** 拆一个 Rust 插件，就是把它整个分成能力和 JS 插件两部分，同一个提交删掉 Rust 版。不留两份并行的实现，不在中间加适配层。
6. **接口只开通用的。**
   - 加接口前，先看已有机制能不能统一。一个新机制和已有的平行，就是走偏的信号。
   - 不为某一个插件开专用方法。
   - 同一段逻辑第三次复制，说明缺了一个归属。要找出归属，而不是再复制一次。

## 分工：Rust 做什么，JS 做什么

一样东西放哪，先答三问：

1. 几个功能都要用吗？
2. JS 做不对吗？要原生接口、要宿主才看得见的状态、要和运行时协议用同一份规则。
3. JS 做不快吗？渲染量大、数据量大、每帧都跑。

有一问答「是」，放 Rust；都是「否」，写在 JS 插件里，宁可几个插件之间有些重复。

换个角度验证：用户把一个插件复制一份重写界面时，**不得不重新实现一遍**的东西，该在 Rust；他**会想改**的东西，该在 JS。

| 放 Rust | 放 JS 插件 |
| --- | --- |
| 数据的同步和缓存：工作区目录、会话状态、话题、机器 | 这项功能自己的数据和规则：会话列表的分组、置顶、排序、折叠，存插件自己的库 |
| 几个功能都要的派生事实：会话状态、agent 种类的名字和图标 | 视图里的一切：摆什么、怎么摆、间距、颜色、图标、文案、时间怎么写、显示哪些信息 |
| 动作：调运行时（`call`）、系统服务（通知、选路径、剪贴板、用别的应用打开） | 界面自己的临时状态：悬停、展开的菜单、输入框里的字、正在改名 |
| 重组件：终端、对话流、markdown、diff、高亮、远程桌面画面、3D 小人 | 把点击、拖动、快捷键接到动作上；右键菜单里有哪些项、怎么排 |
| 交互机制：滚动锚点、拖动、重排动画、弹层、菜单底层、输入框、焦点 | 给别的插件的约定：命令、菜单 id、插槽 |

**界面用细粒度的元素拼。**
- JS 视图用 gpui-shell 的元素（div、flex、文字、图标）和 `smelt-ui` 的零件拼。
- Rust 不做「一行会话」「一张自动化卡片」这种整块业务组件：做了，那块里面的东西用户又改不了。
- Rust 组件只做 JS 拼不出、或拼出来太慢的，外观能开成参数的都开成参数。

## 终态：宿主留什么

宿主只放三种东西：宿主自己要据此行动的、只有宿主看得见的、插件再小心也做不对的机制。别的给插件用的东西做成能力（下一节）。

| 类别 | 内容 |
| --- | --- |
| 窗口 | 只有主窗口：标题栏和交通灯让位、原生窗口外观（背景、透明度、窗口材质）、调试 HUD、退出流程 |
| 页面路由 | 主窗口一次一页，每页一块 `DockArea`；页的布局里可以摆一个出口（`smelt/outlet`）。进首页、按打开的视图换页或换出口里的内容、页里的「返回」回来路；装布局、存档、停靠区开合（见「摆放」） |
| 注册表 | 视图（含设置页）、页、命令和快捷键、菜单贡献、布局、主题、文件打开方式、视图角标。能力和插件登记进同一张表 |
| 命令面板 | 命令注册表上的一个通用界面 |
| 设置 | 视图注册表上的一个通用界面，单独一页、两个视图：导航（`smelt/settings-nav`）和内容（`smelt/settings`）。和命令面板一样不认识任何一页 |
| 插件运行时 | 发现、加载、卸载、热重载；按插件分开的 Policy、日志身份、`smelt-fs`；每个插件一份自己的 SQLite；随 App 带的插件编进二进制（见「插件运行时」） |
| 运行时连接 | 本机 smeltd 的启动、升级、重启；远程机器的配对、连接、中继、升级；按插件登记的话题订阅、转发运行时推送；`call` 调任意控制方法；会话状态和工作区目录的镜像（见「运行时数据只是话题」的例外） |
| 系统服务 | 系统通知和权限、菜单栏图标、Dock 角标、选路径（远程机器用宿主画的目录浏览）、用编辑器或文件管理器打开、剪贴板、对话框 |
| 应用生命周期 | 自动更新、挪到「应用程序」、退出前检查有没有活在跑、应用日志 |
| 宿主机制自己的页 | 外观、快捷键、插件管理、远程机器（连出去的那一半）、关于、更新页。背后是宿主自己的机制（录快捷键、导入卸载插件、更新的状态流转），拆成插件就要给每页开一组只有它一个调用方的接口（原则 6）。宿主以来源 `smelt` 登记进同一张视图表 |

最终的 `Workspace` 只剩窗口、`DockArea`、布局、可见性登记和退出、更新这几件事。

## 终态：能力层

能力是给插件用的 Rust：数据、动作、组件。

- 放 `crates/` 根下，按能力命名，不按功能命名。
- 只依赖 `smelt-plugin-api` 和更底下的能力 crate，由应用 `smelt` 组装。
- 能力不认识任何插件：删掉一个插件，能力不用改；删掉一个能力，宿主不用改。
- 每样能力在 JS 那边都有映射（见「JS 映射」）。只有 Rust 能用的能力不算数，因为没有 Rust 插件会用它。

| 能力 | 给插件的东西 | 现在在哪 |
| --- | --- | --- |
| 会话数据 | 工作区目录、会话状态，带上几个功能都要的派生事实（对话的状态、agent 种类的名字和图标） | 宿主的镜像 + `smelt-model`；派生事实 JS 还拿不到 |
| 终端 | 每格终端一个视图实例（`create_view` / `SmeltViewInstance`），字节流、画面、终端菜单的底层 | Rust 插件 `crates/plugins/terminal` |
| 对话 | 对话流、消息里的 markdown 和 diff、输入框、ACP 连接和会话生命周期 | Rust 插件 `crates/plugins/conversation`；拆到哪一层另定（见「待定」） |
| 组件库 | `smelt-ui` 的 JS 组件：按钮、菜单、弹层、对话框、下拉、列表行底座、滚动区域、吸顶区段、拖动、悬停提示、键帽、设置页骨架、列表动画（开合、重排、落进来、铺底一闪、开始跑时亮一下） | `crates/smelt-ui` + `smelt-plugin-api/src/js/ui` |
| Git | 读写仓库 | `crates/smelt-git`，还没映射给 JS |
| 远程桌面 | 画面组件 | `smelt-runtime-client` 的 `DesktopProxy` |
| 小人 | 3D 小人的帧解码和画法 | Rust 插件 `crates/plugins/buddies` |
| 资源量测 | 进程 CPU、内存 | Rust 插件 `crates/plugins/resources` |
| 更新 | 替换签名过的 App 包（只给随 App 带的更新插件） | `crates/plugins/updater` |

能力自己要登记视图、命令时，用自己的来源 id（如 `smelt.terminal`），和插件一样进注册表。

## 终态：插件接口

插件接口就是 JS 的宿主模块 `smelt-plugin-api`，加上组件模块 `smelt-ui`。Rust 那份 `smelt-plugin-api` 是能力 crate 登记东西用的，也是 JS 映射的来源。

### 读、变化、动作分开走

- **读**：同步函数，只读内存。
- **变化**：事件，用 `await next_event()` 取。不带数据，收到后再去读。
- **动作**：一律是命令，处理函数交回结果。
  - 主窗口关着时，用不到窗口的命令照样执行；本来就要把人带到主窗口的命令先开一扇窗。
  - 谁调用谁处理失败：插件调的，插件自己提示；快捷键、菜单、命令面板执行的，由宿主统一发错误通知。

### 给插件的读和事件

| 类别 | 内容 |
| --- | --- |
| 读 | `machines`（只有 key、名字、不可用的原因）、`machine_online`、`session_presence`（会话进程还在不在）、`session_states`、`workspace_directory`、`path_style`、`window_active`、`overlay_open`、`notification_permission`、`view_shown`、`view_laid_out`、`active_context`、各注册表 |
| 事件 | `machines_changed`、`sessions_changed`、运行时话题（宿主只转发，不解读）、`window_activated`、`overlay_changed`、`notification_permission_changed`、`shown_views_changed`、`laid_out_views_changed`、`active_context_changed`、`locale_changed`，以及各注册表的 `*_changed` |
| 命令 | 通知；菜单栏和 Dock 角标；选路径；在编辑器或文件管理器里打开；`smelt.app/open-view`（打开设置页也是它）；显示主窗口；机器管理 |
| 路径 | 插件数据目录（`data_dir()`）、应用日志 |

### 运行时数据只是话题

会话状态、工作区目录、智能体配置、额度、自动化，都是 smeltd 的数据：

- 插件登记要哪些话题（`register_topics`），宿主按并集订阅、原样转发，不解读，也不缓存：新登记的插件靠重订拿到快照。
- 插件之间不各自镜像一份。
- 例外：会话状态和工作区目录（`session_states`、`workspace_directory`）留作宿主接口。三问都答「是」：宿主自己据此行动（重启守护进程前看有没有会话在跑）；只有宿主看得见（多台机器的订阅合并、机器上下线的代数）；插件再小心也做不对（每个插件各自合并一遍，结果会不一样）。宿主留一份镜像（`crates/smelt/src/daemon_states.rs`），插件只读。
- 会话的显示名、状态、最后更新时间由 smeltd 算好放进推送（`smeltd/src/session_names.rs`），各端直接用，不自己拼。`conversation_name` 是整段对话的名字，`name` 是这一格的名字。
- 还没有话题的数据，由 smeltd 补上话题。

### 视图一张表

- 视图和设置页是同一种东西，按来源整组登记：`register_views(视图)`，id 是 `<来源>/<名字>`，和命令、布局、主题一样。
- 设置页就是带 `settings: {组, 搜索关键词}` 的视图。打开带 `settings` 的视图，就是打开设置、停在这一页。
- 可见性只有一套：`view_shown` 和 `shown_views_changed`。
- 视图第一次露出来时建，之后一直留着，直到登记被替换或撤下。打开时从插件自己的库里读，改了马上写回，不靠视图活着保存东西。
- 每个视图是插件脚本里的一个 View 类，登记时交出类本身（见「插件运行时」）。名字由插件自己起；`main` 不再是保留名，会话列表沿用 `smelt.session-list/main`，布局不用改。
- 视图登记里写标题、图标、是否自己画顶栏（`draws_top_bar`）。自己画顶栏的视图顶上放 `smelt-ui` 的 `SmeltWindowBar`。
- 视图打开时的参数：建的时候在 `init` 里用 `opened_view()` 取；已经建好的视图再被打开、参数变了，插件收到 `view_opened` 事件。
- 视图登记里不写位置。入口放在哪，是菜单贡献和布局的事。
- 按实例建的视图（`instances`，如每段会话一份的终端、对话）不进布局、没有入口：别的插件用 `SmeltViewInstance` 按视图 id 和参数建一份自己摆；只想放进主窗口看的用 `smelt.app/open-view` 带参数打开，宿主建一份放进出口。

### 菜单贡献

插件要在别人画的地方放一个入口（机器菜单里的「远程桌面」、项目菜单里的「用 IDE 打开」），用菜单贡献：

- 登记：`register_context_menu_items(菜单 id, 菜单项)`，按（来源，菜单）整组替换。每一项写标题、图标、要执行的命令和参数，或者一层子菜单；可以只在某台机器上列。条件变了，插件自己重新登记。
- 菜单 id 是字符串，由画菜单的那个插件定义和公布（会话列表的 `smelt.session-list/conversation`、`smelt.session-list/project`、`smelt.session-list/machine`），上下文的形状写在同一处。宿主只存这张表。
- 画菜单的插件用 `context_menu_items(菜单 id, 上下文)` 取项，自己画成菜单项，点了执行命令，参数是登记的参数并上上下文。失败挂在发起的地方（会话列表是那一行），找不到落点的才发系统通知。菜单在打开时取项，开着的不跟着登记变。
- 应用菜单（App、帮助）是另一张表：`register_menu_items(菜单项)`。
- 不为侧栏底部这类地方开「区域贡献」：一块想单独露出来的东西，就做成视图，由布局摆。

### 扩展点

插件往别处加东西的地方都是扩展点：命令、菜单、页、视图、设置页、主题、布局、插槽、文件打开者、退出守卫。每个扩展点先定它是哪一种：

- **并存的**：命令、应用菜单项、右键菜单项、页、视图、设置页、主题、布局、能都摆的插槽。来几个摆几个，装上就有、删了就没。退出守卫也是并存的：退出时挨个问，有一个接手就停。
- **只放一个的**：眼下用哪个主题、哪份布局，只放一个的插槽（会话行首头像），打开文件交给谁。好几个提供的时候，用哪个**由用户选**：
  - 选择归扩展点的主人：宿主的在宿主的设置里选，插件定的插槽在那个插件自己的设置页里选、存进它自己的库。
  - 没选过用默认的（主人自己定，一般是第一个）；选的那个卸了也按没选过算，原来的选择不删，装回来接着用。
  - 不按登记顺序、内置还是用户装的、谁后来去定谁优先。同 id 也不拿来替换：用户插件和随 App 带的插件同 id 时不加载、报重复，想改自带的就复制一份换个 id。
  - 没有「停用某个插件」的开关去绕：不想要哪个提供的就选别的，或者删掉它。
- **点名的能力**：使用方离不开、按 id 点名的（会话里的终端、对话）。提供方定约定，别的插件只能往里加东西（命令、右键菜单项、插槽），不能整个换掉。

加一个新的扩展点，先按上面定它是哪一种；只放一个的，同一次改动里把选择做进主人的设置。打开文件（`register_file_opener`）眼下只有一个登记方，选择等有第二个时再加，在那之前按最后登记的用。

### 插槽

插件要往别人的界面里、跟着别人的某个东西加一块（会话列表每行行首的头像），用插槽：

- 被加的一方定插槽：插槽 id（`<自己的来源>/<名字>`）、给填充视图的参数、能填几个、摆成什么样、没人填时的退路，写在自己的约定里。宿主不登记插槽本身。
- 只放一个的插槽，好几个插件都填时用哪个由用户选：被加的一方在自己的设置页里给一项选择，存进自己的库。
- 加的一方登记一个按实例建的视图，在 `fills` 里写上插槽 id。
- 被加的一方用 `slot_views(插槽 id)` 取填进来的视图，用 `SmeltViewInstance` 按参数建、自己摆，跟着 `views_changed` 建、放。它不认识填的是谁。
- 和直接点名的区别在依赖方向：使用方离不开的能力由使用方点名提供方；可有可无的附加由附加的一方认插槽。
- 已有：会话列表的 `smelt.session-list/session-avatar`，小人填它。

### 插件之间的约定

插件之间不互相依赖，只经命令、事件、菜单 id、插槽打交道：

- 一个插件对外给的视图 id、命令 id、菜单 id、插槽 id 和参数形状，权威定义放在提供方自己的 `contract.js`（JSDoc 写清参数和上下文）。调用方照抄用到的 id 和字段，注明出处。
- 接口不点名任何功能，宿主和能力不实现、也不调用这些约定。
- 提供方改约定，要在同一次改动里搜出调用方的字符串一起改。
- 删掉提供方，调用方拿到「命令没有登记」，Rust 不用改。
- 命令 id 是用户快捷键的存法，改名就丢了用户改过的键。迁移时一律沿用原 id。

### 活动上下文

- 活动上下文（当前项目、正在看的会话、是不是停在最新）是接口里的一个全局槽，由会话插件发布（`set_active_context`），宿主只转发，不解读。
- 文件、Git、历史、通知这些插件据此决定看哪个目录、把哪段会话标成已读。

### JS 映射

- 每个插件一份自己的 gpui-shell Policy，宿主函数知道是哪个插件在调。
- 事件用 `await next_event()` 取；每个插件一条队列，同样的事件只留一份。
- Rust 那份 `smelt-plugin-api` 根上的每一样，都登记在 `src/js/parity.rs` 的表里，写明 JS 那边是同名函数、换了名字的函数、别的形式（命令、组件、gpui-shell 自带的模块），还是只有宿主用、只有 Rust 有（写明为什么）。加接口不填这张表，测试不过。
- 「只有 Rust 有」在终态里只剩能力内部要的东西（开原生字节流的 `connector`、替换 App 包的 `updater`）。插件要的能力，JS 都得拿得到。

### 主题

- 主题文件是 smelt 自己的带版本 JSON（格式、校验、推法见 `docs/ui-design-language.md` 第 2 节）。插件目录下的 `themes/*.json` 是主题贡献；有一份不合法，这个插件的主题一个都不装，登记报错。
- 纯主题包把 `gpui-shell.json` 的 `entry` 指向主题 JSON，不需要 JS。
- 插件重载或卸载时，撤下它的主题。当前主题不在了，就回落到同明暗的 Default；原来的选择保留，重新装上后恢复。
- 主题只在启动和插件变化时读，render 里不读文件。

## 插件运行时

### 一个插件一份脚本实例

- 插件的入口脚本加载一次，是这个插件唯一的一份脚本实例，活到插件卸下。
- 入口的默认导出是插件的根（一个 View 类）。宿主挂上它但不显示，它的 `init` 就是插件的启动：起事件循环、命令循环，登记视图、命令、菜单、话题。
- 插件的每个视图都是这份实例里的一个 View 类。宿主要建时在同一份实例里建，各视图共享模块里的状态。
  - 设置页、按实例建的视图、填插槽的视图，都是这样。
  - 不再给每个视图单独加载一份脚本，也就没有视图之间「不共享内存、只能经库和事件同步」的问题。
- 怎么交出类：宿主函数收不了类，用 gpui-shell 现成的 `DockArea.register_panel(name, Class)`（「脚本交出类、宿主按名字在同一份实例里建」），`register_views` 里同名的视图就按它建。上游没有更直接的接口，不 fork、不等。
  - 打开参数：宿主建视图是同步的，`init` 就跑在里面。视图在 `init` 里调 `opened_view()` 取 `{ view, instance, args }`，只有这时取得到。
  - 再次打开：宿主找不到具体哪份视图，往插件的事件流里发 `{ type: "view_opened", view, instance, args }`，插件的事件循环按 `instance` 转给那份视图。
  - 插件的事件流只有一条（`next_event` 同时只能一个在等），由根的事件循环取，改模块里的状态。
  - 重画：gpui-shell 的 `cx.notify()` 只重画正在跑的那份视图，根的任务里调重画的是根；视图在自己的任务里等根用 JS 的 Promise 叫醒也一样（接着跑的还是根那一轮）。所以状态改了用宿主的 `notify_view(instance?)`：给编号重画那一份，不给重画插件还在的每一份。视图自己的点击里改了只关自己的状态，照常 `cx.notify()`。
- 加载失败的插件没有视图可登记（视图名是脚本登记的），错误在设置的插件页、`smelt plugin status` 和 `~/.smelt/app.log` 里看。
- 这是对现有 JS 插件的破坏性改动（原来主入口自动登记成 `<id>/main`，别的视图各有 `entry`）。用户插件跟着改，不写兼容。

### 随 App 带的插件

- 放仓库根 `plugins/<name>/`，编进二进制（`crates/smelt/src/plugins/builtin.rs`）。正式构建启动时写到 `~/.smelt/builtin-plugins/<内容摘要>/` 再加载，开发构建直接读仓库，改了即重挂。
- 在第一帧之前加载完，布局里摆的视图第一帧就画得出来，不闪空白。
- 先找自带的再找 `~/.smelt/plugins/`，同 id 不加载、报重复。

### 画面和数据

改成 JS 前实测过的写法规则（探针 `crates/smelt-plugin-api/src/js/ui/bench.rs`）：

1. 长内容用虚拟列表，或按行拆子视图。
2. 持续变的条目做子视图（`cx.new` 建的 Entity），变了只通知那一个：会话列表每行一个子视图，状态变了只重画那行，增删、重排、折叠才重画外层。
3. markdown、diff、高亮、终端用 Rust 组件。
4. 数据增量推，不拉整份。
5. 大量数据留 Rust，JS 只拿要画的部分。

会话列表先用现有的「读 + 变化事件」，试点里实测。超出标准再加按键增量推的机制，不先做。

### 文案

插件的文案放 `locales/ui.yml`，格式和 Rust crate 的一样。宿主给 `t(键, 参数)`（`smelt-plugin-api` 模块），按当前语言读调用方插件自己的那份，用的是 rust-i18n 同一个加载函数。这样：

- 迁过来的插件文案表原样搬，不用改格式。
- `smelt-plugin-api` 的 `catalogs` 检查连 JS 插件一起查：两种语言都有、代码取的键都在、没有没人取的键。

## 插件的样子

**用户插件**是一个 gpui-shell 文件夹，导入文件夹就算装上。纯主题包不需要 JS：

```text
my-theme/
  gpui-shell.json
  themes/colors.json
```

```json
{"id":"com.example.my-theme","name":"我的主题","version":"1.0.0","entry":"themes/colors.json"}
```

**随 App 带的插件**和用户插件同一种样子，一个插件一个自包含的目录，复制出去就能跑：

```text
plugins/session-list/
  gpui-shell.json     id 沿用原来 Rust 插件的（smelt.session-list）
  main.js             入口：插件的根，只做组装
  contract.js         对外的约定：视图、命令、菜单、插槽的 id 和参数
  *.js                按职责平铺拆分，不再分子目录
  locales/ui.yml      文案
  assets/             图标、图片
  tests/              纯逻辑单测；fixtures/ 是对照出图用的场景数据
```

入口的样子：

```js
import { View, div } from "gpui-kit";
import { DockArea } from "gpui-base";
import { register_views, next_event, notify_view, opened_view } from "smelt-plugin-api";

const state = { sessions: [] }; // 各视图共用

class List extends View {
  init(_props, _cx) {
    const { instance, args } = opened_view(); // 只在 init 里取得到
  }
  render() { return div().children(state.sessions.map(row)); }
}

export default class Plugin extends View {
  init(_props, cx) {
    DockArea.register_panel("main", List);
    register_views([{ name: "main", title: "会话" }]);
    cx.spawn(async () => {
      for (;;) {
        const event = await next_event();
        if (apply(state, event)) notify_view(); // 根里 cx.notify() 重画的是根
      }
    });
  }
  render() { return div(); } // 根不显示
}
```

1. **只 import 自己目录里的文件和宿主模块**，不设插件间共享的目录：要复用的进组件库或能力。
2. **发的就是源码**：写 JS 加 JSDoc，不经编译。用户复制到手的要能直接改。
3. **逻辑和画面分开放**：数据、规则放不 import gpui-kit 的文件，宿主函数从参数传进来，在 Node 里就能测。视图文件只读这些文件算好的结果。
4. **迁过来的插件沿用原 id**，视图、命令、菜单、插槽的 id 都不变，同一个提交删掉 Rust 版。插件的数据目录、布局里的视图 id、用户的快捷键都不用迁。
5. **数据放 `~/.smelt/plugin-data/<id>/`**（`data_dir()`，库是里面的 `store.sqlite3`，用 `store_query` / `store_execute`），见 `docs/local-storage.md`。

改自带插件是复制一份、换个 id、数据另拷一份，再在布局里换上。步骤写在 smelt skill（`agent/skills/smelt/SKILL.md`）里，由智能体照着做，App 里不另做按钮。

### 检查

- **单测**：`node --test plugins/<name>/tests/*.test.mjs`，测逻辑文件。
- **类型**：tsc 的 checkJs。类型声明由 `smelt plugin check <目录>` 加载插件时写出（`gpui-kit.d.ts`，不进仓库），CI 先跑它、再跑 tsc。
- **加载和渲染**：`smelt plugin check <目录>` 不开 App 加载并渲染一次。
- **对照出图**：从 Rust 插件迁过来时，同一份 `tests/fixtures/` 场景让两版各画一张图比对，删 Rust 版之前做。

## 会话核心

- **权威在 smeltd。** 工作区目录只有 smeltd 一个写者。客户端只发操作（新建、改名、归档、置顶、关闭、改配置），等推送回来。
- **列表只读推送的数据。** 名字、状态、时间由 smeltd 给。选中哪个、展开哪个、怎么分组、排序，是插件自己的状态，存插件自己的库。
- **会话视图是会话插件的一个视图**（`smelt.sessions/session`），是首页出口的默认内容。列表是单独的插件（`smelt.session-list/main`），选中归会话插件，列表经 `smelt.sessions/selection`、`selection-changed` 跟着。
- **会话视图用对话和终端能力**，显示选中的那段会话；分屏归会话插件。
- **别的插件怎么用会话**：跳到某段会话、开新对话、续上历史、交接、往会话里发文字，都是会话插件登记的命令。

## 摆放

插件提供视图，视图摆在哪一页、页里怎么摆是页和布局的事。

- **整个 app 是一个嵌套的路由。** 外层是页：主窗口一次显示一页，每页有自己的布局。内层是出口：页的布局里可以摆一个出口（`smelt/outlet`），出口里显示路由放进去的视图。状态在 `crates/smelt/src/router.rs`。
  - 页按来源整组登记（`register_pages`），有名字、标题、是不是首页，和出口的默认内容（`index`）。插件用 `smelt.app/open-page` 进一页。
  - 启动进首页：登记在前的那个说自己是首页的。首页没有、或没有给它的布局时，宿主把没摆进别的页的视图都摆在一页里兜底（不存档）。
  - 打开一个视图：哪页的布局里摆了它，就去那页露出来；哪页都没摆，就放进出口。
  - 换页记来路，页里的「返回」退回来的那页。出口里换内容不换页、不记来路。`Cmd+W` 不管路由，只关看得见的会话或分屏。
  - 开过的页留着它的 `DockArea` 和出口里放着的东西。
  - 用户把出口里的视图拖进了布局，出口放回默认内容。
- **每页是一块 `DockArea`**，布局是一棵任意的拆分树，用官方的 `DockAreaState` 存。现在的三栏只是出厂给工作台那页的布局。
- **视图里面怎么画归插件，视图之间怎么摆归布局。**
  - 布局文件是纯数据，引用视图 id。布局按来源整组登记（`register_layouts`），登记时写给哪一页。
  - 首页用哪份在外观里选，存在 `appearance.layout_id`。
- **收起是停靠区的，不是视图的。** 左右停靠区各自记着开合和宽度，外壳画开合按钮。面板不能关，只能拖动、放大，或随停靠区收起。自己画顶栏的视图单独成一组时，外壳不给它画标题带。
- **还没做的**：「把视图加进布局」的命令；下停靠区的开合按钮。

## 想扩展时选哪种

先看要改的是什么：

- **智能体怎么干活**（多一个工具、换提示、加技能、换模型）：写 Pi 的扩展或技能。smelt 只负责装、列、开关。
- **到点或有事时自动做**：用自动化。在 smelt 外面用脚本驱动 smeltd 的，走 Control API（`docs/control-api.md`）。
- **App 里多一样东西、改一样东西**：写 JS 插件，或复制随 App 带的插件改。
- **JS 做不到**：补进 Rust 能力层，同时补 JS 映射，不另开口子。

## 迁移

### 已经做完的（2026-11-09 ~ 11-19）

功能从宿主搬成了 Rust 插件（`crates/plugins/*`）：视图一张表、设置进主窗口、页面路由、命令注册表、菜单贡献、插槽、话题登记、目录只有 smeltd 写、会话名由 smeltd 给，宿主里的会话代码全部搬走。`Workspace` 只剩窗口和工作台机制。宿主源码不点名插件的 id，由 `scripts/lint-crate-deps.sh` 守着。JS 那边补齐了插件接口的映射和一批 `smelt-ui` 组件。

### 方法：一个 Rust 插件拆成能力和 JS 插件

1. **列清单。** 把它做的每样东西按「分工」三问分到 Rust 或 JS。拿不准的问用户。
2. **补能力。** Rust 那部分补进能力层，同时补 JS 映射，只补真用到的。补之前先看能不能并进已有的机制。
3. **写 JS 插件。** 沿用原 id，视图、命令、菜单、插槽的 id 都不变。行为和 Rust 版保持一致：做不到一样、或觉得旧行为该改的，先停下来问用户，改进等迁完另提。Rust 版的测试里，纯逻辑的那些改写成 JS 单测。
4. **对照。** 同一份场景让两版各画一张图比对，在真的 App 里过一遍功能清单，测性能（每步耗时、空闲有没有周期唤醒）。
5. **切换。** 同一个提交删掉 Rust 插件和应用 `smelt` 里那行 `register`。开发途中只在本地注释掉 Rust 版的登记，不提交两份同 id 的插件。
6. **自查。** Rust 里还有没有它的名字，有没有给它开专用接口。

### 顺序

1. **运行时机制。** 一个插件一份脚本实例、视图按类登记；宿主的 `t()`；类型声明和检查进 CI。
2. **会话列表（试点）。** 最大的一块之一，碰到的机制最全：插槽、右键菜单、拖动、动画、对话框、设置页。试点结束时记两笔账：JS 和 Rust 的行数，补了哪些能力。据此定后面的节奏。
3. **小插件**：`launcher`、`language`、`layouts`、`themes`、`archive`、`ide`、`maintenance`。
4. **中等的**：`history`、`notifications`、`skills`、`resources`、`desktop`、`machines`、`updater`、`buddies`。
5. **大的**：`agents`、`automations`、`capabilities`、`files`、`git`。
6. **会话插件**，然后是对话页（见「待定」）。

## 待定，要确认后再动

- **对话页拆到哪一层**：对话流里消息怎么排、工具调用卡片长什么样，用户可能想改，按目标该进 JS；但它渲染量最大，组件粒度要按实测定。放到最后另议。
- **内置插件能不能单独关掉**：没做。真要开关得存「关了哪些」，客户端库加表，要先确认。

## 已知缺口

- gpui-shell 没有通用的拖放绑定，拖放用 `smelt-ui` 的：`SmeltDragItem.new(id, kind)` 是能拖着换位置的一项，同一 `kind` 的项之间互放，放下时 `on_drop(from, before)` 交给脚本；`SmeltScrollView` 里拖到上下边缘自动滚，`on_drop_files(paths)` 收从访达拖进来的文件。
- gpui-shell 的 `gpui-shell.json` 拒绝未知字段，所以插件的一切都通过宿主函数登记。命令用 `register_commands` 登记，用 `next_command` 取下一条要执行的，做完用 `resolve_command` / `reject_command` 按 id 交回结果。命令只管工作台级的动作；跟着焦点变的键（列表上下移动、输入框编辑）用视图自己的 action。
- 绕过 smeltd 的修改（手改 Pi 配置文件、直接用 `pi` 命令行）现在收不到，要 smeltd 去监视文件才能补上。
- 手机端是 Flutter，跑不了 gpui-shell。插件只影响桌面，手机直接用 smeltd 协议。
