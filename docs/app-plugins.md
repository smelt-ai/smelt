# 整个 app 插件化

> 状态：方向已定（2026-11-09），分支 `feat/app-plugins`。本文只定宿主和插件的边界与迁移方法；每块的接口在拆到它时再定，写回本文。

## 目标

smelt 的每一项功能都是 gpui-shell 插件，用户也能用同一套接口写自己的插件。宿主只提供机制和基础服务，不认识任何具体功能——包括会话。

## 原则

1. **宿主不认识功能。** 宿主代码里不出现「会话列表」「文件树」「Git」这类功能名，也没有它们的枚举、字段、专用 action。判断标准：删掉任何一个插件，宿主不用改一行。
2. **内置插件没有特权。** smelt 自带的插件和用户写的插件走同一套注册点和宿主接口。自带插件需要的能力，就是开给所有插件的能力。
3. **状态归功能自己。** 一个功能的状态只存在它自己那里（插件内存、插件自己的存储），宿主不留副本、不做同步。插件之间要共享的东西由拥有它的插件发布，别人订阅。
4. **等待一律事件驱动。** 宿主到插件的通知用事件（gpui-shell 宿主不能回调脚本，做成插件 await 的异步函数），不让插件轮询。
5. **搬走，不加层。** 拆一个功能就是把它从 `Workspace` 整个搬进自己的插件 crate；不在 `Workspace` 旁边加镜像、适配层，也不留「先搬出来、以后再接插件接口」的中间状态。`Workspace` 只会越来越小。

## 宿主提供什么

**机制**

- 窗口、标题栏、整个工作台的 `DockArea`（布局文件和存档用官方 `DockAreaState`，见 `AGENTS.md`）。
- 注册表：面板、命令、快捷键、设置页、主题。内置和插件同一张表。
- 插件生命周期：发现、加载、卸载、热重载（基于文件变化事件）、按插件分开的 Policy 和日志身份。
- 事件：插件发布话题、订阅话题；宿主自己发布的只有宿主概念（布局变化、窗口、哪个面板获得焦点）。
- 活动上下文：获得焦点的面板可以发布一份通用上下文（运行时、目录、标题等），宿主只转发，不解读。文件、Git 一类插件据此决定看哪个目录。

**基础服务**

- smeltd 通道：连接本机和远程运行时，按协议发请求、收推送。插件拿到的是通道，不是「会话接口」。
- 存储：插件的业务数据进 SQLite（宿主给每个插件一块），不用 gpui-shell 自带的 JSON 存储。
- 文件、进程、剪贴板、对话框、通知、打开外部程序。

**原生组件**

脚本跑在 UI 线程、整视图重渲，高频大数据的界面只能用 Rust 写。宿主把它们作为组件交给脚本摆放，组件本身不知道是谁在用：

- 终端（pty 流、网格渲染、IME）
- 对话（ACP 流式渲染、markdown、mermaid）
- Diff（带行评论、hunk 操作）、代码编辑器
- 远程桌面画面

## 宿主接口（2026-11-09 定）

- **宿主服务是一个 gpui 全局。** `smelt-plugin-api` 定义接口，宿主启动时实现并装上，插件用 `smelt_plugin_api::host(cx)` 取：机器列表和客户端、通知、用系统编辑器打开文件、在某台机器上选路径、画页头。运行时话题（`pi_config.changed`、重新订阅上）和机器列表变化由宿主转成插件可订阅的事件（`HostEvent`）。
- **页面按字符串 id 登记。** 注册表记 id、标题、图标、侧栏位置、是否进机器菜单、建视图的函数；工作台路由是 `Page(id)`。宿主里别处跳过去用 `open_page("capabilities", {"tab": "plugins"})`，不出现插件的类型；侧栏入口和机器菜单都按登记生成。路由落盘只记 id，启动时那一页没登记了（插件下线）就回会话；`agents`、`automations`、`desktop`、`session` 是宿主自己的路由，页面不能用这几个 id。
- **插件 crate 只依赖 `smelt-plugin-api` 和 gpui 组件库。** 插件要用的协议类型（`smelt-model`）和共用组件（`smelt-ui`）由 `smelt-plugin-api` 再导出，和 JS 插件拿到的一致。

## 插件的样子

**用户插件**是一个 gpui-shell 文件夹（`gpui-shell.json` + JS），导入文件夹就算装上。

**内置插件**用 Rust 写，每个是一个单独的 crate（`crates/plugins/<name>`），编译进 app。规矩：

1. **宿主接口只有一份**，在 `smelt-plugin-api` crate 里（注册表、smeltd 通道、事件、存储、活动上下文）。Rust 插件直接调它；给 JS 的宿主模块是同一套接口的薄映射，不另造。
2. **边界靠编译器**：插件 crate 只依赖 `smelt-plugin-api` 和 gpui 组件库，不能依赖宿主 crate `smelt`。
3. **注册表按 id，不分语言**：用户导入同 id 的 JS 插件就替换掉内置的 Rust 插件；内置插件也能关掉。
4. **插件之间不互相依赖**：插件 crate 不能依赖别的插件 crate，插件之间只经宿主的事件和命令打交道（JS 插件也只能这样）。
5. **只在画界面上有差别**：Rust 插件直接用 GPUI，JS 插件用 gpui-shell；数据、服务、注册两边拿到的一样。

- **纯脚本插件**：设置页、能力库、额度、历史、自动化等。
- **脚本 + 原生组件**：对话插件用对话组件，终端插件用终端组件；脚本负责数据、交互、摆放。
- 会话列表也是插件：从 smeltd 通道拉会话，自己记选中项，发布「当前会话」话题；打开会话就是让对话或终端插件在舞台面板里显示它。

## 迁移方法

每次拆一个功能，一次提交可编译、可用：

1. 确认它要的宿主能力，按原则 1、2 补进 `smelt-plugin-api`（只补它真用到的），同时补上 JS 映射。
2. 把它的代码搬进 `crates/plugins/<name>`，改成只用插件接口。
3. 从 `Workspace`、`SessionUiState`、`ProjectUiState`、各个写死的枚举和 action 里删掉它的全部代码。
4. 对照本文原则自查：宿主里还有没有它的名字。

顺序从外围到中心：先拆依赖少的功能把宿主骨架（注册表、smeltd 通道、事件、存储）立起来，再拆文件、Git，最后拆会话、对话、终端这三个中心功能。

## 已知缺口

- gpui-shell 没有拖放绑定（会话列表拖动排序要用）、终端组件；Tree 只有 label，编辑器内容不可读写。缺的组件由宿主提供原生组件，或给上游提 PR，不 fork。
- gpui-shell 的 `gpui-shell.json` 拒绝未知字段，插件要声明的面板、命令放在哪里待定（旧分支用另一个 `smelt.json`）。
- 别的插件或客户端改了 smeltd 的数据，靠 smeltd 推事件通知，不靠插件自觉广播。Pi 配置已经这样做了（`pi_config.changed`，放在单独的一条订阅里，v7 的运行时不推）。绕过 smeltd 的修改（手改 Pi 配置文件、直接用 `pi` 命令行）目前收不到，要 smeltd 监视文件才能补上；在那之前，能力库的「刷新」只重读能力库自己，不再顺带让对话重拉模型目录。
- 手机端是 Flutter，跑不了 gpui-shell；插件只影响桌面，手机直接用 smeltd 协议。
