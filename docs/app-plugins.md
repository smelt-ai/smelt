# 整个 app 插件化

> 状态：方向已定（2026-11-09），分支 `feat/app-plugins`。本文只定宿主和插件的边界与迁移方法；每块的接口在拆到它时再定，写回本文。

## 目标

smelt 的每一项功能都是 gpui-shell 插件，用户也能用同一套接口写自己的插件。宿主只提供机制和基础服务，不认识任何具体功能——包括会话。

## 原则

1. **宿主不认识功能。** 宿主代码里不出现「会话列表」「文件树」「Git」这类功能名，也没有它们的枚举、字段、专用 action。判断标准：删掉任何一个插件，宿主不用改一行。
2. **内置插件没有特权。** smelt 自带的插件和用户写的插件走同一套注册点和宿主接口。自带插件需要的能力，就是开给所有插件的能力。
3. **状态归功能自己。** 一个功能的状态只存在它自己那里（插件内存、插件自己的存储），宿主不留副本、不做同步。插件之间要共享的东西由拥有它的插件发布，别人订阅。
4. **等待一律事件驱动。** 宿主到插件的通知用事件（gpui-shell 宿主不能回调脚本，做成插件 await 的异步函数），不让插件轮询。
5. **搬走，不加层。** 拆一个功能就是把它从 `Workspace` 整个搬进自己的插件 crate；不在 `Workspace` 旁边加镜像、适配层，也不留「先搬出来、以后再接插件接口」的中间状态。`Workspace` 只会越来越小。

## 宿主提供什么

**机制**

- 窗口、标题栏、整个工作台的 `DockArea`（布局文件和存档用官方 `DockAreaState`，见 `AGENTS.md`）。
- 注册表：面板、命令、快捷键、设置页、主题。内置和插件同一张表。
- 插件生命周期：发现、加载、卸载、热重载（基于文件变化事件）、按插件分开的 Policy 和日志身份。
- 事件：插件发布话题、订阅话题；宿主自己发布的只有宿主概念（布局变化、窗口、哪个面板获得焦点）。
- 活动上下文：获得焦点的面板可以发布一份通用上下文（运行时、目录、标题等），宿主只转发，不解读。文件、Git 一类插件据此决定看哪个目录。

**基础服务**

- smeltd 通道：连接本机和远程运行时，按协议发请求、收推送。插件拿到的是通道，不是「会话接口」。
- 存储：插件的业务数据进 SQLite（宿主给每个插件一块），不用 gpui-shell 自带的 JSON 存储。
- 文件、进程、剪贴板、对话框、通知、打开外部程序。

**原生组件**

脚本跑在 UI 线程、整视图重渲，高频大数据的界面只能用 Rust 写。宿主把它们作为组件交给脚本摆放，组件本身不知道是谁在用：

- 终端（pty 流、网格渲染、IME）
- 对话（ACP 流式渲染、markdown、mermaid）
- Diff（带行评论、hunk 操作）、代码编辑器
- 远程桌面画面

## 宿主接口（2026-11-09 定）

- **宿主服务是一个 gpui 全局。** `smelt-plugin-api` 定义接口，宿主启动时实现并装上，插件用 `smelt_plugin_api::host(cx)` 取：机器列表和客户端、通知、用系统编辑器打开文件、在某台机器上选路径、画页头、某台机器的智能体配置（`agent_settings`，只读）、某个视图此刻看不看得见（`view_shown`）、某台机器上各会话的守护状态（`session_states`）和对话目录（`workspace_directory`）、哪些会话有待关注的提醒（`attention`）。运行时话题（`pi_config.changed`、`history.changed`、`attention.changed`，原样带着载荷和快照转发；重新订阅上）、机器列表、活动上下文、智能体配置、看得见的视图、会话状态和目录（`SessionsChanged`）、提醒（`AttentionChanged`）的变化由宿主转成插件可订阅的事件（`HostEvent`）。插件据「看得见」决定什么时候读数据，看不见时不读。活动上下文（`active_context`：当前项目、舞台上露着的会话和它是不是停在最新）是 `smelt-plugin-api` 里的一个全局槽，由显示会话的舞台发布、别的插件读，变了发 `ActiveContextChanged`；宿主不解读它。
- **读、变化、动作分开走。** 读是 `Host` 上的同步方法，只读内存；变化是 `HostEvent`，不带数据，收到再读；动作一律是命令。宿主的动作也登记成命令，插件用 `smelt_plugin_api` 里带类型的常量（`Command<参数, 结果>`）调：`NOTIFY`、`OPEN_IN_TEXT_EDITOR`、`PICK_PATHS`、`OPEN_VIEW`、`SHOW_MAIN_WINDOW`、`SET_STATUS_MENU`（菜单栏图标的标题、提示和菜单，菜单项点了执行一条命令）、`SET_DOCK_BADGE`，会话的 `sessions::ACTIVATE`、`RESUME`、`RESUME_IN_TERMINAL`、`HANDOFF`、`SEND_TEXT`。这些要参数，登记时标 `requires_args`：不进命令面板，不能绑快捷键。
- **命令交回结果。** 处理函数返回 `Handled::Done(任务)`，任务交回结果或者失败原因；`run` 把它交给调用方，命令自己不报错。处理函数拿到的主窗口是可选的：主窗口关着时命令照样执行，用不到窗口的（发通知、打开文件、在本机选路径）照常做；本来就是要把人带到主窗口的（`SHOW_MAIN_WINDOW`、`sessions::ACTIVATE`、在远程机器上选路径）先开一扇；其余用得到的交回「主窗口没有打开」。谁调谁处理失败：插件调的自己提示，快捷键、菜单、命令面板执行的由宿主统一发错误通知。
- **插件登记视图，不登记位置。** 视图按字符串 id 登记（`register_view`），只记 id、标题、图标、能不能针对某台机器打开、建视图的函数——插件只说「我能画什么」，摆在哪归宿主（见下面「摆放」）。宿主里别处打开它用 `open_page("capabilities", {"tab": "plugins"})`，不出现插件的类型。能针对机器打开的视图，宿主在每台机器的菜单里给一个入口，打开参数带 `{"machine": …}`：这是视图自己的能力，不是位置。`agents`、`automations`、`desktop`、`session` 是宿主自己的路由，视图不能用这几个 id。
- **JS 插件的宿主模块也叫 `smelt-plugin-api`**，是 Rust 那份接口的薄映射（`smelt_plugin_api::js`）：`active_context`、`agent_settings`、`view_shown`、`next_event`、`run`、`register_themes`、`register_layouts` 等。宿主的动作和 Rust 一样经 `run("<命令 id>", 参数)` 调，返回 Promise，兑现为命令的结果。每个插件一份自己的 gpui-shell Policy（应用名是插件 id），模块装在里面，所以宿主函数知道是哪个插件在调。宿主不能回调脚本，事件做成 `await next_event()`：每个插件一条队列，同样的事件只留一份。每个 JS 插件挂载时登记成一个视图，id 就是插件 id（`plugins::mount_all`），和 Rust 视图一样由布局摆放。注册表缓存建好的视图，登记变了宿主收到 `ViewsChanged`，重装布局（新登记的补上、撤下的变占位）再对路由。
- **设置页按来源登记，宿主管侧栏。** 插件用 `register_settings_pages(来源, 页)` 往设置窗口里加页，id 是 `<来源>/<名字>`；每页给标题、图标、放进哪一组（通用、Agent 与远程、系统、插件，排在宿主自己的页后面）、搜索用的关键词和建页的函数。侧栏、分组、搜索归宿主；页面在设置窗口里第一次点开时才建，切走再回来是同一份，设置窗口关了就放掉，登记换过或撤下也放掉。所以页面打开时从插件自己的库里读当前值，改了马上写回，不靠页面活着保存。页面想和宿主的页长得一样，用 `settings_pane` 包一个组件库的 `SettingPage`。JS 插件登记时给的是插件目录里另一个入口脚本（`entry`），点开时在设置窗口里单独加载、挂载，和主入口是两份实例、不共享内存（像浏览器扩展的 options 页）：值走插件的库，要主入口跟着变就 `run` 它登记的命令；这份脚本里调 `register_*` 一律报错，免得顶掉主入口登记的那组。插件重载、卸载、加载失败时它的设置页跟着撤下。社区做法的比较：VS Code、Raycast、Zed 是声明式的配置项清单，宿主画表单；JetBrains（Configurable）、Obsidian（`addSettingTab`）、浏览器扩展（`options_ui`）是插件自己画页。这里选后者，声明式清单等真有很多插件只要几个开关时再加。
- **主题按来源登记，内置和第三方共用目录。** 主题文件沿用 gpui-kit 的 ThemeSet JSON。插件目录下 `themes/*.json` 是主题贡献；纯主题包把 `gpui-shell.json` 的 `entry` 指向主题 JSON，不需要 JS 视图。JS 插件也可以通过 `register_themes` 登记主题集。重载或卸载时撤下该插件的主题；当前主题不再存在时回落到同明暗的 Default，保留原选择以便重新安装后恢复。主题只在启动和插件变化时读取，不在 render 中读文件。
- **插件 crate 只依赖 `smelt-plugin-api` 和 gpui 组件库。** 插件要用的协议类型（`smelt-model`）和共用组件（`smelt-ui`）由 `smelt-plugin-api` 再导出，和 JS 插件拿到的一致。

## 摆放

插件提供视图，视图摆在哪是布局的事。最终整个窗口是一块 `DockArea`，布局就是一棵任意的拆分树（横竖任意嵌套，叶子是标签组），用官方 `DockAreaState` 存；没有「左侧栏 / 舞台 / 右面板」这种固定区域，现在的三栏只是自带的那份默认布局。所以：

- **视图里面怎么画归插件**：gpui-shell 脚本或 Rust 视图里自己排版，想画什么画什么。
- **视图之间怎么摆归布局**：布局文件是纯数据，引用视图 id。插件可以带一份布局一起导入，比如股票看板插件登记「行情列表」「K 线」两个视图，再带一份「左列表、右 K 线」的布局；切到这份布局时窗口里只有这两块，会话列表、对话不在里面也没关系——它们也只是视图。
- **布局里没提到的视图**（刚装的插件）由宿主放到一个默认位置；用户拖到哪，存档记到哪。
- 位置提示也不进视图登记（不加「我想在左边」之类的字段），要给就写在布局文件里。

现在（2026-11-10）：

- 整个工作台已经是一块 `DockArea`（`Workspace::shell_dock`，外壳画法见 `workspace_shell.rs`，装布局、存档见 `workspace_layout.rs`）。面板名就是视图 id；`DockAreaState` 原样存进客户端库的 `workspace_layout_state`，按布局 id 一份；布局文件变了存档照用，要新版本就删存档。
- 布局由插件登记（`register_layouts`，JS 同名），按来源整组登记，id 是 `<来源>/<名字>`（JS 插件的来源就是插件 id），所以插件替换不了别人的布局。宿主不认识任何一份：出厂的默认布局在内置插件 `crates/plugins/layouts`（`smelt/default`：会话列表在左停靠区，舞台在中间，文件、变更、历史、技能在右停靠区）。
- 用哪份在设置的外观里选，存在 `appearance.layout_id`。装的是：选的登记着就用它，否则用登记的第一份，一份都没有就把所有视图摆在中间一组（不存档）。选的那份没登记（插件还没加载、被卸了）时选择不改，它登记上就换过去。登记变了（`LayoutsChanged`）、选择变了宿主重新挑，和装着的不同才换；插件重载、卸载、加载失败都撤下它的布局。外观里的「恢复」删掉当前布局的存档，回到它本来的样子。「把视图加进布局」的命令还没做。
- 收起是停靠区的，不是视图的：`DockAreaState` 的左右停靠区（`left_dock`、`right_dock`）各自记着开合和宽度，外壳在窗口左上角（交通灯右边）和右上角各画一个开合按钮，布局里有这个停靠区才画。视图不知道自己能不能收起，也不自己画开关：放进左右停靠区的就能收，放在中间的不能。不做开合的命令和快捷键：布局可以任意嵌套，「左侧栏」不是一个固定的东西。打开一个在收起停靠区里的视图（比如聚焦侧栏）会先展开它。下停靠区还没给开合按钮。
- 布局里没摆的视图在侧栏给入口，当舞台上的一页打开；摆进布局的就在布局里看。布局里提到却没登记的视图、同一个 id 摆了两次的，都占着位置但不显示，存档原样留着，装回来就回来。
- 面板不能关，只能拖动、放大（Esc 还原）、随停靠区收起。会话列表、舞台单独一组时自己画顶栏（交通灯、拖窗口），外壳不给它们画标题带。
- 舞台还是一个视图里装着会话、智能体、自动化、桌面和没摆进布局的页面这几种路由；拆成各自的视图是后面的事。

## 插件的样子

**用户插件**是一个 gpui-shell 文件夹，导入文件夹就算装上。纯主题包不需要 JS：

```text
my-theme/
  gpui-shell.json
  themes/colors.json
```

```json
{"id":"com.example.my-theme","name":"我的主题","version":"1.0.0","entry":"themes/colors.json"}
```

`colors.json` 是 gpui-kit 的 ThemeSet，例如：

```json
{"name":"我的主题","themes":[{"name":"我的深色主题","mode":"dark","colors":{"background":"#1a1b26","foreground":"#c0caf5","primary.background":"#7aa2f7"}}]}
```

在设置的「面板插件」里导入整个目录，再到「外观」选择主题。主题包不会新增面板。

**内置插件**用 Rust 写，每个是一个单独的 crate（`crates/plugins/<name>`），编译进 app。规矩：

1. **宿主接口只有一份**，在 `smelt-plugin-api` crate 里（注册表、smeltd 通道、事件、存储、活动上下文）。Rust 插件直接调它；给 JS 的宿主模块是同一套接口的薄映射，不另造。
2. **边界靠编译器**：插件 crate 只依赖 `smelt-plugin-api` 和 gpui 组件库，不能依赖宿主 crate `smelt`。
3. **注册表按 id，不分语言**：用户导入同 id 的 JS 插件就替换掉内置的 Rust 插件；内置插件也能关掉。
4. **插件之间不互相依赖**：插件 crate 不能依赖别的插件 crate，插件之间只经宿主的事件和命令打交道（JS 插件也只能这样）。
5. **只在画界面上有差别**：Rust 插件直接用 GPUI，JS 插件用 gpui-shell；数据、服务、注册两边拿到的一样。

- **纯脚本插件**：设置页、能力库、额度、历史、自动化等。
- **脚本 + 原生组件**：对话插件用对话组件，终端插件用终端组件；脚本负责数据、交互、摆放。
- 会话列表也是插件：从 smeltd 通道拉会话，自己记选中项，发布「当前会话」话题；打开会话就是让对话或终端插件在舞台面板里显示它。

## 迁移方法

每次拆一个功能，一次提交可编译、可用：

1. 确认它要的宿主能力，按原则 1、2 补进 `smelt-plugin-api`（只补它真用到的），同时补上 JS 映射。
2. 把它的代码搬进 `crates/plugins/<name>`，改成只用插件接口。
3. 从 `Workspace`、`SessionUiState`、`ProjectUiState`、各个写死的枚举和 action 里删掉它的全部代码。
4. 对照本文原则自查：宿主里还有没有它的名字。

顺序从外围到中心：先拆依赖少的功能把宿主骨架（注册表、smeltd 通道、事件、存储）立起来，再拆文件、Git，最后拆会话、对话、终端这三个中心功能。

## 已知缺口

- gpui-shell 没有拖放绑定（会话列表拖动排序要用）、终端组件；Tree 只有 label，编辑器内容不可读写。缺的组件由宿主提供原生组件，或给上游提 PR，不 fork。
- gpui-shell 的 `gpui-shell.json` 拒绝未知字段，所以脚本通过宿主函数登记能力；纯数据主题约定放在 `themes/*.json`。命令也是：JS 用 `register_commands` 登记、`next_command` 取执行，`run` 执行别人的命令（Promise，失败 reject；脚本登记的命令接到就算成功）。命令只管工作台级的动作；视图里面、意思随焦点变的键（列表上下、输入框编辑）用视图自己的 action（JS 是 gpui-shell 的 `ShellAction`），不能改键，不进命令面板。
- **自带视图还是 `Workspace` 代画的**（`builtin_views.rs`）：会话列表、舞台、文件、变更的状态和画法都还在 `Workspace` 上（历史已拆成内置插件 `crates/plugins/history`），适配层把它们包成视图登记进注册表，外壳和布局已经不认识它们。这正是「参考」里说不要的封闭枚举，只是过渡：按「迁移方法」每拆走一块，就从适配层删掉一项，删空为止。
- 用户能拖、能放大、能换插件带的布局，但加不了没摆进去的视图（见「摆放」）。
- 别的插件或客户端改了 smeltd 的数据，靠 smeltd 推事件通知，不靠插件自觉广播。Pi 配置已经这样做了（`pi_config.changed`，放在单独的一条订阅里，v7 的运行时不推）。绕过 smeltd 的修改（手改 Pi 配置文件、直接用 `pi` 命令行）目前收不到，要 smeltd 监视文件才能补上；在那之前，能力库的「刷新」只重读能力库自己，不再顺带让对话重拉模型目录。
- 手机端是 Flutter，跑不了 gpui-shell；插件只影响桌面，手机直接用 smeltd 协议。
- 接口里还有些是照着宿主现在的样子开的口子，拆到对应的功能时收掉或换成通用的：

  | 接口 | 为什么是过渡的 | 什么时候收 |
  | --- | --- | --- |
  | `Machine.has_desktop` | 远程桌面是一个功能，不是机器的属性 | 外围功能拆分（第 3 步） |
  | `RESERVED_VIEW_IDS`（`agents`、`automations`、`desktop`、`session`） | 舞台路由还写死在宿主里 | 外围功能（第 3 步）、对话和终端视图（第 5 步） |
  | `page_header` | 页头画法是舞台的，插件该自己画 | 对话和终端视图拆成插件（第 5 步） |
  | `sessions::RESUME`、`RESUME_IN_TERMINAL`、`HANDOFF`、`SEND_TEXT` | 由宿主里的会话代码处理 | 对话和终端视图拆成插件（第 5 步） |
